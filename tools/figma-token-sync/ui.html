변수로 가져오기

build/tokens.figma.json을 붙여넣거나 파일로 선택해 Import 합니다.

자세히

재실행해도 기존 변수를 갱신할 뿐 중복 생성되지 않습니다.

"드리프트 점검"은 아무것도 바꾸지 않고 위 JSON 과 이 파일의 변수를 대조만 합니다 — 누락(빌더가 throw 하는 원인) · 값 불일치(조용히 틀리게 렌더되는 원인) · 라이브 전용(코드가 모르는 변수)을 각각 나눠 보고합니다.

소비 프로젝트 컬렉션 오버라이드

활성화된 변수 라이브러리에서 필요한 CoUI 컬렉션만 골라 이 파일의 확장 컬렉션으로 자동 생성합니다. 원본에 새 변수가 추가되면 계속 상속하고, 이 파일에서는 바꾼 값만 저장됩니다.

자세히

라이브러리 컴포넌트가 이미 참조하는 변수를 실제로 덮어쓰려면 Figma의 Extended Variable Collection이 필요합니다. 같은 이름의 일반 로컬 컬렉션을 복사해도 기존 바인딩에는 적용되지 않습니다. Figma는 이 기능을 Enterprise 플랜 기능으로 안내하지만 그 밖의 플랜에서도 만들어질 수 있습니다 — 거부되면 그 이유를 알립니다. 먼저 Assets에서 CoUI 라이브러리를 활성화하세요.

라이브러리 컬렉션을 불러오는 중…

"다시 맞추기"는 이 파일의 확장 컬렉션마다 덮어쓰기가 없는 변수를 이름으로 다시 채웁니다. 브랜드 탭에서 만든 코드 브랜드의 확장은 브랜드 값 표로, 그 밖의 확장은 이름과 타입이 같은 로컬 변수의 별칭을 모든 모드에 넣고, 짝이 없는 변수는 로그에 적습니다. 라이브러리 컴포넌트를 넣은 뒤나 파일을 다시 연 뒤에 돌리세요 — 다시 열면 이 파일이 쓰지 않던 라이브러리 변수가 덮어쓰기와 함께 정리되고, 다시 들어온 변수는 덮어쓰기 없이 CoUI 기본값으로 칠해집니다.

팔레트 생성

8개 HSL 입력(color_palette.json)으로 CoUI Primitive 64색을 제자리에서 다시 칠합니다.

자세히

PrimitiveColors.generate의 8개 입력값으로 파일 전체를 다시 테마 적용합니다 (h 0–360, s/l 0–100). 변수를 추가하지 않습니다: 64개 Primitive 색상을 제자리에서 다시 칠할 뿐이라 Semantic과 모든 컴포넌트가 그대로 따라갑니다. 로그에 바로 붙여넣을 수 있는 Dart 코드 스니펫이 출력됩니다. 먼저 변수로 가져오기를 실행하세요.

컴포넌트

Import된 변수에 바인딩해 CoUI 컴포넌트를 캔버스에 반영합니다 — 변수 Import 이후에 실행하세요.

자세히

섹션 구분은 docs 사이트(coui.cocode.im/components-overview)의 그룹과 동일합니다. 반영·전체 새로 생성 모두 노드를 지우고 다시 만들지 않습니다 — 이름으로 찾아 그 자리에서 다시 그리는 것이라 컴포넌트의 id/key가 보존되고, 이미 배치한 인스턴스가 따라옵니다. 더 이상 만들어지지 않는 멤버는 지우지 않고 거부합니다(유령은 폐기된 컴포넌트 제거). 섹션 사이에 의존성이 있어(예: Form 의 입력 컴포넌트들이 Icon·Control 의 부품을 사용) 처음 채울 때는 전체 새로 생성을 쓰고, 그 뒤부터 섹션을 나눠 컴포넌트 반영으로 재실행하세요.

체크하면 ❖ 컴포넌트 페이지와 섹션 헤더를 문서 사이트 카탈로그 순서로 맞춘다 — 이미 순서가 맞는 페이지는 두고, 헤더는 자기 블록 첫 페이지 바로 위에 둔다. 직접 만든 디바이더 · 강등 메모 · 시안 페이지는 움직이지 않는다. 이미 맞는 파일에서는 아무것도 옮기지 않는다. 체크하지 않아도 새로 만든 페이지(빠진 섹션 헤더 포함)는 맨 끝이 아니라 제 섹션에 놓인다.

선택한 컴포넌트를 레시피가 그대로여도 다시 그린다. 캔버스가 코드와 어긋났는데 반영이 "변경 없음"으로 건너뛸 때 쓴다. 실행이 끝나면 자동으로 해제된다.

멤버를 세트에 되붙이는 동안 현재 페이지를 다른 페이지로 옮긴다 — 열린 페이지의 세트에 붙일 때마다 렌더러가 갱신된다는 가설의 실험. 켜고 끈 두 실행의 ⏱ finish 를 비교한다(켠 실행은 페이지 밖 으로 표시). 효과가 없으면 이 옵션은 사라진다.

리디자인은 원본 옆 사본에서 한다 — 세트를 ⌘D 로 복제해 같은 페이지 최상위에 <이름>(리디자인) 으로 두면 그것과 새로 그린 세트를 값으로 대조해 차이를 로그에 낸다(⇄). 이 줄이 "차이 없음" 이면 대조가 읽는 값(색 · 크기 · 보더 · 글자 · 아이콘 · 패딩 · 간격)은 사본과 같다 — 효과 · 정렬 · 컴포넌트 속성은 따로 확인한다 (docs/contributing/design-collaboration.md 3장). 세트를 직접 고친 경우의 보존은 사고 대비다 — 다시 그릴 세트에 지난 실행 뒤 손이 닿았으면 그 그림을 <이름> (리디자인 · 시각) 프레임으로 오른쪽에 남기고, 손 사본이 없을 때만 그것을 기준으로 삼는다. 감지가 모든 편집을 잡는다는 보장은 없다.
지문이 없어 손이 닿았는지 판단할 수 없었던 세트는 <이름> (이전 · 시각) 백업만 남기고 대조하지 않는다 — 그것은 어제의 생성본이지 리디자인의 의도가 아니다(백업은 세트당 하나, 손 편집 보존본은 지우지 않는다). 전체 결과는 designer-parity-*.json 으로도 내려온다 — 로그는 세트당 14 줄에서 잘리지만 파일은 잘리지 않는다. 지문은 다시 그린 세트에만 남는다 — 기존 파일에서 보존을 전 세트에 켜려면 아래 두 번째 체크를 켜고 전체 새로 생성을 한 번 돌려야 한다. 그 전까지 아직 한 번도 다시 그려지지 않은 세트는 손 편집 여부를 알 수 없어 개수만 보고된다.

컴포넌트 목록을 불러오는 중…

선택 없음

선택한 컴포넌트 중 레시피가 바뀐 것만 골라 지금 코드대로 제자리에서 다시 그린다. 노드 id/key 는 유지되므로 이미 배치한 인스턴스는 따라온다. 해시는 레시피만 본다 — 캔버스가 틀렸는데 레시피가 그대로면 건너뛴다. 그때는 위 변경 없어도 다시 그리기 또는 아래 전체 새로 생성을 쓴다.

그리지 않는다. 선택과 무관하게 레지스트리 전 엔트리의 캔버스 해시를 지금 코드와 대조해, 다음 반영이 다시 그릴 세트만 센다.

그리지도 지우지도 않는다. 모든 페이지의 직계 자식 중 세트·docs 프레임·디자이너 사본이 아니면서 원점에 떠 있는 것만 센다 — 어디에도 붙인 적이 없다는 신호다. 같은 줄이 컴포넌트 반영 끝에도 붙는다.

그리지도 지우지도 않는다. 세트 변형마다 같은 이름의 직계 자식이 다른 세션의 id 대역으로 한 벌 더 있는 것만 센다 — 같은 세션이 만든 반복(item × 4)은 빠진다. 페이지 직계의 잔해는 고아 노드 보기가, 중첩 인스턴스의 프로퍼티는 재생성만이 본다. 같은 줄이 컴포넌트 반영 끝에도 붙는다.

그리지도 고치지도 않는다. 모든 페이지의 세트·컴포넌트가 선언한 프로퍼티(변형 축 제외) 중 어느 노드도 참조하지 않는 것을 센다. 기대값은 0 이다. 정의를 읽을 수 없는 세트는 따로 한 줄로 나온다.

선택·해시와 무관하게 모든 컴포넌트를 제자리에서 다시 그린다 — 노드를 지우고 새로 만들지 않으므로 id/key 는 유지된다. 페이지 순서 정리도 켠 채로 돈다(❖ 페이지 · 섹션 헤더만 옮기고 직접 만든 디바이더는 그대로). 새 문서를 처음 채울 때, 또는 레시피는 그대로여서 반영이 건너뛸 때 쓴다. 오래 걸린다.

브랜드 확장 컬렉션

CoUI 의 색 컬렉션(Semantic/ Color · CoUI)을 이 파일의 확장 컬렉션으로 열고, 코드 브랜드의 값을 덮어쓰기로 채웁니다. 화면과 컴포넌트의 연결은 CoUI 변수 그대로이고 값만 확장 컬렉션이 덮습니다.

자세히

브랜드 값의 정본은 코드(export_figma_tokens.dart 의 브랜드 목록)입니다. 이 플러그인 빌드에 든 표가 그 값이고, 표는 브랜드가 CoUI 와 다른 값만 담아 나머지는 CoUI 를 따라갑니다. Figma 가 플랜을 이유로 확장 컬렉션을 거부하면 그 이유를 알리고, 먼저 Assets 에서 CoUI 라이브러리를 활성화해야 합니다. 값을 채운 뒤에는 선택한 레이어(선택이 없으면 현재 페이지)가 그 브랜드 모드를 쓰도록 모드를 옮깁니다 — 확장은 그 모드를 쓰는 화면에만 칠해집니다. 이미 만든 브랜드는 컬렉션을 다시 만들지 않고 값만 다시 채웁니다. 파일을 다시 열면 이 파일이 쓰지 않는 변수의 덮어쓰기가 정리되므로, 컴포넌트를 넣은 뒤 토큰 탭의 이름으로 다시 맞추기를 돌리세요.

고정폭 글의 한글을 본문 서체로

선택한 프레임(선택이 없으면 현재 페이지 전체)의 고정폭(Geist Mono) 글에서 한글 구간만 본문 서체(Pretendard)로 칠합니다. 글을 고쳐 쓰면 다시 돌리세요.

자세히

Geist Mono 에는 한글이 없어, 앱과 웹은 한글을 본문 서체로 대신 그립니다. Figma 는 대신할 글꼴을 고를 수 없어 이 명령이 한글 구간의 글꼴과 fontFamily 변수만 본문 서체로 바꿉니다. 크기 · 행간 · 자간은 건드리지 않습니다. 다른 고정폭 서체로 쓴 글은 바꾸지 않고 목록으로 알려줍니다. 텍스트 스타일이 붙은 글은 칠한 구간이 스타일에서 갈라질 수 있습니다. Cmd/Ctrl+Z 로 되돌릴 수 있습니다.

소비 파일 점검

제품 화면 파일에서 돌립니다. 보이는 글자 중 코드로 옮길 때 CoUI 와 갈라지는 것을 같은 값끼리 묶어 보여 주고, 같은 라이브러리 변수를 두 번 가져온 옛 사본과 옛 브랜드 컬렉션에 묶인 곳을 파일 전체에서 찾습니다. 점검은 아무것도 바꾸지 않습니다 — 항목을 누르면 그 노드를 선택하고 화면을 옮깁니다.

자세히

덮어쓰기 — CoUI 컴포넌트 안 글자의 모양을 인스턴스에서 바꿨습니다. 역할에 없는 조합 — 크기 · 행간 · 자간 · 글꼴 중 하나라도 역할과 다릅니다(가장 가까운 역할을 함께 보여 줍니다). 스타일 없음 — 값은 역할과 같은데 역할에 연결돼 있지 않습니다. 로컬 스타일 — CoUI 라이브러리가 아닌 텍스트 스타일입니다. CoUI 스타일, 역할 변수에 묶고 굵기만 바꾼 글자, 고정폭 글 안에서 본문 서체로 칠한 한글, 덮어쓰지 않은 컴포넌트 안 글자는 통과입니다. 크기는 글자가 그려지는 타이포 모드(Mobile · Tablet · Desktop)의 값과 견줍니다. 주석처럼 점검할 필요 없는 레이어는 이름을 적어 건너뜁니다(그 아래 글자 수는 따로 세고, 찾지 못한 이름은 로그에 적습니다). 적은 이름은 이 컴퓨터에 기억해 다음에 다시 채웁니다.

가져온 사본 중복 — 이 파일이 같은 라이브러리 변수를 두 번 가져와 사본이 둘입니다. 옛 사본에 묶인 레이어는 라이브러리가 바뀌어도 옛 값으로 남고, 사본이 둘인 변수는 확장 컬렉션에서 덮어쓸 수 없습니다. 범위와 상관없이 파일 전체를 보고, 옛 사본마다 그것을 참조하는 노드 · 스타일 · 별칭의 수와 현재 사본과의 모드별 값 차이를 보여 줍니다.

옛 브랜드 컬렉션 — 화면이 브랜드마다 따로 게시되던 라이브러리 컬렉션(Semantic/ Color · <브랜드>)에 묶여 있습니다. 브랜드 확장 컬렉션은 Semantic/ Color · CoUI 변수만 덮으므로 그 자리는 브랜드 값이 바뀌어도 따라오지 않습니다. 변수마다 그것을 참조하는 곳의 수와 같은 이름의 CoUI 변수(짝)가 있는지를 보여 줍니다. 브랜드 원시값(color/<브랜드>/…)에 직접 묶인 곳은 따로 셉니다.

"옛 사본 다시 연결"은 문서를 바꿉니다 — 모든 페이지에서 옛 사본을 참조하는 채움 · 선 · 효과 · 그 밖의 필드와 로컬 스타일 · 로컬 별칭을 현재 사본으로 옮깁니다. 라이브러리 컴포넌트 안에서 덮어쓰지 않은 자리는 건드리지 않습니다. 끝나면 파일을 닫았다가 다시 열어 옛 사본을 정리하고, 토큰 탭의 "다시 맞추기"를 돌립니다.

"옛 브랜드 컬렉션 다시 연결"도 문서를 바꿉니다 — 모든 페이지에서 옛 브랜드 컬렉션의 변수를 참조하는 곳을 같은 이름의 Semantic/ Color · CoUI 변수로 옮깁니다. 범위는 "옛 사본 다시 연결"과 같습니다. 짝이 없는 이름과 브랜드 원시값에 직접 묶인 곳은 옮기지 않고 로그에 적습니다. 끝나면 파일을 닫았다가 다시 열고, 토큰 탭의 "이름으로 다시 맞추기"를 돌립니다.

자세히

mint-by-name (#3737)이 실제로 identity를 보존하는지 확인합니다. "identity 멱등성"은 Generate Components를 두 번 실행해 두 실행 사이에 어떤 컴포넌트의 id/key도 바뀌지 않았는지 검사합니다(빠름). "reset 완전성"은 임시 페이지에서 항목 하나(비워두면 전체 — 느림, 수 분 소요)를 두 번 빌드해, 새로 만든 노드와 재사용된 노드 사이의 PNG와 바인딩된 변수를 비교합니다.

"충실도 → .json"은 "충실도"와 같은 검사를 돌린 뒤 결과를 파일로 내려받습니다 — 로그는 창을 닫으면 사라지지만 파일은 남습니다. "구조 → .json"은 전 페이지의 노드 구조·기하(id·이름·타입·x/y/w/h)를 한 파일로 내려받습니다 — reverse/incoming/ 에 커밋하면 구조 드리프트 대조(Channel A)의 입력이 됩니다. "픽셀 → .json"은 플러그인이 그린 세트·컴포넌트마다 PNG 를 내보내 해시를 적습니다(수 분 소요) — 두 실행 뒤에 하나씩 받아 npm run pixel:diff -- A.json B.json 으로 견주면 그림이 달라진 세트가 나옵니다.

내려받은 파일은 어디에 두나요?

레포 checkout 이 없다면 — 대개 이 경우입니다 — 파일을 그대로 엔지니어에게 전달하세요(Slack 이든 이슈 첨부든 상관없습니다). 넣을 자리와 커밋은 받은 쪽이 처리합니다.

checkout 이 있다면 tools/figma-token-sync/reverse/incoming/ 에 넣고 main 에서 브랜치를 따 커밋한 뒤 PR 을 올리세요 — 커밋되지 않은 파일은 자동화가 읽지 못합니다.

한 번 실행 = 파일 하나입니다. 여러 개가 쌓이면 파일명이 가장 뒤인 하나만 읽히고 나머지는 조용히 버려지니, 새로 내보냈으면 이전 파일은 지우세요.

성능 프로브

임시 페이지에 합성 세트(64 · 256 · 972 멤버, 멤버당 노드 15)를 만들어 세트 안·밖 호출 비용을 잰 뒤 전부 지웁니다 — 큰 문서에서는 수 분이 걸립니다. 결과는 표 한 장과 H1/H2 판정 한 줄.

자세히

Generate 의 ⏱ 줄은 실제 실행에서 역산한 추정입니다. 이 프로브는 같은 호출을 격리해서 20회씩 재고 중앙값을 냅니다: 세트 안 노드와 loose 멤버의 fills 쓰기, 직전 읽기가 있는·없는 속성 참조 쓰기, 직전 쓰기가 있는·없는 .visible 읽기, 재조립의 append 와 그 뒤 variantProperties 읽기, 2멤버 세트 스테이징 왕복, 텍스트 스타일 부착, 세트가 현재 페이지일 때와 아닐 때의 append. 표 끝의 판정은 "쓰기가 세트 크기에 비례"(H1) 와 "쓰기 뒤 읽기가 재유도"(H2) 중 표가 지지하는 쪽을 말합니다. 실제 빌더는 쓰지 않으며 문서 인덱스도 건드리지 않습니다.

마지막 단계

생성이 로그 없이 멈췄을 때 — 플러그인을 다시 열고 누르면, 그 실행이 문서에 마지막으로 남긴 위치와 그 뒤로 지난 시간, 그리고 큰 세트가 25콤보마다 남긴 성장 발자국(어느 구간이 콤보가 갈수록 비싸지는지)을 보여줍니다. 실행 중에 누르면 다음 틱에 답합니다 — 세트 재조립·속성 바인딩처럼 await 가 없는 구간에서는 그 구간이 끝난 뒤에 답합니다.
