# Socratic discovery — Neo-brutalism 커스텀 스타일

> 요청: "neobrutalism 디자인 적용이 커스텀 스타일 가능하도록 개선" + neobrutalism.dev 레퍼런스 + 스크린샷 4장(blue/green/orange/violet).
> 이 문서는 그 한 줄이 **감추고 있던 전제**를 드러낸 기록이다. 답이 결정으로 굳은 것은 `decision-log-neobrutalism-custom-style.md`.

## Q1 — "커스텀" 을 누가 하는가

스크린샷은 **문서 사이트의 라이브 커스터마이저**다. 실제 제품에서 그 화면이 뜻하는 바는 두 가지로 갈린다.

- (a) 앱 개발자가 빌드 시점에 한 번 고른다 — 제품은 하나의 룩을 가진다.
- (b) 최종 사용자가 런타임에 고른다 — 제품이 테마 피커를 노출한다.

**두 요구는 transport 가 다르다.** (a) 는 `ThemeConfig` 생성 시점에 CSS 로 구워지면 끝이고, (b) 는 Web 에서 리빌드 없이 CSS 변수를 덮어써야 한다(현재 style switcher 는 `data-coui-style` attribute 만 쓰는데, attribute 로는 **연속값을 고를 수 없다** — 값마다 선택자가 하나씩 필요해진다).

레퍼런스 사이트가 (b) 처럼 보인다고 해서 요청이 (b) 인 것은 아니다. 그 사이트가 파는 것은 커스터마이저가 아니라 **커스터마이즈된 결과물**이고, 커스터마이저는 그걸 보여주는 데모다.

## Q2 — 스크린샷 4장의 차이 중 이미 되는 것은 무엇인가

"강조색이 4가지" 가 새 기능처럼 보이지만, `CoreSurfaceColorConstraint` 는 **hue 를 의도적으로 건드리지 않는다**. 강조 hue 는 앱 팔레트가 정하므로 blue/green/orange/violet 은 오늘도 `PrimitiveColors` 교체만으로 나온다.

그래서 진짜 없는 것만 남는다 — **페이지 배경이 강조 hue 를 따라가는 것**, 그리고 **모서리·그림자·테두리를 앱이 정하는 것**. 요청을 "색 커스터마이즈" 로 읽으면 이미 있는 것을 다시 만들게 된다.

## Q3 — 배경 틴트는 무엇까지 물들이는가

스크린샷을 확대해 보면 세 층이 서로 다른 색이다.

| 층 | 색 |
|---|---|
| 페이지 배경 | 강조 hue 의 저채도 (연한 blue/green/cream/lavender) |
| 컴포넌트 채움 (Alert · Accordion header · Button · Badge · Select) | 강조색 그대로 |
| Accordion 본문 | **흰색** — 틴트되지 않음 |

"배경을 강조색으로" 를 `surface*` 전체에 적용하면 세 번째 층이 사라진다. 틴트 대상은 **페이지(`surface`)뿐**이고 `surfaceContainer*` 는 남아야 한다는 것이 스크린샷이 실제로 말하는 바다.

## Q4 — 앱이 hue 를 자유롭게 고르는데 대비는 누가 보증하는가

이게 이 기능의 유일한 난제다. `docs/preset-acceptance-gate.md` G4 는 프리셋이 색을 굽히면 **감사된 스킴을 등록**하라고 요구하고, CI(`_checkPresetCoverage`)가 그걸 강제한다. 그런데 앱이 hue 를 고르면 등록할 스킴이 앱마다 달라진다 — 등록이라는 방법 자체가 성립하지 않는다.

세 가지 답이 가능했다.

1. **색은 커스터마이즈에서 빼고 기하만 연다.** 게이트는 지켜지지만 스크린샷의 배경 틴트를 못 만든다.
2. **앱이 자기 조합을 직접 감사한다.** CoUI 가 도구를 주고 책임을 넘긴다 — 아무도 안 돌리고, 안 돌린 사실은 화면에 안 나타난다.
3. **자유 파라미터(hue)의 최악값을 CI 가 훑는다.** 크기를 bound 로 묶고, hue 0~360 전 범위에서 최악의 쌍이 임계를 넘는지 증명한다.

3번만이 "앱이 무엇을 고르든 안전" 을 **구조적으로** 보증한다. 1번은 요청을 못 채우고, 2번은 보증이 아니라 보증의 외주다.

## Q5 — 두께를 0 으로 두면 계약이 거짓이 되는가

neo-brutalism 의 `boundaryMechanism` 은 `.stroke` 다 — 강제 색상 모드에서 경계가 살아남는 근거가 그 선언이다. 앱이 `strokeFloor` 를 0 으로 두면 그 선언은 **값이 아니라 거짓말**이 된다.

두 갈래가 있었다: a11y 계약을 레시피에서 파생시키거나, 파라미터 범위가 계약을 깨지 못하게 막거나. 전자는 앱이 계약을 바꿀 수 있다는 뜻이고, 계약은 **앱이 협상할 대상이 아니다**.

## Q6 — 그림자를 키우면 눌림 피드백은 따라오는가

`pressedTranslateOffset` 은 `shadowOffsetAdd` 에서 파생된다(하드코딩이 아니다). 즉 오프셋을 키우면 눌렸을 때 이동량도 같이 커진다 — **이미 연동돼 있다**. 이 사실이 없었다면 파라미터 하나가 두 값을 갈라놓았을 것이다.

같은 확인이 Web 에도 필요했다: Web 은 `geometry.radius(step)` 의 **결과값**을 CSS 변수로 굽는다. 변환식이 아니라 결과가 나가므로, 레시피만 바뀌면 CSS 가 따라온다.

## Q7 — 이건 neo-brutalism 만의 기능인가

요청은 neo-brutalism 이지만 막힌 지점은 `CoreSurfaceRecipe.presets` 가 `static const` 라는 것 하나다. 그 자물쇠는 프리셋 종류를 모른다.

메커니즘을 neo-brutalism 전용으로 만들면 다음 프리셋에서 같은 자물쇠를 두 번째로 열게 된다. 반대로 메커니즘을 프리셋 무관으로 두더라도 **검증과 문서는 한 프리셋에서 먼저 끝나야** 한다 — 네 프리셋의 범위를 동시에 정하는 것은 근거 없이 넓히는 일이다.
