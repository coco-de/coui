## 1. Flutter

### 1-1. 언제 걸리나

- **고르는 자리는 하나입니다.** `CoUILayer.build` 의 `scaling ?? AdaptiveScaler.defaultScaling(theme)` (`packages/coui_flutter/lib/src/coui_app.dart:727`). 앱 경로에서 `defaultScaling` 을 부르는 곳은 여기 하나입니다. 저장소 안의 다른 호출은 공개 함수 `defaultScalingOf` 가 그대로 넘기는 것 하나입니다(`theme.dart:80`). 표면 스타일을 적용한 뒤에 곱합니다(`:766`).
- **기준은 OS 플랫폼 하나입니다.** `defaultScaling` 은 `theme.platform` 으로 갈립니다(`packages/coui_flutter/lib/src/theme/theme.dart:83-94`). `theme.platform` 은 따로 정하지 않으면 `defaultTargetPlatform` 입니다(`theme.dart:355`).
- 같은 판정을 공개 함수 `AdaptiveScaler.defaultScalingOf(context)` 로도 꺼낼 수 있습니다(`theme.dart:77-81`).

| 플랫폼 | 배율 (실측) |
|---|---|
| iOS · Android | **1.25** (`AdaptiveScaling.mobile`, `theme.dart:35`) |
| macOS · Windows · Linux · Fuchsia | 1 (`AdaptiveScaling.desktop`, `theme.dart:34`) |

- **화면 크기는 보지 않습니다.** iOS · Android 태블릿도 1.25 입니다.
- **Flutter 를 Web 으로 빌드해도 휴대폰 브라우저에서는 1.25 입니다.**
  - 배율 경로는 `kIsWeb` 을 보지 않습니다(`kIsWeb` 은 `coui_app.dart:353, 520, 800` 의 우클릭 메뉴 · 텍스트 선택에만 쓰임).
  - Flutter SDK 가 브라우저 OS 로 플랫폼을 정하고, 모르는 OS 는 `android` 로 봅니다(SDK `packages/flutter/lib/src/foundation/_platform_web.dart:50-59`, 모르는 OS 는 `:57-58`).
  - "Mac 이라고 하면서 터치 지점이 2개보다 많으면" iPad 로 봅니다(SDK `bin/cache/flutter_web_sdk/lib/ui_web/ui_web/browser_detection.dart:150-178`, 같은 내용이 `lib/ui/ui_web/src/ui_web/` 에도 있음). 그래서 데스크톱 모드 iPad 도 1.25 일 것입니다 **(추정)**.
  - 그러므로 이 결정에서 말하는 "Web" 은 **Jaspr `coui_web`** 입니다. Flutter Web 앱이 아닙니다.
- **`flutter test` 에서도 1.25 입니다.** 테스트 환경은 `android` 로 판정됩니다(SDK `_platform_io.dart:29-33`). `CoUIApp` 을 띄우는 테스트는 따로 고정하지 않으면 1.25 로 돕니다(실측).
- **`CoUIApp` 없이 쓰면 1 입니다.** `ThemeData()` 의 기본 `scaling` 이 1 이기 때문입니다(`theme.dart:117`). 공개 위젯 `CoUILayer` 를 직접 쓰면 플랫폼 기본값이 걸립니다.

**테두리는 두 갈래입니다.**

- 공용 함수 `stroke()` 호출 51곳 중 **43곳은 `scaling:` 을 넘겨 곱하고, 8곳은 곱하지 않습니다**(실측: 호출의 인자 목록에 `scaling:` 이 있는지로 분류, `21ba1698a` 에서 다시 셈). 공용 함수가 `px × scaling` 을 냅니다(`packages/coui_core/lib/src/surface/surface_geometry_constraint.dart:293-297`).
- 곱하는 곳의 예: TextField(`text_field_style.dart:621-626`), OutlinedContainer(`outlined_container_style.dart:388-393` — 위젯 `OutlinedContainer(` 를 호출하는 파일 34개(정의 파일 제외, 주석 제외), 컴포넌트 폴더 34개; Checkbox · Card · Command 등), FocusOutline, Popup, Avatar 링, Tabs 본체, Badge, Divider, Dialog.

- 그래서 같은 입력 계열인 TextField 와 TextArea 가 휴대폰에서 **반경 12.5 대 8, 테두리 1.25 대 1** 로 갈립니다(실측).

### 1-5. OS 글자 크기 설정과의 관계 — 곱해진다

**글자**는 테마 글자 크기(이미 1.25배)에 OS 글자 배율이 한 번 더 곱해집니다. Button md 라벨 실측:

| OS 글자 배율 | 데스크톱(1) | 휴대폰(1.25) |
|---|---|---|
| 1.0 | 14 | 17.5 |
| 1.3 | 18.2 | 22.75 |
| 2.0 | 28 | 35 |

- **컨트롤의 최소 높이는 OS 글자 배율을 따라가지 않습니다.** 큰 글자에서는 내용이 높이를 정합니다. 얼마나 따라 커지는지는 컨트롤마다 다릅니다.
  - Button md 실측: 휴대폰 OS 1.3 에서도 50, OS 2.0 에서 내용이 넘쳐 62. 데스크톱 OS 2.0 은 50.
  - TextField md 는 휴대폰 OS 2.0 에서 **70.5** 입니다. 같은 조건의 Button 은 62 에서 멈춥니다(#5224 실측 — 실제 `CoUIApp` 경로, iOS, Pretendard, 393×852 @3x. #5284 전후 같음). TextField 의 control-size 도 최소 높이라서, 큰 글자에서는 글자 줄과 패딩이 높이를 정합니다.
  - 그래서 같은 `md` 라도 큰 OS 글자에서는 TextField 가 Button 보다 커집니다(2.0 에서 8.5 차이). TextField 의 OS 1.3 값은 재지 않았습니다.
- 예외는 Tabs 하나입니다. 항목 높이에 OS 배율을 곱합니다(`flutter/navigation/tabs/tabs_style.dart:352-356`).
- `Text(...).then(...)` 경로는 OS 배율을 무시합니다(`flutter/text/text.dart:956` `textScaler ?? .noScaling`). 코드로만 확인했고 재지는 않았습니다.
- **Web 은 반응 범위가 다릅니다.** Web 의 사용자 글자 크기 설정은 글자뿐 아니라 rem 치수 전부를 키웁니다(§2-4). 이 비대칭은 휴대폰 배율과 별개로 이미 있습니다.

### 1-7. 언제 왜 들어왔나

- **CoUI 안 이력**: `AdaptiveScaling` · `defaultScaling` 은 히스토리 리셋 커밋 `9284012ef6`(2025-09-22, "초기 커밋 (히스토리 리셋)")에 이미 있었습니다. 그 전 이력은 저장소에 없습니다.
- **원출처**: `NOTICE` 에 따르면 `coui_flutter` 는 shadcn_flutter 에서 갈라져 나왔습니다. 업스트림 `packages/shadcn_flutter/lib/src/theme/theme.dart`(`gh api` 로 받음, 마지막 커밋 `8556eec13`)에 같은 상수와 같은 iOS · Android 분기가 있습니다. 근거는 "Default scaling for mobile layouts (1.25x)" 한 줄뿐입니다.
  - 업스트림 초기 이슈(2024-08-04, 닫힘) "모바일에서 요소가 너무 작다 — 사용자 지정 배율 또는 화면 크기 기반" 이 출발점으로 보입니다 **(추정 — 연결 근거 없음)**.
- **Button 에 밀도 배율을 넣은 변경**(`84c286a4b`, #4458, 2026-08-20): 높이 · 패딩 · 반경에 배율을 걸었습니다. 커밋이 적은 원칙은 "Web 에서 rem 인 것은 곱하고, px 인 것(테두리)은 곱하지 않는다" 입니다.
  - 이 근거는 글자 축과 밀도 축을 섞고 있습니다. 규칙은 "rem 은 밀도가 아니라 텍스트 축에 반응한다" 고 적습니다(`.claude/rules/core/design-tokens.md:93`). 휴대폰 브라우저의 rem 은 1.25배가 되지 않습니다(§2-3 실측).
  - 같은 주석(`button_style.dart:450-458`)은 "반경도 Web 에서 rem" 이라고 적지만 사실이 아닙니다. Web 반경은 대부분 px 입니다(§2-2 — rem 으로 내보내는 예외 세 곳 포함).
- **합성 표면의 패딩 · 반경에 배율을 넣은 변경**(`19d97a00b`, #4512, 2026-08-26): OutlinedContainer 를 합성하는 표면(Card 등)의 패딩 · 반경도 곱하게 했습니다. 그 전에는 테두리만 1.25배였습니다.
- **그래서 지금의 전면 1.25 는 약 5주 된 모습입니다.** 두 변경 모두 `coui_flutter-v0.131.0`(2026-08-31)에서 처음 출시됐습니다(`git tag --contains`). 그 전 휴대폰 Button 은 xs 28 · sm 40 · **md 44** · xl 60 이었습니다(`84c286a4b` 커밋 메시지의 실측 — 높이 토큰은 1배이고 글자만 커져 내용이 최소 높이를 넘은 값). 알려진 소비 앱은 모두 이 버전 이후에 고정돼 있습니다(§4-4).
- **1.25 라는 숫자를 적은 저장소 문서**는 세 파일입니다.
  - `docs/density-axis.md:37`(`3643e0f6c`, 2026-07-29) — "데스크톱 1 / 모바일 1.25 — 그 기존 배수는 밀도 축이 아니다, 플랫폼이 정하는 것" 이라고만 적고 이유는 없습니다. Web 에 짝이 없다는 말도 없습니다.
  - `.claude/rules/resolver/scaling-and-gap.md:242` — "iOS/Android = `.mobile` (`AdaptiveScaling(1.25)`, 3축 모두 1.25)". 역시 Web 이야기는 없습니다(§4-6).
  - 배포되는 스킬 문서 `packages/coui/skills/coui-theme/SKILL.md:127, 188` — 사용 예로만 나옵니다(§1-4).

### 2-5. 맞추려면 무엇이 가능한가

**방법 1 — 휴대폰에서 루트를 125% 로 (실측).** 예: `@media (hover:none) and (pointer:coarse){html{font-size:125%}}` 를 `ThemeConfig.cssVariables` 한 곳에서 내보냅니다.

루트를 20px 로 두고 잰 결과:

| | 루트 16 | 루트 20 | Flutter 휴대폰 |
|---|---|---|---|
| Button 높이 · 패딩 · 반경 | 40 · 16 · 8 | 50 · 20 · **8** | 50 · 20 · 10 |
| TextField 높이 (#5284 전 값) | 37.19 | 46 | 46.5 |
| Card | 241.69×144.39, 반경 16, 테두리 1 | 301.61×180, 반경 **16**, 테두리 **1** | 반경 20, 테두리 1.25 |
| `var(--shadow-md)` | `0 4 8 -2` | `0 5 10 -2.5` | 대부분 곱하지 않음 |

- **따라오는 것**: rem 항목 전부. Flutter 의 크기 축과 글자 축을 한 번에 재현합니다.
- **그대로라서 Flutter 와 맞는 것**: 터치 하한 24, 화면 너비 분기점(390 폭은 양쪽 다 `xs` 를 유지한 채 내용만 커짐), 실행 중 잰 위치.
- **어긋나서 따로 손봐야 하는 것**:
  1. **반경** — Web 은 대부분 px 고정입니다(rem 예외 세 곳, §2-2). 같은 미디어 쿼리에서 `--coui-radius-*` 19단계를 다시 적어야 합니다. 그래도 Flutter 쪽이 세 갈래라(§1-3) 어느 값에 맞출지 먼저 정해야 합니다.
  2. **테두리** — Web 1px. Flutter 는 8곳이 1, 43곳이 1.25, TextArea 가 1(§1-3). TextField 46 vs 46.5 의 차이가 바로 이것입니다: (37.19 − 2) × 1.25 + 2 = 45.99.
  3. **그림자** — Web 은 rem 이라 커지고, Flutter 는 대부분 곱하지 않습니다. `flutter/layout/window_panel/window_panel_style.dart:188-196` 은 "Web box-shadow 는 커지지 않는다" 를 근거로 들지만, 루트를 바꾸면 커지는 것을 쟀습니다.
  4. **포커스 링** — Web 안에서도 두 경로가 갈립니다. 테마 링 변수는 px, 범위 지정 링은 rem 입니다.
  5. **적용 범위** — rem 은 언제나 문서 루트 기준이라 `.coui-root` 밖 콘텐츠도 같이 커집니다(예: 문서 본문 `jaspr_content-0.5.3+1/lib/src/theme/_base.dart:4` 의 `1.rem`) **(코드로 추론 — 재지 않음)**. 다만 `CoUIWeb` 은 앱 전체를 `.coui-root` 하나로 감싸므로(`coui_web.dart:726-737`), 이 차이는 문서 사이트처럼 CoUI 가 아닌 콘텐츠가 섞인 페이지에서 주로 생깁니다. Flutter 쪽도 CoUI 위젯에만 닿는 것은 아닙니다 — `routes` 아래의 평범한 Flutter `Text` 가 1.25 에서 20 으로 그려집니다(G5 실측). `CoUIApp` 의 `DefaultTextStyle.merge`(`coui_app.dart:818`)와 `IconTheme.merge`(`:828`)를 물려받기 때문입니다.
- **퍼센트로 써야 합니다.** px 로 쓰면 사용자 글자 크기 설정이 무시됩니다(§2-4 표).

**방법 2 — `.coui-root` 에 CSS `zoom` (추정 — 재지 않음).**

- `CoUIWeb` 은 앱 전체를 `.coui-root` div 하나로 감쌉니다(`packages/coui_web/lib/src/coui_web.dart:726-737`). 오버레이 포털 자리(`OverlayHost`)도 그 안에 있습니다(`:604-608`).
- 그래서 zoom 은 CoUI 트리에만 걸리고, 떠 있는 패널도 같이 커질 것입니다. 방법 1 의 "CoUI 밖도 커짐" 문제가 없습니다.
- rem 뿐 아니라 px(반경 · 테두리 · 테마 링)도 같이 커집니다. 반경 19단계를 다시 적을 필요가 없습니다. 대신 Web 테두리가 모두 1.25 가 되어 Flutter 의 곱하지 않는 8곳 · TextArea 와 어긋납니다.
- 위험: 위치 엔진은 `getBoundingClientRect` 로 잰 좌표로 위치를 씁니다(`packages/coui_web/lib/src/overlay/positioning/overlay_positioner_web.dart:252`). zoom 아래에서 재는 좌표와 쓰는 좌표의 단위가 같은지는 확인하지 않았습니다. 고정 위치 요소 · container query · 드래그 좌표 · 브라우저별 차이도 같은 질문이 남습니다.
- 고르기 전에 반드시 재야 합니다.

**방법 3 — 변수만 다시 적기.** `--coui-space/size/font-size` 등만 바꿉니다. 변수를 거치지 않는 rem 리터럴 437줄과 Tailwind 기본 rem 클래스에는 닿지 않아 한 컴포넌트 안에서 일부만 커집니다. **권하지 않습니다.**

**기준을 무엇으로 볼까** — Flutter 는 "OS 가 iOS · Android 인가" 입니다.

| 기준 | 장점 | 어긋나는 곳 |
|---|---|---|
| `(hover:none) and (pointer:coarse)` | CSS 만으로 첫 화면 전에 적용, 서버 렌더링 안전. 저장소가 이미 `(hover: …)` 를 터치 판별 자리로 씀 | 트랙패드 iPad · 마우스 꽂은 안드로이드 · 터치스크린 윈도우 노트북 **(추정 — 표준 정의 기준, 실기기 미측정)** |
| Flutter 와 같은 OS 판정을 head 인라인 스크립트로 → html 속성 → CSS | Flutter 와 똑같음. 그리기 전에 속성을 다는 선례가 있음(`docs_site/lib/main.server.dart:59-66`) | 스크립트 의존 |
| `max-width` 화면 폭 | — | 기기 축과 폭 축을 섞습니다. Flutter 가 명시적으로 막는 형태입니다(`breakpoint.dart:50-55`). 태블릿이 빠집니다 |

**손잡이 자리**

- 테마 → CSS 변수 생성은 한 곳이 원칙입니다(`theme_config.dart:834`).
- Core 에 이미 `sizeScaling` · `radiusScaling` 필드가 있습니다(§2-1). Web 이 이것을 버리지 않고 읽게 하는 것이 `CoUIApp.scaling`(`coui_app.dart:699, 727`)의 짝이 됩니다.
- 이미 있는 `CoUIThemeController.setCustomTheme(radiusScaling:)`(`theme_controller_web.dart:482-500` → `css_variable_generator.dart:96-108`)은 쓸 수 없습니다.
  - 반경 변수 9개를 내보내고 그중 8개만 곱합니다(`--coui-radius-9999` 제외, `:107`). 반경 19단계 중 나머지는 덮지 않습니다.
  - 저장소 안에서 이 함수를 부르는 코드는 없습니다. 그러나 테마 이름 상수 30개의 `@Deprecated` 메시지가 "setCustomTheme 를 쓰라 (since 0.150)" 고 안내합니다(`theme_controller_web.dart:32` 등 30회, `theme_controller_stub.dart` 도 30회). 공식으로 안내된 이전 경로입니다.
  - 색 변수를 OKLch 로 덮어쓰는데(`css_variable_generator.dart:87`), CSS 는 RGB 세 숫자를 기대합니다(`core_to_css.dart:253-260`). 호출하면 색이 깨질 것으로 봅니다 **(추정, 미측정)**. 안내된 경로라서 이 위험은 "안 쓰는 코드" 보다 무겁습니다. 이 결정과 별개로 `[일반]` 후보입니다(D15).

## 3. 실측 표

텍스트 배율(OS · 브라우저 글자 크기)은 기본값 기준입니다.

- **Flutter 두 열**: 잰 값입니다(렌더 크기 또는 resolver 가 위젯에 넘긴 값). **(계산)** 표시만 예외입니다.
- **Web 휴대폰 열**: ● 표시는 배포 사이트에서 잰 값, 나머지는 Core 기본값에서 유도한 값입니다. Web 에 기기 배율이 없으므로 유도값 = 데스크톱 값입니다.
- **데스크톱 열**: Flutter 1배 값입니다. Web 데스크톱도 ● 항목은 같게 쟀습니다(Button 40 · TextField 37.19).

| 항목 | 데스크톱 (Flutter = Web) | Flutter 휴대폰 | Web 휴대폰 |
|---|---|---|---|
| Button 높이 xs / md / lg | 24 / 40 / 48 | 30 / **50** / 60 | 24 / 40● / 48 |
| Button md 좌우 패딩 | 16 | 20 | 16● |
| Button md 라벨 글자 | 14 | 17.5 | 14 |
| Button 반경 | 8 | 10 | 8● |

2. **C 는 기본 경로의 갈림길을 없앱니다.** B 는 Web 에 수단을 더하고, 그 전에 Flutter 안에서 갈린 반경 세 갈래 · 테두리 두 갈래의 값을 정해야 기본 경로에서 파리티에 도달합니다(D8). C 에서 그 값은 1 이 아닌 배율을 켠 앱 안의 일관성 문제로 줄어듭니다. 단 C 도 남긴 손잡이의 Web 짝(D11)은 만들어야 하므로, 두 안의 Web 작업 차이는 "기본값인가, 켜는 선택지인가" 입니다.
3. **C 의 저장소 안 비용은 실측으로 작습니다.** 기본값을 1 로 바꿔도 coui_flutter 테스트 66개 파일이 0개 실패했습니다. 다만 이것은 기본 배율을 지키는 테스트가 없다는 뜻이기도 하므로, 1배 · 1.25배 테스트를 같이 넣어야 합니다. 저장소 밖 비용은 소비 앱 네 곳의 한 줄씩입니다(위험 참고).
4. **검증 장치가 보는 것이 출하 기본값이 됩니다.** 캔버스 · 파리티 · 골든 · 문서 미리보기가 모두 1배입니다(§4-1~4-3). 1 이 아닌 배율 경로에는 결함 7건(G1~G6 · G9)과 정책 갈림 2건(G7 · G8)이 있는데, G1~G9 를 보는 장치가 없습니다. 1 이 아닌 배율을 넣는 Flutter 테스트는 16개 파일 있지만(§4-2) 그 자리를 보지 않고, 가드도 잡지 못합니다(§1-6).
5. **B 의 수단은 아직 재 볼 것이 남았습니다.** 루트 방식은 `.coui-root` 밖 콘텐츠도 키우지만, 순수 `CoUIWeb` 앱에서는 문제가 작습니다(코드로 추론). zoom 은 재지 않았고 위치 측정 위험이 남습니다 **(추정)**. 이 논거는 처음 판보다 약하고, zoom 을 재서 문제가 없으면 더 약해집니다.
6. **터치 편의는 실제 요구지만, 숨은 배수보다 크기 단계로 드러내는 편이 낫습니다.** 디자이너가 캔버스에서 고른 크기가 그대로 렌더되고, 밀도 축의 기록된 방향(이산 step 재지정)과도 맞습니다. 누르는 영역만 넓히는 E 는 D 와 함께 쓸 수 있습니다.
