# Design — Apple 구조를 CoUI Core 안에서

제약: **Apple 스타일을 따르되 Core 를 해치지 않는다.**

"해친다"의 정의는 내 취향이 아니라 `core/theme-axis-composition.md` 의
체크리스트다. 아래 셋을 그 항목들에 하나씩 대조했다.

---

## Apple 이 말하는 세 가지

| | HIG | 우리에게 필요한 것 |
|---|---|---|
| (a) | 재질 변형 둘 — `regular`(휘도 조정) / `clear`(매우 투명) | 재질이 하나뿐이다 |
| (b) | 기능층만 유리, 콘텐츠층은 표준 재질 | 층 개념이 없다 |
| (c) | 유리 위 버튼은 **thin**, 떠 있으면 **glass**, 툴바 안이면 **채움 없음** | 중첩 개념이 없다 |

---

## (a) 변형 둘 — 위험 없음

이미 있는 것과 같은 모양이다. `CoreSurfaceToken` 은 opacity · blur ·
saturation · sheen · refraction 을 든다. 여기에 **휘도 항** 하나가 는다.

측정으로 이미 도달했고(알파 0.65 / 밝기 0.25), HIG 가 그것을 `regular`
변형의 정의로 부른다. 새 seat 이 아니라 기존 토큰의 필드 하나다.

체크리스트: seat 1개 ✅ · 컴포넌트가 안 읽음 ✅ · `==` 포함 필요 ⚠️(작업 항목)
· 읽는 쪽 동반 필요 ⚠️(작업 항목) · 양 플랫폼 손잡이 ✅
(`backdrop-filter: brightness()` / `ColorFilter.matrix`).

---

## (b) 층 — **마커에 역할을 실어서** 표현한다

여기가 위험한 자리였다. "기능층/콘텐츠층"은 축이 컴포넌트를 분류해야 하는
것처럼 들리고, 그건 금지다:

> 축이 컴포넌트 목록을 들고 있지 않는다 — 목록은 새 컴포넌트가 추가될 때
> 조용히 낡는다.

하지만 같은 룰이 답도 준다:

> 표시가 컴포넌트 쪽에 있으면 표면을 새로 만드는 사람이 그 자리에서
> 결정한다.

그래서 **층은 축이 아니라 마커가 나른다.** 컴포넌트는 "나는 표면이다"가
아니라 **"나는 이런 종류의 표면이다"** 라고 말한다. 한 단어가 는다.

- `functional` — 콘텐츠 위에 떠 있는 것: 오버레이 · 네비 · 툴바 · 메뉴
- `content` — 콘텐츠층의 면: 카드 · 테이블 · 본문 패널

레시피는 **역할마다 재질을 진술**한다. 축은 여전히 목록이 없고, 새
컴포넌트는 자기 자리에서 자기 역할을 고른다.

체크리스트: 컴포넌트 목록 없음 ✅ · 컴포넌트가 축을 안 읽음 ✅ (자기 역할만
선언) · 새 컴포넌트가 조용히 빠지지 않음 ✅

### 이게 왜 "번들"이 아닌가

컴포넌트별 Theme 번들은 금지다. 이건 그게 아니다 — **역할은 2개이고
컴포넌트는 138개**다. 저작 대상이 컴포넌트 수만큼 늘지 않는다. 레시피가
2개의 재질을 진술하고, 138개가 둘 중 하나를 가리킨다.

---

## (c) 중첩 — 깊이는 ambient, 값은 축

"유리 위 버튼은 더 얇게"는 조상에 의존한다. 컴포넌트가 조상을 읽으면
그건 축을 간접적으로 읽는 것이다. 그래서 **깊이만 ambient 로 흐르고 그
깊이가 무엇으로 해석되는지는 축이 정한다.**

**Web — 공짜다. CSS 가 이미 한다.** 실측:

```
[data-coui-style="liquidGlass"] .coui-surface            → --probe: base
[data-coui-style="liquidGlass"] .coui-surface .coui-surface → --probe: nested
```

카드는 `base`, 그 안의 컨트롤은 `nested` 로 갈리고 재질이 자동으로
얇아진다. 컴포넌트 코드 변경 0.

**Flutter — 표면 프리미티브가 ambient 깊이를 publish 한다.** `SurfaceBlur`
가 이미 모든 표면의 통과 지점이므로, 자기 아래로 "너는 표면 안에 있다"를
흘리고 중첩된 `SurfaceBlur` 가 그것을 읽는다. `Theme`/`Directionality` 와
같은 기존 관용구다.

### 왜 얇아져야 하는가 — 이건 취향이 아니다

중첩 backdrop-filter 는 **쌓인다**. 브라우저에서 재봤다: 유리 카드 안의
유리 버튼은 카드 뒤 배경을 그대로 통과시킨다(불투명해지지 않는다). 두
재질이 곱해지므로 같은 값을 두 번 쓰면 안쪽이 과하게 탁해진다. Apple 이
thin 을 쓰라는 이유가 이것이고, 우리 실측이 같은 결론이다.

### 깊이에는 바닥이 있어야 한다

카드 안 다이얼로그 안 메뉴 = 깊이 3. 무한히 얇아지면 결국 사라진다.
얇아짐은 **바닥이 있는 단계**여야 한다 — 그 아래로는 더 얇아지지 않는다.
(배율이 아니라 이산 step 인 이유는 `theme-axis-composition.md` 의 "절대값
축과 배율 축" 절과 같다.)

---

## 그래서 Core 에 무엇이 느는가

새 seat 0개. 새 merge-chain 레벨 0개. 컴포넌트 Theme 번들 0개.

1. `CoreSurfaceToken` — 휘도 항 1개
2. `CoreSurfaceRecipe` — 재질을 **역할별로** 진술 (2개)
3. 중첩 깊이의 재질 — 바닥 있는 단계

컴포넌트 쪽: 이미 마커를 다는 자리에 **역할 한 단어**. 마커를 안 단
컴포넌트는 이번에 달면서 같이 고른다.

## 다른 프리셋은 한 픽셀도 안 바뀐다

default · neoBrutalism · claymorphism · neumorphism 은 재질을 진술하지
않는다 → 역할도 중첩도 해석될 것이 없다 → emit 0. 이건 주장이 아니라
파리티 스냅샷으로 확인한다.

## 범위에 대한 결론

HIG 의 "콘텐츠층에 유리 쓰지 마라"는 **금지가 아니라 두 재질로 표현된다** —
콘텐츠층은 `clear` 쪽(옅은 유리), 기능층은 `regular` 쪽(휘도 조정된 유리).
그래서 A+B 범위를 줄이지 않고도 Apple 의 위계가 산다: 카드는 여전히 유리고
다이얼로그·메뉴가 더 또렷하게 그 위에 뜬다.

Apple 의 "sparingly" 경고는 *한 층에 유리를 남발하지 마라*는 뜻이었고,
층을 나누면 그 경고가 구조로 지켜진다.
