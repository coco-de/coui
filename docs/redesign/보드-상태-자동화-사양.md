## 0. Claude Code에게

- 이 문서는 무엇을 자동화할지에 대한 합의다. 구현 방식(Action 구조, 스크립트 언어)은 저장소 관례에 맞춰 개발자가 정한다.
- 저장소 규칙(`.claude/rules/`)과 부딪히면 규칙을 따르고 이슈에 보고한다.
- `<...>`로 표시한 값은 저장소와 ZenHub 설정을 확인해 채우고, 확인할 수 없으면 묻는다.
- 자동화가 판단을 대신하면 안 된다. 조건이 애매하면 **옮기지 않고 그대로 둔다.**
- "확인 필요"로 표시한 ZenHub 동작은 아직 확인하지 못한 것이다. 시험 이슈로 확인하고 결과를 이 문서에 적는다.

## 1. 구조 — 보드 하나, 라벨로 나눔

| 항목 | 값 |
|---|---|
| 워크스페이스 | `CoUI` (2026-10-01 생성, 공유) — 디자이너와 개발팀이 함께 쓴다 |
| 연결 저장소 | `coco-de/coui` |
| 칸 | 미착수 · 조사중 · 결정완료 · 구현중 · 캔버스 확인 · Closed |
| 나누는 기준 | `redesign` 라벨 |
| 이전 개발팀 워크스페이스 | 목록에서 사라졌고 열리지 않는다(삭제로 보임, 개발팀 확인 필요) |

### 1-1. 칸

| 칸 | 뜻 | ZenHub에서 |
|---|---|---|
| 미착수 | 아직 손대지 않음 | 기본 `New Issues` 칸의 이름을 바꿨다. 새 이슈가 자동으로 들어온다 |
| 조사중 | 디자이너가 조사와 사본 리디자인을 진행 중 | 리디자인 이슈만 |
| 결정완료 | 스펙 6항목 확정, 열린 질문 없음. 개발자가 가져갈 수 있음 | 리디자인 이슈만 |
| 구현중 | 개발 진행 중 | 모든 이슈 |
| 캔버스 확인 | 반영 완료, 디자이너가 캔버스를 사본과 비교하는 중 | 리디자인 이슈만 |
| 완료 | 이슈가 닫힘 | 기본 `Closed` 칸. 이름 변경 메뉴가 없어 그대로 쓴다. 닫지 않은 이슈는 여기로 옮길 수 없다 |

### 1-2. 두 종류의 이슈

| | 리디자인 이슈 (`redesign` 라벨) | 일반 이슈 (라벨 없음) |
|---|---|---|
| 예 | 계열 리디자인 스펙 | 버그, CI, 문서, 도구 |
| 지나는 칸 | 미착수 → 조사중 → 결정완료 → 구현중 → 캔버스 확인 → Closed | 미착수 → 구현중 → Closed |
| 누가 닫나 | 디자이너 (캔버스 확인 후) | 개발팀 규칙대로 |
| 보는 법 | 저장한 보기 "리디자인"(`redesign` 라벨 필터) | 필터 없이 전체 보기 |

- 일반 이슈가 조사중 · 결정완료 · 캔버스 확인에 들어가지 않게 한다. 이 세 칸은 리디자인 전용이다.
- 스프린트와 포인트는 칸이 아니라 ZenHub의 스프린트 기능으로 관리한다. 리디자인 이슈도 개발팀이 스프린트에 넣을 수 있다.
- "리디자인" 보기는 `redesign` 라벨이 붙은 이슈가 하나라도 생긴 뒤에 저장할 수 있다. ZenHub 필터는 실제로 쓰이는 라벨만 목록에 보여준다.

## 2. 전환과 수단 (리디자인 이슈)

같은 보드를 쓰므로 개발자도 카드를 직접 옮긴다. ver.1의 역할 나눔으로 돌아간다.

| 전환 | 신호 | 지금(손으로) | 자동화 후 |
|---|---|---|---|
| 미착수 | 이슈 생성 | ZenHub 기본 | 그대로 |
| 조사중 | 디자이너 착수 | 디자이너 | Actions 2단계(담당 지정) |
| 결정완료 | 스펙 6항목 완료 | 디자이너 | Actions 3단계(본문 판정, 선택) |
| 구현중 | 개발 착수 / PR `Part of #` | 개발자 | Actions 1단계 |
| 캔버스 확인 | `### 캔버스 확인 요청` 댓글 | 개발자 | Actions 1단계 |
| 반려 후 구현중 | 디자이너의 `반려:` 댓글 | 디자이너 | Actions 1단계 |
| 완료 | 이슈 닫힘 | ZenHub 기본 | 그대로 |
| 다시 열림 → 구현중 | 이슈 다시 열림 | 개발자 | Actions 1단계 |

자동화 전에도 동작한다. 자동화는 손으로 옮기는 일을 줄일 뿐이고, 손으로 옮기는 것은 언제든 허용한다.

### 2-1. 단계별 범위

| 단계 | 전환 | 이유 |
|---|---|---|
| **1단계 (먼저)** | 구현중, 캔버스 확인, 반려 후 구현중, 다시 열림 | 신호가 분명하다 |
| 2단계 | 조사중 | 신호가 약하지만 틀려도 손해가 작다 |
| 3단계 (선택) | 결정완료 | 이슈 본문을 해석해야 한다 |

EmptyState 한 바퀴를 손으로 돌린 뒤 1단계부터 만든다. 1단계는 2026-10-01 실제 모드로 켰고, 2단계 · 3단계는 **EmptyState 한 바퀴를 손으로 돌린 뒤** 착수한다(디자이너 결정 2026-10-02).

## 3. 전환 규칙

공통 조건: 대상 이슈에 `redesign` 라벨이 있고, 워크스페이스 `CoUI`에서 그 이슈를 찾을 수 있어야 한다. 아니면 아무것도 하지 않는다. **일반 이슈는 이 자동화의 대상이 아니다.**

"허용 출발 칸"이 아닌 칸에서 신호가 오면 옮기지 않는다.

### 3-1. 구현중 (1단계)

| 항목 | 내용 |
|---|---|
| 신호 | PR이 열리거나(`opened`, `reopened`) 본문이 수정됨(`edited`) |
| 조건 | PR 본문에 `Part of #<번호>`가 있음. 여러 개면 각각 처리 |
| 허용 출발 칸 | 결정완료 |
| 도착 칸 | 구현중 |
| 이미 구현중, 캔버스 확인 | 아무것도 하지 않음 |
| 미착수, 조사중일 때 | 옮기지 않고, 이슈에 경고 댓글 1회: "결정완료 전에 PR이 열렸습니다(#PR). 스펙 확정 여부를 확인해 주세요." |

- 번호 패턴은 `Part of #123` 형태만 인정한다(대소문자 무시). `Closes`, `Fixes` 등은 읽지 않는다.
- 경고 댓글은 같은 PR에 대해 한 번만 단다(숨은 표식 예: `<!-- board-bot:early-pr:#PR -->`).
- **ZenHub의 "PR을 이슈에 연결" 기능은 쓰지 않는다.** 연결하면 이슈가 PR과 같은 칸으로 따라 움직이고, 머지 때 이슈가 닫히는지 확인되지 않았다. 연결은 `Part of #` 하나로만 한다.

### 3-2. 캔버스 확인 (1단계)

| 항목 | 내용 |
|---|---|
| 신호 | 이슈에 댓글이 달림(`issue_comment` `created`) |
| 조건 | 댓글 본문 첫 줄이 `### 캔버스 확인 요청` (앞뒤 공백 무시) |
| 허용 출발 칸 | 구현중 |
| 도착 칸 | 캔버스 확인 |

이 제목은 `design-collaboration.md` 7-3 댓글 형식의 첫 줄이다. 형식을 바꾸면 이 조건도 같이 바꾼다. 작성자는 제한하지 않는다.

### 3-3. 반려 후 구현중 (1단계)

| 항목 | 내용 |
|---|---|
| 신호 | 이슈에 댓글이 달림 |
| 조건 | 작성자가 디자이너 목록에 있음, 댓글 본문이 `반려:`로 시작 (정규식 `^\s*반려\s*:`) |
| 허용 출발 칸 | 캔버스 확인 |
| 도착 칸 | 구현중 |

일반 댓글(질문, 답변)은 칸을 바꾸지 않는다.

### 3-4. 다시 열림 → 구현중 (1단계)

| 항목 | 내용 |
|---|---|
| 신호 | 이슈가 다시 열림(`issues` `reopened`) |
| 허용 출발 칸 | 캔버스 확인 (2026-10-01 디자이너 결정 — 처음 사양은 "제한 없음") |
| 도착 칸 | 구현중 |

다시 열린 이슈가 ZenHub에서 어느 칸으로 가는지는 확인 필요. ZenHub가 스스로 알맞게 되돌리면 이 규칙은 지운다.

> **확인 결과 (2026-10-01)**: ZenHub 는 다시 열린 이슈를 **닫히기 직전에 있던 칸**으로 돌려놓는다(미착수에서 닫은 시험 이슈가 다시 열리자 미착수로 돌아감, 6초 동안 관찰). 닫힌 동안에도 그 칸을 기억한다. 캔버스 확인에서 닫힌 리디자인 이슈는 캔버스 확인으로 돌아가므로 **이 규칙은 지우지 않는다.**
>
> **허용 출발 칸을 캔버스 확인으로 좁힌 이유 (디자이너 결정 2026-10-01)**: ZenHub 보드에서 닫힌 이슈를 Closed 칸 밖으로 끌어내도 GitHub 이슈가 다시 열리고 `reopened` 가 온다(시험으로 확인 — 조사중으로 끌어낸 이슈에 처음 규칙은 `조사중 → 구현중` 을 판정했다). 그 이슈는 사람이 고른 칸에 있으므로 덮지 않는다. GitHub 에서 다시 연 리디자인 이슈는 캔버스 확인으로 돌아오므로 이 규칙이 그대로 받는다. 남는 예외는 하나 — 보드에서 굳이 캔버스 확인 칸으로 끌어내면 구현중으로 옮겨진다.

### 3-5. 조사중 (2단계)

| 항목 | 내용 |
|---|---|
| 신호 | 이슈에 담당자가 지정됨(`issues` `assigned`) |
| 조건 | 지정된 사람이 디자이너 목록에 있음 |
| 허용 출발 칸 | 미착수 |
| 도착 칸 | 조사중 |

### 3-6. 결정완료 (3단계, 선택)

| 항목 | 내용 |
|---|---|
| 신호 | 이슈 본문이 수정됨, 이슈 생성 |
| 조건 | 아래 "본문 판정"을 모두 통과 |
| 허용 출발 칸 | 미착수, 조사중 |
| 도착 칸 | 결정완료 |
| 결정완료 뒤 6번이 다시 "없음"이 아니게 바뀜 | 옮기지 않고 경고 댓글 1회: "결정완료 뒤 열린 질문이 추가됐습니다. 개발자 확인이 필요합니다." |

본문 판정 (이슈 폼 `.github/ISSUE_TEMPLATE/redesign.yml`이 만든 `### <칸 제목>` 구획):

1. `1. 무엇이 바뀌나`에 템플릿 기본 표 외에 값이 있는 행이 1개 이상
2. `2. 왜`가 비어 있지 않음(`_No response_` 아님)
3. `3. 구조 변경 여부`가 `있음`이면 `3-1`도 비어 있지 않음
4. `4. Figma 링크`에 `figma.com` 링크가 1개 이상
5. `5. 검수 기준`에 빈 체크박스가 아닌 항목이 1개 이상
6. `6. 열린 질문`이 정확히 `없음`

판정이 애매하면 옮기지 않는다.

## 4. 전환 요약 (리디자인 이슈)

```
미착수 ──(디자이너)──> 조사중 ──(디자이너)──> 결정완료
결정완료 ──(개발자 착수 / PR에 Part of #)──> 구현중
구현중 ──(### 캔버스 확인 요청 댓글)──> 캔버스 확인
캔버스 확인 ──(디자이너 "반려:" 댓글)──> 구현중
캔버스 확인 ──(디자이너가 이슈 닫음, ZenHub 기본)──> Closed
Closed ──(이슈 다시 열림)──> 구현중
```

## 6. 구현 참고

### 6-1. 인증

- ZenHub GraphQL API(`https://api.zenhub.com/public/graphql`, POST만)는 **개인 API 키**로 인증한다(대시보드 API 메뉴, 계정당 최대 5개, `Authorization: Bearer <키>`).
- 키는 특정 사람의 ZenHub 계정에 묶인다. 그 사람이 빠지거나 키를 지우면 멈춘다. 주인과 교체 담당을 5장에 적는다.
- 경고 댓글은 GitHub 쪽이라 기본 `GITHUB_TOKEN`(`issues: write`)으로 충분하다.
- GitHub 조직 Projects 권한은 필요 없다.
- 키가 무효이면 워크플로가 실패로 끝나야 한다.

### 6-2. 처리 흐름

1. 이벤트에서 대상 이슈 번호를 얻는다(PR은 본문의 `Part of #`에서).
2. `redesign` 라벨이 있는지 확인한다(GitHub API).
3. 워크스페이스 `CoUI`에서 그 이슈와 현재 칸을 조회한다. 이슈 ID · 칸 목록 쿼리는 ZenHub GraphQL Explorer에서 확인해 쓴다. 못 찾으면 종료.
4. 현재 칸이 허용 출발 칸인지 확인한다. 아니면 종료(경고가 정의된 경우만 경고).
5. `moveIssue` 뮤테이션(이슈 ID, 칸 ID, 위치)으로 옮긴다.
6. 실행 로그에 "이슈 #N: A → B (신호)"를 한 줄 남긴다.

### 6-3. 안전장치

- 같은 이슈의 실행은 `concurrency` 그룹(`board-<이슈번호>`)으로 하나씩.
- 포크 PR은 `pull_request_target`으로 본문만 읽고 코드를 체크아웃하지 않는다. 내부 브랜치만 쓰면 `pull_request`로 충분하다.
- 봇이 단 댓글은 신호로 쓰지 않는다.
- 3-4를 빼면 칸을 뒤로 옮기지 않는다. 닫히지 않은 이슈를 `Closed`로 옮기지 않는다.
- `DRY_RUN=true`면 로그만 남긴다. 처음 배포할 때 켠다.

## 8. 완료 기준

시험: 2026-10-01, 시험 이슈 #5197 ~ #5202 · 시험 PR #5203(base 를 시험 브랜치로 둬 CI 를 돌리지 않음). 워크플로는 시험 모드(`REDESIGN_BOARD_DRY_RUN` 없음)로 돌았다. 시험 모드에서는 실제로 옮기지 않으므로, 이동과 경고 1회는 같은 스크립트를 시험 이슈에만 실제 모드로 로컬 실행해 따로 확인했다. 시험 이슈 · PR · 브랜치는 끝나고 닫거나 지웠다.

### 운영 시작 전

- [x] `New Issues` 이름 변경 가능(미착수로 바꿈), `Closed`는 변경 메뉴 없음
- [ ] "리디자인" 보기에서 `redesign` 라벨 이슈만 보인다 — 디자이너가 ZenHub 화면에서 확인할 항목(API 로 볼 수 없음)
- [x] 이슈를 닫으면 Closed로 간다 — 닫은 시험 이슈가 ZenHub 의 닫힌 이슈 목록에 들어감. 새 이슈는 미착수로 자동으로 들어옴(시험 이슈 6개)
- [x] 확인 필요: 다시 열린 이슈의 기본 칸 — **닫히기 직전 칸으로 돌아간다**(3-4 참고)
- [ ] 확인 필요: ZenHub PR 연결 시 머지에서 이슈가 닫히는지 — 시험하지 않음. 이 기능은 쓰지 않기로 했고(3-1), 확인하려면 PR 을 실제로 머지해야 한다

### 1단계

| 기준 | 결과 | 근거 |
|---|---|---|
| 결정완료 이슈에 `Part of #N` PR을 열면 구현중이 된다 | ✅ | 워크플로: `#5197: 결정완료 → 구현중 (PR #5203) [dry-run]`(PR 열림 · 본문 수정 둘 다). 실제 모드 로컬 실행에서 실제로 구현중이 됨 |
| 조사중 이슈에 `Part of #N` PR을 열면 옮겨지지 않고 경고 댓글이 한 번 달린다 | ✅ | 워크플로: `#5198: 경고 댓글 — PR #5203 이 조사중 에서 열림 [dry-run]`. 실제 모드로 두 번 돌리자 경고는 한 개, 두 번째는 "경고는 이미 달림" |
| 구현중 이슈에 `### 캔버스 확인 요청` 댓글을 달면 캔버스 확인이 된다 | ✅ | `#5199: 구현중 → 캔버스 확인 (캔버스 확인 요청 댓글) [dry-run]` |
| 캔버스 확인 이슈에 디자이너가 `반려: ...` 댓글을 달면 구현중이 된다 | ✅ | `#5200: 캔버스 확인 → 구현중 (반려 댓글) [dry-run]`. `반려 아님 — …` 댓글은 "신호가 아닌 댓글" 로 건너뜀 |
| 디자이너가 아닌 사람이 달면 아무 일도 없다 | ⚠️ 단위 테스트만 | 이 머신의 GitHub 계정이 디자이너 계정 하나뿐이라 실제로는 못 함. `commentSignal` 테스트가 고정한다 |
| 닫힌 이슈를 다시 열면 구현중이 된다 | ✅ (뒤에 범위를 좁힘) | 시험 때: `#5201: 미착수 → 구현중 (이슈 다시 열림) [dry-run]`. 이후 3-4 를 캔버스 확인에서만으로 좁혔다(3-4 참고) |
| `redesign` 라벨이 없는 이슈에는 아무 일도 없다 | ✅ | 라벨 없는 #5202 의 `### 캔버스 확인 요청` 댓글 → 잡이 건너뛰어짐(skipped) |
| API 키가 무효이면 실패로 표시된다 | ✅ 로컬 | 무효 키 → `ZenHub API HTTP 401`, exit 1. 빈 키 → exit 1. 저장소 시크릿을 바꿔야 해서 Actions 에서는 시험하지 않음 |
| `DRY_RUN=true`에서는 로그만 남는다 | ✅ | 시험 뒤 #5197 ~ #5200 의 칸이 시작 칸 그대로, 봇 댓글 0 개 |

함께 확인한 것:
- PR 제목만 바꾼 `edited` → "본문이 바뀌지 않은 edited" 로 건너뜀.
- 저장소 시크릿 키의 소유자는 `designcocode` 다(실행 로그).

### 실제 모드

- 2026-10-01 디자이너 결정으로 실제 모드로 바꿨다(`REDESIGN_BOARD_DRY_RUN=false`). 다시 시험 모드로 돌리려면 그 변수를 지우거나 `true` 로 둔다.
- 5장의 키 소유자 · 교체 담당은 디자이너(`designcocode`)로 정했다(2026-10-01).

## 9. 구현 메모 — 사양이 정하지 않아 구현에서 정한 것 (1단계, 2026-10-01)

| 항목 | 정한 것 | 이유 |
|---|---|---|
| `concurrency` | 잡 수준, 그룹 `redesign-board-<이슈 번호>`(PR 이벤트는 PR 번호), `queue: max` | 기본 큐(`single`)는 대기 중이던 실행을 다음 실행이 취소해, 연달아 온 신호(캔버스 확인 요청 → 반려) 하나가 흔적 없이 사라진다. PR 이벤트는 한 번에 여러 이슈를 가리킬 수 있어 PR 번호로 묶는다 |
| PR `edited` | 본문이 실제로 바뀐 경우만 신호(제목 · base 만 바뀐 edited 는 무시) | 3-1 의 신호는 "본문이 수정됨" 이다 |
| `Part of #N` 형태 | 대소문자 무시, `Part` · `of` · `#` 사이는 같은 줄의 공백만 | 줄을 넘긴 `Part\nof #N` 은 신호로 보지 않는다 |
| 대상 이슈 | `redesign` 라벨이 있고 **열린** 이슈. 없는 번호(404)는 건너뛰고 실패로 만들지 않는다 | 리디자인과 무관한 `Part of` PR 에 빨간 체크가 붙지 않게 |
| ZenHub 에서 못 찾음 | 이슈가 없거나 열렸는데 칸이 없으면 옮기지 않는다. 다시 열림은 30초까지 기다려 본다 | 3장 공통 조건 · 6-2 "못 찾으면 종료" |
| ZenHub 오류 | "이슈 없음"(`NOT_FOUND`)만 찾지 못함으로 본다. 그 밖의 오류(장애 · 레이트 리밋)와 무효 키는 실패로 끝난다 | 실패가 보여야 다시 돌릴 계기가 생긴다 |
| 칸 안 위치 | 옮긴 카드는 도착 칸의 맨 위(`position: 0`) | 새로 도착한 것이 눈에 띄도록. 칸 안 순서를 지키려면 이 값을 바꾼다 |
| 포크 PR | 건너뛴다 | 포크 PR 실행은 시크릿을 받지 못한다(6-3 의 `pull_request` 선택) |
| `DRY_RUN` | 저장소 변수 `REDESIGN_BOARD_DRY_RUN` 이 정확히 `false` 일 때만 실제로 옮긴다 | 처음 배포는 시험 모드(6-3) |
| 키 소유자 | 실행 로그("ZenHub 칸 옮기기" 단계) 첫 줄에 GitHub 아이디를 찍는다 | 5장의 키 소유자를 확인하는 근거 |

**알려진 한계였던 것**: ZenHub 보드에서 Closed 밖으로 끌어 다시 연 이슈를 3-4 가 구현중으로 덮던 문제는 3-4 의 허용 출발 칸을 캔버스 확인으로 좁혀 해결했다(디자이너 결정 2026-10-01). 캔버스 확인 칸으로 끌어낸 경우만 여전히 구현중으로 옮겨진다.
