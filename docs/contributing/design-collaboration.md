# 디자이너 · 개발자 협업 — 리디자인을 받아 캔버스까지

[가이드 목차](README.md) · 관련: [Figma 플러그인 작업](figma.md)

작성 코코드(디자이너) · 대상 개발자, Claude Code

CoUI 리디자인을 디자이너와 개발자가 나눠 진행하는 방식이다. **디자인 결정은
디자이너만 하고, 개발자는 디자인 판단 없이 반영하고 기계적으로 확인한다.**
디자이너는 코드를 만지지 않고, 개발자는 캔버스를 고치지 않는다.

팀의 원문은 [디자인·코드 협업 규칙](https://github.com/coco-de/skills/blob/main/internal/coui/rules/process/design-code-handoff.md)에 있다.
이 문서와 규칙이 다르면 규칙을 따르고, 어긋난 지점을 리디자인 이슈에 적는다.

---

## 1. 원칙

| 규칙 | 뜻 |
|---|---|
| 정답은 코드 계약 | 캔버스는 코드에서 다시 그려진다. Figma 에서만 고친 값은 코드로 돌아가지 않는다. |
| 결정은 디자이너 | 스펙에 없는 결정이 필요하면 개발자는 추측하지 않고 멈추고 묻는다. |
| 기록은 이슈 하나 | 스펙, 질문, 답, 캔버스 확인 결과가 모두 리디자인 이슈에 남는다. 메신저로 물어도 답은 이슈로 옮긴다. |
| 검수는 증거로 | 기계가 볼 수 있는 것은 개발자가 기계로 확인해 이슈에 붙이고, 디자이너는 기계가 못 보는 것만 본다. |

### 1-1. 파이프라인은 한 방향이다

```text
코드 계약 ──> 토큰 내보내기 ──> Import   ──> Figma 변수 · 텍스트 스타일
코드 계약 ──> components.json ──> 컴포넌트 반영(Generate) ──> Figma 컴포넌트 세트

Figma 에서 고친 값 ──X──> 코드   (역방향 없음)
```

- 컴포넌트 페이지의 세트는 코드에서 다시 그려지는 결과물이다. 세트를 직접 고치면
  다음 반영이 코드대로 다시 그린다. 플러그인이 손 편집을 감지하면 세트 옆에
  `(리디자인 · 시각)` 사본을 남기지만, 모든 편집을 잡는다는 보장은 없다. 그래서
  원본 세트는 고치지 않는다(3장).
- 플러그인의 **리디자인 대조(`⇄`)** 는 디자이너 사본과 새로 그린 세트를 변형마다
  비교한다.
  - 요약하면 **보이는 기본 값**(박스의 색 · 크기 · 보더, 글자, 아이콘, 오토레이아웃
    패딩 · 간격)과 **한쪽에만 있는 변형**은 잡고, 그림자 같은 효과 · 정렬 ·
    그라디언트 · 불린 같은 **컴포넌트 속성**은 못 잡는다. 정확한 목록은
    [팀 규칙](https://github.com/coco-de/skills/blob/main/internal/coui/rules/process/design-code-handoff.md)의 "손 편집 대조가 하는
    것과 하지 않는 것" 이 정본이다.
  - 못 잡는 항목이 바뀌는 리디자인은 스펙 5번(검수 기준)에 적어 사람이 확인한다.
  - 글자 **내용**도 비교하므로, 사본의 예시 문구는 원본 세트의 것을 그대로 둔다.
- 순서는 항상 **스펙 확정 → 코드 계약 수정 → 머지 → 컴포넌트 반영** 이다.

### 1-2. 용어

| 말 | 뜻 |
|---|---|
| 코드 계약 | 컴포넌트의 기본값 · 축을 정한 코드. 캔버스는 여기서 그려진다 |
| 컴포넌트 반영(Generate) | 플러그인이 코드대로 세트를 다시 그리는 버튼 |
| 번들 | 플러그인이 실행하는 코드 파일. "main 의 어느 커밋으로 그렸나" 를 커밋 번호(`abc1234`)로 적는다 |
| 낡은 세트 | 아직 옛 코드로 그려져 있는 세트. 0 이면 캔버스가 최신이다 |
| `⇄` 대조 | 디자이너 사본과 새로 그린 세트의 값 비교 |
| `(리디자인 · 시각)` | 세트를 직접 고친 흔적을 플러그인이 보존한 프레임 |
| `(이전 · 시각)` | 플러그인이 남긴 직전 생성본 백업. 대조에 쓰지 않으며 지워도 된다 |
| 이슈 | 할 일 한 건의 기록. 본문(스펙) · 댓글 · 라벨 · 담당자를 갖고 열림/닫힘 두 상태만 있다. 이 협업에서는 리디자인 한 계열 = 이슈 하나 |
| 보드 | ZenHub 워크스페이스 `CoUI` 하나. 디자이너와 개발팀이 같이 쓰고, 리디자인 이슈는 `redesign` 라벨로 가른다. 이슈를 칸별로 늘어놓고 진행을 보는 화면이라 카드를 옮겨도 이슈 내용은 그대로다 |
| 라벨 | 이슈에 붙이는 분류 표(`redesign`, `question` 등) |
| PR | 코드 변경 묶음. 머지하면 main 에 들어간다 |
| Development 연결 | 이슈 옆 칸에서 브랜치 · PR 을 이슈에 묶는 기능. 머지 때 이슈를 닫으므로 리디자인 이슈에는 쓰지 않는다 |

## 2. 역할

보이는 것은 디자이너가, 코드로 옮기는 방식은 개발자가 정한다.

| 영역 | 디자이너가 정함 | 개발자가 정함 |
|---|---|---|
| 값 | 크기, 간격, radius, 색 토큰 선택, 상태별 값 | 토큰 참조로 쓸지 계산식으로 쓸지 |
| 구조 | 축(Size, State 등), 변형 구성, 컴포넌트 속성, 의미 있는 이름 | 파일과 클래스 구조, API 형태 |
| 변경 | 무엇을 없애고 새로 만들지 | 디프리케이션 절차(두 마이너), 마이그레이션 |
| 품질 | 시각 위계, 대비 기준 | 성능, 플랫폼 호환, 테스트 |
| 캔버스 | 사본 작업, 최종 확인, 이슈 닫기 | 컴포넌트 반영(한 사람, main 번들), 대조 결과 보고 |

애매한 대표 경우는 스펙 값이 기존 토큰 스케일에 없을 때다. 개발자는 가까운
토큰을 임의로 고르지 않고 "스케일에 추가" 또는 "기존 값으로 맞춤" 같은
선택지를 이슈에 제안한다. 결정은 디자이너가 한다.

## 3. Figma 작업 공간 — 원본 옆 사본

디자이너는 컴포넌트 페이지의 원본 세트를 직접 고치지 않고, **같은 페이지의
사본**에서 리디자인한다.

| 항목 | 규칙 |
|---|---|
| 위치 | 원본 세트와 **같은 페이지의 최상위**, 원본 옆. 그룹 · 섹션으로 감싸지 않는다 |
| 이름 | `<세트 이름>(리디자인)` — 예: `EmptyState(리디자인)`. 괄호 앞 공백 한 칸은 있어도 된다 |
| 형태 | 같은 파일 안에서 원본 세트를 **복제(⌘D)한 컴포넌트 세트**. 멤버 이름(변형 이름)은 그대로 둔다 — 대조가 그 이름으로 변형끼리 짝을 짓는다 |
| 개수 | 세트당 하나 |
| 이슈 연결 | 스펙 4번 칸에 세트마다 사본 노드 링크를 적는다 |
| 삭제 | 캔버스 확인을 통과시킨 뒤 디자이너가 지운다. 반려되면 수정이 끝날 때까지 남긴다 |

**이름 · 위치 · 형태가 정확해야 하는 이유**: 플러그인은 대조할 사본을 **원본과
같은 페이지의 최상위**에서, 이름이 **원본 세트 이름 바로 뒤에 `(리디자인`** 으로
이어지는 것만 찾는다(사이에 공백 한 칸은 있어도 된다). 다른 페이지에 두거나, 그룹 · 섹션으로 감싸거나, 이름 앞에
무언가 붙이면(`_Preview / EmptyState`) 대조가 돌지 않고 로그에
`리디자인 사본 없음` 만 남는다. 그러면 개발자가 디자인 판단 없이 "반영됐다" 를
확인할 수단이 사라진다. `CheckboxGroup(리디자인)` 은 `Checkbox` 뒤가 `Group`
이라 `Checkbox` 의 사본으로 읽히지 않는다.

같은 이름 규칙에 걸리는 후보가 여럿이면 이름 정렬의 마지막이 기준이다. 다만 사본이 컴포넌트
세트이고 옆에 `EmptyState(리디자인) / 비교` 같은 일반 프레임이 함께 있으면, 플러그인은
컴포넌트 세트를 기준으로 삼고 비교용 프레임은 건너뛴다(이름을 바꿀 필요 없다).

**하지 말 것**

- 복사 · 붙여넣기로 만든 사본 — 같은 파일 안에서 세트를 복사 · 붙여넣기하면 원본의
  인스턴스를 담은 프레임이 되고, 이것은 원본을 비추는 거울이라 대조를 건너뛴다(로그
  `대조 건너뜀`). 그 인스턴스를 detach 해도 멤버 이름이 변형 이름이 아니라 세트
  이름이라 변형끼리 짝을 짓지 못한다. 사본은 ⌘D 로만 만든다.
- 다른 파일에서 붙여 넣은 사본 — 텍스트 스타일 연결이 끊겨 자간 · 크기 차이가
  거짓으로 나온다.
- 사본의 변형을 하나씩 페이지 최상위로 끌어내 두기 — 컴포넌트 반영이 그것을
  원본 세트의 멤버로 가져갈 수 있다.
- 플러그인이 만든 `(이전 · 시각)` 프레임을 복제해 사본으로 쓰기 — 플러그인 표식이
  따라와 대조에서 빠지고, 다음 반영 때 지워질 수 있다.
- 사본을 둘 이상 두기 — 대조는 이름 순으로 하나만 기준으로 삼아, 디자이너가
  최신이라 여긴 사본과 실제로 대조된 사본이 갈릴 수 있다. 결정 전의 탐색은 세트
  이름 바로 뒤에 `(리디자인` 이 오지 않는 다른 이름(예: `EmptyState 탐색`)으로 둔다.

**변형 이름이 바뀐 세트의 사본.** 컴포넌트 반영은 변형 개명을 원본 세트에만 적용하고
사본은 건드리지 않는다. 그래서 개명 전에 복제한 사본은 옛 변형 이름을 그대로 들고
있다. `⇄` 는 사본의 변형 이름이 새로 그린 세트에 이미 있으면 그대로 짝짓고(새 이름을
쓴 사본), 없으면 개명표(`VARIANT_RENAMES`)로 옛 이름을 새 이름으로 읽어 짝을 짓는다
(옛 이름을 둔 사본). 표로 맺은 짝은 `↻ 개명표로 짝지음` 줄에 옛 이름 → 새 이름으로
적고, 그 세트는 요약 줄의 `개명표로 짝지음` 에 센다. 표가 가리키는 새 이름을 사본의
다른 변형이 이미 쓰고 있으면 옮기지 않고 `⚠ 개명 목적지를 …` 줄로 알리니, 그 줄이
나오면 사본에서 같은 포즈의 옛 이름 변형과 새 이름 변형 중 하나를 정리한다.

**그 밖에**

- 컴포넌트 반영은 사본을 덮어쓰거나 지우지 않고, 고아 노드로 신고하지도 않는다.
- 플러그인이 손 편집을 감지해 남긴 `(리디자인 · 시각)` 사본도 자동으로 지우지
  않는다. 확인이 끝나면 디자이너가 지운다.
- 사본(컴포넌트 세트)은 라이브러리를 게시할 때 함께 나갈 수 있다. 사본이 남아
  있는 동안 게시한다면 게시 목록에서 사본을 확인한다.
- 변형 축이 없는 단일 컴포넌트는 ⌘D 복제본도 세트가 아니라 컴포넌트라 대조되지
  않는다. 이 경우는 1번 표와 검수 기준으로 사람이 확인한다.
- Figma 브랜치는 쓰지 않는다. 플러그인은 브랜치에서도 돌지만, 개발자는 대조와
  컴포넌트 반영을 정본 파일에서만 돌리므로 브랜치에 둔 사본은 대조되지 않는다.

## 4. 작업 흐름

핸드오프 단위는 컴포넌트 계열이다(예: Form 계열 = TextField, TextArea,
FormLabel, FormField, Fieldset). 서로 영향을 주는 컴포넌트를 한 이슈로 묶는다.

**이슈는 계열당 하나, PR 은 계열 안의 컴포넌트 단위로 여러 개**다. 각 PR 은 그
컴포넌트의 Core · Flutter · Web · 문서 · 재촬영 이미지를 함께 담는다 — 한
플랫폼만 바꾼 PR 은 규칙 위반이다. 렌더를 바꾸면 Web · Flutter 재촬영 이미지를
baseline 워크플로(`.github/workflows/parity-baseline.yml` 등)를 기능 브랜치로 실행해
같은 PR 에 넣는다. **이 누락은 CI 가 대부분 막지 못한다** — Web · Flutter 파리티
비교는 아직 참고용이라 실패해도 머지를 막지 않고, Flutter 골든 · 프리셋 스냅샷이
덮는 일부 컴포넌트에서만 CI 가 빨개진다. 그래서 PR 템플릿의 재촬영 항목을 개발자가
직접 챙긴다.

### 4-1. 단계와 담당

| 단계 | 담당 | 하는 일 | 보드 상태 |
|---|---|---|---|
| 1. 계열 선택 | 디자이너 | 리디자인 스펙 템플릿으로 이슈 생성. 조사 전에 만들어도 된다 | 미착수 |
| 2. 조사와 결정 | 디자이너 | 실측, 다른 시스템 조사, 원본 옆 사본에서 리디자인 | 조사중 |
| 3. 스펙 확정 | 디자이너 | 6항목을 채우고(열린 질문에 "없음") 카드를 결정완료로 옮긴다 | 결정완료 |
| 4. 착수 전 확인 | 개발자 | 아래 "착수 전 확인" | 결정완료 |
| 5. 구현 | 개발자 | 코드 계약 수정 → PR(`Part of #이슈`) → CI 초록 → 머지 | 구현중 |
| 6. 질문(필요 시) | 개발자 → 디자이너 | 이슈 댓글로 질문(`question` 라벨), 디자이너가 댓글로 답하고 본문 갱신 | 구현중 |
| 7. 캔버스 반영 | 개발자 | 이슈에 필요한 PR 이 **전부 머지된 뒤 한 번**, main 번들로 컴포넌트 반영 → 대조 확인 → 이슈에 "캔버스 확인 요청" 댓글 | 캔버스 확인 |
| 8. 캔버스 확인 | 디자이너 | 캔버스를 사본과 비교. `⇄` 가 못 보는 것(속성 · 효과 · 시각 위계)을 본다 | 캔버스 확인 |
| 9a. 통과 | 디자이너 | 사본을 지우고, 라이브러리를 게시한 뒤 이슈를 닫는다(아래 "게시") | Closed |
| 9b. 반려 | 디자이너 | 이슈 댓글을 `반려:` 로 시작해 구체적으로 지적 | 구현중 |
| 10. 후속 | 개발자 | 같은 이슈로 후속 PR → 7단계부터 다시 | 구현중 |

**착수 전 확인** — 구현중으로 옮기기 전에 개발자가 본다.

- 스펙 3번의 구조 변경마다, 캔버스의 축 · 속성만 바뀌는지 코드의 공개 API(계약
  필드 · enum 값)도 없어지는지 가른다. 공개 API 가 없어지면 디프리케이션 창(두
  마이너)이 붙는다.
- 그 필드를 다루는 규칙이 있는지 확인한다(`grep -rn <필드명> .claude/rules`).
  규칙과 부딪히면 구현 전에 이슈에 묻는다.
- 1번 표와 사본이 같은지 본다. 다르면 묻는다.
- 변형을 개명하거나 은퇴시키는 구조 변경은 **구 변형 → 신 변형 매핑표**와 **옮길 소비처
  인스턴스 목록**을 PR 본문에 적는다(PR 템플릿의 같은 이름 칸). 매핑표는 개명표
  (`VARIANT_RENAMES`)의 행과 같은 내용이다. 소비처 목록은 구 변형을 쓰는 인스턴스가
  있는 파일 · 노드 링크이고, 게시 전에 살아남을 변형으로 옮긴다(4-3a).

**7단계에서 `⇄` 차이가 남으면** 디자이너에게 넘기기 전에 개발자가 후속 PR 로
맞춘다. 맞출 수 없거나 의도된 차이로 보이면 추측하지 말고 이슈에 묻는다.
디자이너의 답은 셋 중 하나다.

- **코드가 틀렸다** → 후속 PR.
- **사본이 틀렸다** → 디자이너가 사본을 고치고 댓글로 알린다. 개발자는 다시
  그리지 않고 플러그인의 **리디자인 대조** 버튼으로 다시 잰다.
- **알고 남기는 차이다** → 디자이너가 이슈 본문 5번에
  `허용 차이: <변형> — <이유>` 로 적는다.

캔버스 확인 요청은 `⇄` 가 "차이 없음" 이거나, 남은 차이가 전부 허용 차이일 때
보낸다.

**보드 이동.** 같은 보드를 쓰므로 개발자도 카드를 직접 옮긴다. 신호는 사람이 이미
하는 행동이다.

| 칸 이동 | 신호 | 손으로 옮기는 사람 | 자동화 |
|---|---|---|---|
| → 미착수 | 이슈 생성 | ZenHub 기본 | 그대로 |
| 미착수 → 조사중 | 디자이너 착수 | 디자이너 | 2단계(나중) |
| 조사중 → 결정완료 | 스펙 6항목 완료, 열린 질문 "없음" | 디자이너 | 3단계(선택, 나중) |
| 결정완료 → 구현중 | 개발 착수, PR 본문 `Part of #이슈` | 개발자 | **1단계** |
| 구현중 → 캔버스 확인 | 첫 줄이 `### 캔버스 확인 요청` 인 댓글 | 개발자 | **1단계** |
| 캔버스 확인 → 구현중 | 디자이너의 `반려:` 댓글 | 디자이너 | **1단계** |
| → Closed | 디자이너가 이슈를 닫음 | ZenHub 기본 | 그대로 |
| Closed → 구현중 | 이슈 다시 열림 — ZenHub 는 닫히기 직전 칸으로 돌려놓고, 그 칸이 캔버스 확인일 때만 구현중으로 옮긴다 | 개발자 | **1단계** |

- 1단계 자동화는 켜져 있다(2026-10-01, 8-1). 손으로 옮기는 것은 언제든 된다.
  자동화가 틀렸으면 사람이 고친다.
- 보드에서 닫힌 이슈를 Closed 칸 밖으로 끌어내면 GitHub 이슈가 다시 열린다. 그 이슈는
  끌어다 놓은 칸에 그대로 둔다(캔버스 확인 칸으로 끌어낸 경우만 구현중으로 옮겨진다).
- 출발 칸이 맞지 않으면 옮기지 않는다. 애매하면 안 옮기는 쪽을 택한다.
- 결정완료 전에 PR 이 열리면 옮기지 않고 이슈에 경고 댓글을 한 번 단다.
- 일반 댓글(질문 · 답)은 칸을 바꾸지 않는다. 반려만 `반려:` 로 시작한다.
- **일반 이슈**(`redesign` 라벨 없음 — 버그 · CI · 문서 · 도구)는 미착수 → 구현중 →
  Closed 만 쓴다. 조사중 · 결정완료 · 캔버스 확인에 넣지 않고, 자동화 대상도 아니다.

**캔버스 감시가 여는 드리프트 이슈**(`디자인 구조 드리프트` 제목, 자동 생성)는
신호다. 그중 코드에 반영할 결정이 있으면 디자이너가 리디자인 이슈로 옮겨 받는다.

### 4-2. 이슈와 PR 의 역할

- 이슈는 "무엇을, 왜" 를 정하고 "반영됐는가" 를 확인하는 곳이다. 디자이너가
  만들고, 디자인 질문과 답, 캔버스 확인 결과가 여기 쌓인다.
- PR 은 "어떻게" 를 담는 곳이다. 개발자가 만들고 CI 가 검증한다. 디자이너
  승인 없이 머지한다 — 디자이너의 확인은 머지 후 캔버스에서 한다.
- **이슈는 디자이너가 캔버스를 확인하고 라이브러리를 게시한 뒤 닫는다.** 머지는 반영이 아니다.

그래서 PR 이 이슈를 닫으면 안 된다. 이슈를 닫는 경로는 여섯이고 전부 피한다.

1. **PR 본문** — 기본 PR 템플릿의 `Closes #` 칸에 리디자인 이슈 번호를 넣지
   않는다. 리디자인 PR 은 리디자인 템플릿으로 연다(8장).
2. **PR 제목 · 커밋 제목** — `fix: #123` 처럼 키워드 바로 뒤에 번호가 오면 닫힌다.
   제목에 번호를 쓰지 않거나 `fix(core): #123` 처럼 scope 를 넣는다.
3. **브랜치의 커밋 메시지** — 스쿼시 머지 본문은 커밋 메시지를 모은 것이다. 커밋
   메시지에도 closing keyword(close · fix · resolve 와 그 활용형)를 이슈 번호에
   붙이지 않는다.
4. **머지할 때** — `gh pr merge --squash --body "Part of #123"` 처럼 스쿼시
   본문을 직접 지정하면 확실하다. 이렇게 하면 커밋의 `BREAKING CHANGE:` 푸터도
   지워지므로, 푸터가 있으면 그 줄을 지정하는 본문에 함께 넣는다(푸터 규칙은
   [업그레이드 가이드](upgrading.md#coui-패키지-릴리스)).
5. **Development 연결** — `gh issue develop` 도, 이슈 사이드바에서 브랜치 · PR 을
   손으로 연결하는 것도 머지 때 이슈를 닫는다. 브랜치는 `git checkout -b` 로 만든다 —
   Figma 플러그인 번들을 굽는 체크아웃(7-1 의 0번)에서는 브랜치를 바꾸지 않고
   `git worktree add -b` 로 워크트리를 만든다.
6. **ZenHub 의 PR 연결 기능** — 쓰지 않는다. 연결하면 이슈가 PR 과 같은 칸으로
   따라 움직이고, 머지 때 이슈가 닫히는지도 확인되지 않았다. 이슈 연결은 PR 본문의
   `Part of #` 하나로만 한다.

### 4-3. 스펙 본문 갱신 규칙

- 댓글로 결정이 바뀌면 디자이너는 이슈 본문(스펙)도 고친다. 개발자는 댓글을 다
  읽지 않아도 본문만 보면 최신 스펙을 알 수 있어야 한다. 본문을 고칠 때는 해당
  칸 끝에 `(변경: YYYY-MM-DD, 댓글 링크)` 를 남긴다.
- 결정완료 뒤에는 **사본도 스펙이다.** 사본을 고치면 1번 표도 같이 고치고, 위
  표기를 남긴 뒤 댓글로 개발자를 멘션한다. 대조는 실행하는 순간의 사본을
  기준으로 재므로, 알리지 않고 고치면 개발자의 기준이 조용히 움직인다.

### 4-3a. 게시

라이브러리 게시는 **디자이너**가 **계열 리디자인의 캔버스 확인을 통과시킬 때마다** 한다
(2026-10-02 결정). 소비 파일은 게시된 라이브러리만 받으므로, 게시 전까지 그 결정은
제품에 닿지 않는다.

게시 전에 본다:

- 사본(`(리디자인)` 세트)이 남아 있으면 게시 목록에서 뺀다.
- 이번 계열에서 은퇴하거나 이름이 바뀐 변형을 소비 파일(유니북 등)이 쓰고 있으면,
  게시 전에 그 인스턴스를 살아남을 변형으로 옮긴다 — 게시 뒤에는 연결이 끊긴다.
  옮길 대상은 PR 본문의 **옮길 소비처 인스턴스** 목록이고, 어디로 옮길지는 같은 PR 의
  **구 변형 → 신 변형 매핑표**가 정한다. 둘 중 하나라도 비어 있으면 게시하지 않는다.

**첫 재게시 전에 한 번**: 발행 대상 세트 전부의 key 와 변형 수를 원본과 대조해 발행
누락을 찾고, 소비 파일을 다시 대조해 "기본값으로 올릴 반복 수정 후보" 와 "재게시 때
끊길 인스턴스" 목록을 먼저 만든다.

### 4-4. 릴리스

머지된 코드는 릴리스 PR 이 머지될 때 소비 앱에 나간다. **머지된 PR 이 있는데
아직 닫히지 않은 리디자인 이슈가 있으면, 릴리스 PR 은 그 이슈가 닫힌 뒤 머지한다.**
상태 칸(구현중 · 캔버스 확인)이 아니라 이 사실로 판단한다 — 반려되면 이슈가
구현중으로 돌아가므로, 칸으로 판단하면 반려된 중간 상태가 그대로 출하된다.

## 5. 스펙은 이슈 6항목

| # | 항목 | 쓰는 법 | 예 |
|---|---|---|---|
| 1 | 무엇이 바뀌나 | 전후 값 표. 값은 토큰 이름으로. 스케일에 없는 값은 "새 토큰 필요" 로 표시 | hover: fill wash 8% → stroke outline |
| 2 | 왜 | 한두 문장. 조사와 실측 근거는 링크로 — 전수조사 · 제안 · 결정 문서는 [`docs/redesign/`](../redesign/README.md) 에 둔다 | 보더 있는 컨트롤은 상태를 선으로 표현 |
| 3 | 구조 변경 여부 | 축, 변형, 컴포넌트 속성의 추가 · 삭제 · 이름 변경과 이유. 캔버스 표현만 바뀌는지, 코드 파라미터도 없어지는지 | Show icon 불린 추가 |
| 4 | Figma 링크 | 세트마다 원본 옆 `<세트 이름>(리디자인)` 사본의 노드 링크 | `EmptyState(리디자인)` 링크 |
| 5 | 검수 기준 | 체크할 수 있는 문장. `⇄` 가 못 보는 것(컴포넌트 속성 · 효과 등)은 반드시 적는다. 허용 차이도 여기 | "Show icon 을 끄면 아이콘 자리가 사라진다" |
| 6 | 열린 질문 | 없으면 직접 "없음" 이라고 적는다(빈 칸과 구분) | 없음 |

- 1 · 2 · 4 · 5 · 6 번은 결정완료로 옮기기 전에 채운다(3번이 "있음" 이면 3-1 도).
  이슈를 처음 만들 때는 비워 둬도 된다.
- 6번이 "없음" 이 아니면 "결정완료" 로 옮기지 않는다. 개발자는 "결정완료" 이슈만
  가져간다.
- 3번이 "있음" 이면 디자이너가 `structure-change` 라벨을 붙인다(이슈 폼은 조건부
  라벨을 붙이지 못한다).
- **1번 표와 사본이 다르면 개발자는 질문한다.** 표가 스펙의 정본이지만 `⇄` 는
  사본과 비교하므로, 둘이 다르면 기계 확인이 틀린 기준으로 통과하거나 실패한다.
- 구조 변경(3번)은 이유가 있어야 한다. 이유가 없는 구조 변경 스펙은 개발자가
  질문으로 되돌려도 된다.
- 머지된 뒤에는 코드가 값의 정본이다. 이슈의 표는 반영 전 입력으로 남는다.

## 6. 막혔을 때

어디서 묻든 답은 이슈에 남긴다.

| 상황 | 할 일 |
|---|---|
| 스펙에 없는 판단이 필요 | 구현을 멈추고 이슈에 댓글로 질문, `question` 라벨 |
| 1번 표와 사본이 다름 | 이슈에 질문 |
| 규칙과 스펙이 부딪힘 | 그 부분의 구현을 멈추고, 부딪히는 규칙 파일 · 절을 링크해 이슈에 묻는다. 스펙을 고칠지 규칙 변경을 요청할지는 디자이너가 고르고, 규칙 변경은 개발자가 규칙 PR 로 낸다 |
| 급한 질문 | 메신저로 묻고, 답을 이슈 댓글로 옮긴다 |
| 특정 변형에 관한 질문 | Figma 해당 노드에 코멘트, 그 링크를 이슈에 |

추측으로 채우고 PR 설명에서 해명하는 방식은 쓰지 않는다. 추측으로 채운 값은
다음 리디자인에서 원인 모를 차이가 된다.

## 7. 검수 — 누가 무엇을

기계가 볼 수 있는 것은 기계가 보고, 디자이너는 기계가 못 보는 것만 본다.

| 누가 | 언제 | 무엇을 |
|---|---|---|
| CI | PR | 필수 가드(빌더 리터럴 금지, 내보내기 신선도, 토큰 · 구조 가드 등)와, 바뀐 재촬영 이미지가 PR 의 예측과 맞는지. 실패하면 머지되지 않는다. 재촬영 자체의 누락은 대부분 못 막는다(4장) |
| 개발자 | 머지 후 | `⇄` 차이 없음(또는 허용 차이만), 낡은 세트 0, 로그 경고 0, Web · Flutter 재촬영 결과, 캔버스 출력 점검(7-2) |
| 디자이너 | 머지 후 | 시각 위계, 상태 간 구분, 여백 리듬, `⇄` 가 못 보는 항목(컴포넌트 속성 · 효과 등) |

화면이 바뀌는 PR 에는 Web · Flutter 재촬영 이미지가 함께 올라온다. 디자이너가
머지 전에 볼 의무는 없지만, 실제 렌더를 미리 보고 싶으면 PR 의 Files 탭에서
전후를 나란히 볼 수 있다.

### 7-1. 컴포넌트 반영 운영 (개발자)

**컴포넌트 반영은 한 사람(개발자)만, 정본 파일에서, main 으로 구운 번들로**
돌린다. 두 사람이 각자 빌드로 돌리면 세트가 "다른 빌드" 로 뒤집히고 손 편집
보존의 기준도 흔들린다.

0. Figma 에 연결한 플러그인 manifest 는 번들을 굽는 목적지 체크아웃의 것이어야
   한다. 목적지는 `COUI_BUNDLE_DEST`(기본 `$HOME/orca/coui/tools/figma-token-sync`)
   이고, 체크아웃이 다른 곳이면 이 값을 지정한다. 기능 브랜치 워크트리의 manifest
   를 연결해 두면 main 번들이 그 플러그인에 닿지 않는다.
1. main 으로 번들을 굽는다 — `scripts/figma/rebuild_bundle_from_main.sh`
   (다음 번들을 적재만 하므로 돌고 있는 반영에 안전하다).
2. 플러그인을 닫고 `scripts/figma/rebuild_bundle_from_main.sh --promote` 로
   승격한다. 승격 출력의 `번들 출처 = main <커밋>` 이 7-3 댓글의 번들 칸에 적을
   값이다(나중에 다시 보려면 번들 목적지 디렉터리에서 `npm run bundle:owner`).
3. 오래 열어 둔 Figma 탭은 닫고 파일을 새로 연다.
4. 플러그인에서 **전체 선택**을 체크하고, 손 편집 보존이 켜진 상태에서
   **컴포넌트 반영**을 누른다. 해시가 같은 세트는 건너뛴다.
5. **낡은 세트 보기**로 낡은 세트가 0 인지 본다(첫 줄이 `캔버스 = 현재 코드 ✅`).
6. `⇄` 줄은 그 실행에서 다시 그린 세트에만 찍힌다. 대상 세트가 건너뛰어졌으면
   세트를 선택하고 **리디자인 대조** 버튼으로 받는다(그리지 않고 읽기만 한다).

- 반영이 도는 동안에는 번들 파일(`code.js`)을 다시 쓰는 동작을 하지 않는다 —
  `--promote` · `--now`, 그리고 연결된 체크아웃에서의 `npm run build` ·
  `melos run figma:sync`. 파일이 다시 쓰이면(내용이 같아도) 돌던 실행이 로그
  없이 끝난다.
- 경고는 로그에서 ⚠ 가 들어간 줄이다(`⇄` 블록 안에 들여쓴 줄 포함). 대상 계열의
  ⚠ 줄이 0 이어야 한다.
- 실행이 로그 없이 끝나거나 오류로 멈추면: 먼저 그 사이 위 동작이 돌았는지 본다.
  플러그인을 다시 열고 같은 선택으로 다시 반영한다 — 이미 끝난 세트는 건너뛴다.
  코드는 그대로인데 캔버스가 틀리면 **변경 없어도 다시 그리기**를 켜고 대상
  세트만 반영한다. 두 번 되풀이되면 로그 마지막 줄을 붙여 버그 이슈를 열고,
  리디자인 이슈에는 반영이 늦어진다고 알린다.
- 자세한 단계와 문제 해결은 [Figma 플러그인 작업](figma.md)을 따른다. Claude
  Code 를 쓰면 `/cc-coui-sync:status` 가 번들 출처와 낡은 세트를 한 표로 보여준다.

### 7-2. 캔버스 출력 점검 (개발자)

리디자인 과정에서 실제로 깨졌던 항목이다. 좌표와 크기가 맞아도 렌더가 틀릴 수
있어서, 노드 수치가 아니라 캔버스를 보고 확인한다.

| 확인 항목 | 기준 | 놓치면 |
|---|---|---|
| 노드 transform | 반전 없음 | 뒤집힌 노드가 좌표 검사를 통과해 상태 레이어가 빗나감 |
| clipsContent 조상 | 포커스 링 등 바깥으로 나가는 요소 위에 없음 | 포커스 링이 잘려 안 보임 |
| 복제 후 속성 참조 | 원본 변형과 같음 | 불린 · 교체 속성 연결이 일부 변형에서만 끊김 |
| 아이콘 슬롯 · 인스턴스 크기 | 스펙 값과 같음 | 크기별 아이콘이 어긋남 |
| 숨김 슬롯 | 실제로 숨겨짐 | 꺼도 보이는 요소가 남음 |
| 렌더 범위 | 바운딩 박스 안 | 인접 컴포넌트와 겹침 |

같은 결함이 두 번 나오면 그건 점검 항목이 아니라 빌더 결함이다. 이슈로 올리고,
가능하면 플러그인이 그리는 시점에 스스로 확인하게 만든다.

### 7-3. 캔버스 확인 요청 댓글

개발자가 7단계에서 이슈에 남기는 댓글 형식이다. **첫 줄 `### 캔버스 확인 요청` 이
보드를 캔버스 확인으로 옮기는 신호다** — 이 줄을 바꾸면 자동화가 멈추므로, 바꿀 때는
`.github/redesign-board.json` 의 `canvasCheckHeading` 도 같이 바꾼다.

````markdown
### 캔버스 확인 요청

- 머지: #PR, #PR (마지막 main 커밋 `abc1234`)
- 번들: `번들 출처 = main abc1234` 로 컴포넌트 반영
- Web · Flutter: 재촬영 결과 링크 (렌더 변화가 없으면 "없음")
- 낡은 세트: 0
- 로그 경고: 0
- 캔버스 출력 점검(7-2): 이상 없음
- 사람이 봐야 할 것: (스펙 5번 중 `⇄` 가 못 보는 항목)

`⇄` 대조 (로그의 `⇄ <세트>` 블록 전체):

```text
(여기에 붙인다)
```
````

- `⇄` 블록 첫 줄의 기준이 디자이너 사본(`<세트>(리디자인)`)인지 확인한다.
  `(리디자인 · 시각)` 이면 사본을 찾지 못한 것이다.
- 로그가 잘렸으면 플러그인이 내려받게 하는 `designer-parity-*.json` 을 첨부한다.
- `⇄` 가 `대조 건너뜀` 이나 `리디자인 사본 없음` 이면 요청하지 않는다 — 대조가
  돌지 않은 것이다. 사본의 형태 · 위치 · 이름을 디자이너와 먼저 맞춘다(3장).

## 8. GitHub 세팅

새로 설치할 서비스는 없다.

| 항목 | 상태 |
|---|---|
| 디자이너 권한 | 디자이너 계정이 저장소 관리자라 할 일 없음 |
| 라벨 | `redesign`, `structure-change` 는 만들어져 있다. `question` 은 기존 라벨을 쓴다. `family:<계열>` 은 필요할 때 만든다 |
| 이슈 템플릿 | `.github/ISSUE_TEMPLATE/redesign.yml` — 새 이슈에서 **리디자인 스펙** 선택 |
| PR 템플릿 | `.github/PULL_REQUEST_TEMPLATE/redesign.md` — `gh pr create --template redesign.md`, 또는 PR 작성 URL 에 `template=redesign.md` 쿼리(이미 `?` 가 있으면 `&template=redesign.md`) |
| 보드 | ZenHub 워크스페이스 [`CoUI`](https://app.zenhub.com/workspaces/coui-6abdd7b1938f40001c4865f1/board) (아래) |

템플릿을 지정하지 않고 PR 을 열면 기본 템플릿이 붙는다. 그 템플릿의 `Closes #`
칸에 리디자인 이슈 번호를 넣으면 머지 때 이슈가 닫힌다 — 리디자인 PR 에서는
`Part of #` 로 바꾼다.

### 8-1. 보드

보드는 ZenHub 워크스페이스 [`CoUI`](https://app.zenhub.com/workspaces/coui-6abdd7b1938f40001c4865f1/board)
하나다. 디자이너와 개발팀이 같이 쓰고, 저장소 `coco-de/coui` 가 연결돼 있다. ZenHub 가
저장소의 이슈를 자동으로 가져오므로 이슈 폼에 보드 설정이 없다.

| 칸 | 뜻 | 쓰는 이슈 |
|---|---|---|
| 미착수 | 아직 손대지 않음. 새 이슈가 자동으로 들어온다(ZenHub 기본 `New Issues` 칸의 이름을 바꾼 것) | 전부 |
| 조사중 | 디자이너가 조사와 사본 리디자인을 진행 중 | 리디자인 전용 |
| 결정완료 | 스펙 6항목 확정, 열린 질문 없음. 개발자가 가져갈 수 있음 | 리디자인 전용 |
| 구현중 | 개발 진행 중 | 전부 |
| 캔버스 확인 | 반영 완료, 디자이너가 캔버스를 사본과 비교하는 중 | 리디자인 전용 |
| Closed | 이슈가 닫힘. ZenHub 고정 칸이라 이름을 바꿀 수 없고, 닫지 않은 이슈는 옮길 수 없다 | 전부 |

- 리디자인 이슈만 보려면 저장한 보기 "리디자인"(`redesign` 라벨 필터)을 쓴다. ZenHub
  필터는 실제로 붙은 라벨만 목록에 보여주므로, 첫 리디자인 이슈가 생기면 디자이너가
  저장한다.
- 스프린트와 포인트는 칸이 아니라 ZenHub 스프린트 기능으로 관리한다. 리디자인 이슈도
  스프린트에 넣을 수 있다.
- 다른 보드로 같은 이슈를 추적하지 않는다. 보드가 둘이면 어느 상태가 사실인지 모르게
  된다.

**쓰지 않는 ZenHub 기능**

| 기능 | 이유 |
|---|---|
| PR 을 이슈에 연결 | 연결하면 이슈가 PR 과 같은 칸으로 따라 움직인다. 머지 때 이슈가 닫히는지도 확인되지 않았다. 이슈 연결은 PR 본문의 `Part of #` 하나로만 한다(4-2 의 6번) |
| 칸 자동화(Smart Pipelines) | 칸에 들어오거나 나갈 때 라벨 · 담당자를 바꾸는 기능이라 아래 자동화와 섞이면 원인을 찾기 어렵다 |
| Workflows(워크스페이스 사이 연결) | 보드가 하나라 필요 없다 |

**보드 자동화** (4-1 "보드 이동" 표의 1단계)

ZenHub 에는 PR 이나 댓글을 보고 칸을 옮기는 기능이 없어서, GitHub Actions 가 ZenHub
GraphQL API 로 옮긴다. 대상은 `redesign` 라벨이 붙은 이슈뿐이다. 사양은
[보드 상태 자동화 사양](../redesign/보드-상태-자동화-사양.md)이다.

| 무엇 | 어디 |
|---|---|
| 워크플로 | `.github/workflows/redesign-board.yml` |
| 판정 규칙 | `.github/scripts/redesign_board.mjs` (테스트: `redesign_board.test.mjs`) |
| 설정값 — 워크스페이스 · 칸 이름 · 라벨 · 디자이너 목록 | `.github/redesign-board.json` |

- **인증**: 저장소 시크릿 `ZENHUB_API_KEY` — ZenHub 설정 → API 의 **GraphQL Personal
  API Key**. 키는 발급한 사람의 ZenHub 계정에 묶여서, 그 사람이 빠지면 자동화가 멈춘다.
  키가 비었거나 무효이면 워크플로가 실패로 끝난다. 경고 댓글은 기본 `GITHUB_TOKEN` 으로
  단다. 지금 키는 디자이너(`designcocode`) 계정 것이고 교체도 디자이너가 맡는다 —
  자동 이동은 ZenHub 활동 기록에 이 이름으로 남는다.
- **실제 모드**(2026-10-01 디자이너 결정): 저장소 변수 `REDESIGN_BOARD_DRY_RUN=false`.
  시험 모드로 되돌리려면 변수를 지우거나 `true` 로 둔다 — 그동안은 옮기지 않고 실행
  로그에만 남긴다.
- 칸 ID · 이슈 ID 는 코드에 두지 않고 실행 때 이름과 이슈 번호로 찾는다. 보드의 칸
  이름을 바꾸면 설정 파일의 `status` 도 같이 바꾼다.
- 결정완료 판정(3단계)은 판정 함수와 테스트만 있고 워크플로에 연결하지 않았다.
- **이슈를 양식 밖에서 만들 때**(`gh` · Claude Code)도 본문은 양식과 같은
  `### <칸 제목>` 구조로 쓴다 — 3단계가 그 제목으로 칸을 찾게 된다.
  Claude Code는 팀용 [`redesign-handoff` 스킬](https://github.com/coco-de/skills/blob/main/internal/coui/skills/redesign-handoff/SKILL.md)을
  따른다 — 이슈 초안부터 캔버스 확인 요청 · 보드 옮기기까지 칠 명령이 거기 있다.

### 8-2. 두지 않는 것

- **머지 전 디자이너 승인 게이트.** 검수를 머지 후 캔버스에서 하므로 머지 전에
  승인할 대상이 없다. 게다가 브랜치 보호의 승인 요구는 경로별로 좁힐 수 없어,
  켜면 리디자인과 무관한 모든 PR(릴리스 PR · 재촬영 PR 포함)이 승인을 기다린다.
  디자이너의 통제 지점은 **이슈를 닫는 것**과 **반려**다.
- **리디자인 대조를 PR 에서 자동 실행하는 워크플로.** 대조는 Figma 데스크톱 안의
  플러그인에서만 돈다. 대신 개발자가 머지 후 로그를 이슈에 붙인다(7-3).

| 2 | 개발자 컴퓨터에 플러그인 연결과 번들 굽기 확인(7-1 의 0번 포함, [Figma 플러그인 작업](figma.md)) | 개발자 | [ ] |

첫 대상은 EmptyState 다. 한 바퀴 돌린 뒤 막힌 곳이 있으면 이 문서를 고친다.
