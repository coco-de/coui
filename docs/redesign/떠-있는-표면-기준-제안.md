## 1. 실측 (2026-10-06)

### 1-1. 범위

**대상 20곳**: Popup, Menu, DropdownMenu, ContextMenu, Menubar 드롭다운, Popover, HoverCard, Tooltip, Toast, Select 패널, DatePicker · TimePicker · ColorPicker 팝오버, Autocomplete · PhoneInput 드롭다운, NavigationMenu 패널, Fab 팝업, Command dialog, Dialog, Drawer 패널.

**뺀 것 3곳** — 떠 있지 않다.

| 표면 | 이유 |
|---|---|
| Command inline | 제자리에 놓이는 목록이다. 그림자 `none` (코드 대조) |
| Command fullscreen | 화면 전체다. 반경 0 · 테두리 0 · 그림자 `none` (코드 대조) |
| ItemPicker | 위젯 주석이 `surface:content — a picker laid out in the page flow, not mounted over it` 라고 적는다. OutlinedContainer 를 합성하고 그림자가 없다. 테두리 `outline-variant` 1 (코드 대조) |

### 1-2. 토큰

**그림자 스케일** — `CoreShadow` (`packages/coui_core/lib/src/effect/shadow_scale.dart`). 아래 네 단은 모두 레이어 두 장이다(스케일 전체는 `none` · `xs` · `sm` · `md` · `lg` · `xl` · `xl2` · `xl3` · `inset` 9단이고, `inset` 은 한 장, `none` 은 0장이다). 값은 (x, y, blur, spread, 불투명도).

| 토큰 | 레이어 1 | 레이어 2 | 코드 주석이 적은 용도 |
|---|---|---|---|
| `sm` | 0, 2, 4, −1, 0.05 | 0, 1, 2, 0, 0.03 | Card default state |
| `md` | 0, 4, 8, −2, 0.06 | 0, 2, 4, −1, 0.04 | Card hover, Dropdown |
| `lg` | 0, 8, 16, −3, 0.07 | 0, 4, 6, −2, 0.04 | Popover, Tooltip |
| `xl` | 0, 14, 28, −5, 0.08 | 0, 6, 10, −3, 0.05 | Modal, Dialog |

주석의 용도와 실제 쓰임이 다르다. Popover 는 `md` 를 쓰고, Tooltip 은 그림자가 없다 (코드 대조).

**그림자 색** — 모든 떠 있는 표면이 `shadow` 토큰을 기준색으로 쓴다(Web Toast 만 예외, §1-6). `shadow` 는 Light · HCLight 에서 순검정, Dark · HCDark 에서 순백이다. 코드 주석의 이유: "on a dark page black is simply the page" (코드 대조, `semantic_mapping.dart`). 캔버스 변수 `color/shadow` 도 같은 값이다 (캔버스).

**테두리 · 채움 색** — 캔버스 변수 `1-1. Semantic/ Color · CoUI` 의 별칭 (캔버스). 코드 `semantic_mapping.dart` 와 같다 (코드 대조).

| 토큰 | Light | Dark | HCLight | HCDark |
|---|---|---|---|---|
| `surface` | neutral/white (`#fcfcfd`) | neutral/black | neutral/white | neutral/black |
| `outline` | grey-darker (`#646568`) | grey-light | grey-darkest | grey-lightest |
| `outline-variant` | grey-lighter (`#c3c4c6`) | grey-darker | grey-dark | grey-light |
| `inverse-surface` | neutral/black (`#18191b`) | neutral/white | neutral/black | neutral/white |

`surface` 는 고대비 모드에서 움직이지 않는다. `outline` 과 `outline-variant` 는 움직인다.

**대비** — CoUI 브랜드, `surface` 위. `outline-variant` 는 Light 1.70 · Dark 3.02 · HCLight 3.92 · HCDark 8.02 (`skeleton-조사.md` 실측). `outline` 은 Light 5.68 · Dark 8.02 (같은 문서) · HCLight 8.11 · HCDark 12.09. HCLight · HCDark 두 값은 이번에 캔버스 변수의 hex(위 표 · `surface` Light `#fcfcfd`, Dark `#18191b`)로 WCAG 휘도 공식을 써서 계산했다 — 같은 계산이 문서의 나머지 여섯 값도 그대로 재현한다 (캔버스).
대비 가드는 `outline` 을 모든 surface 톤에 대해 3:1(WCAG 1.4.11)로 검사하고, 지금 기준선에 `outline` 위반은 0건이다. `outline-variant` 는 "the subtle divider tone" 이라며 **일부러 검사하지 않는다** (코드 대조, `packages/coui_core/tool/check_contrast.dart`).

캔버스에는 코드에 없는 `color/outline-subtle` 변수도 있다 — Light grey-lightest(`#d5d6d7`) · Dark grey-darkest · HCLight · HCDark grey (캔버스). 패키지 코드(`coui_core` · `coui_flutter` · `coui_web`)에는 같은 이름이 없고, 플러그인 selftest 주석 하나가 이 이름을 유니북 발행 컬렉션의 변수로 언급할 뿐이다 (코드 대조, `tools/figma-token-sync/scripts/selftest-rebind-brand.ts`). 아래 선택지에는 넣지 않았다.

### 1-5. 코드와 캔버스가 다른 곳

| # | 무엇 | 코드 | 캔버스 |
|---|---|---|---|
| 1 | 메뉴 계열 테두리 색 — Menu · DropdownMenu · ContextMenu · Menubar · Fab (5세트) | `outline-variant` | `outline` (Popup 인스턴스를 덮지 않음) |
| 2 | Menubar 드롭다운 테두리 두께 | 0 | 1 |
| 3 | 그림자 색 (모든 세트) | `shadow` 토큰 — Dark 에서 순백 | 리터럴 검정, 모든 모드 |

3번은 결함이 아니라 플러그인의 설계다. 불투명도가 1 미만인 그림자에 색 변수를 연결하면 변수가 알파를 덮어써 6% 그림자가 불투명해진다. 그래서 플러그인은 알파 1 이상일 때만 연결한다 (코드 대조, `tools/figma-token-sync/src/paint.ts` `setShadow`). 결과로 **캔버스에서는 Dark 모드의 그림자를 볼 수 없다.** 아래 선택지의 다크 모드 항목은 코드 기준이다.

반경 차이(HoverCard 8 · 16, Drawer 붙은 모서리)는 `컨테이너-반경-사다리-제안.md` 가 이미 다뤘다.

### 1-6. Flutter 와 Web 이 다른 곳 (코드 대조)

| 무엇 | Flutter | Web |
|---|---|---|
| Toast 그림자 기준색 | `shadow` 토큰 | `rgb(var(--coui-on-surface))` |
| Toast 그림자 출력 | 공용 어댑터 | 레이어를 리터럴로 굽는다(`shadowLayers.toValue(base: …)`). 다른 표면은 `emitShadow` 를 거쳐 `var(--shadow-md)` 로 나가므로 표면 스타일 프리셋이 그림자를 바꿀 수 있다. Toast 만 프리셋이 닿지 않는다 |

## 2. 테두리를 제약하는 것

### 2-1. 강제 색 모드 — 그림자만으로 된 경계는 사라진다

코드 계약(`surface_a11y_contract.dart`)이 이렇게 적는다: "Forced-colours modes replace colours but do not create geometry: a boundary drawn purely with shadow has nothing to force, so it disappears rather than changing colour." 그래서 그림자로 경계를 그리는 프리셋은 대신 그릴 테두리를 **선언해야 하고**, 선언하지 않으면 생성자의 `assert` 가 막는다(디버그 빌드에서만 도는 검사다).

그런데 이 장치는 **프리셋 단위**다. 기본 스타일은 경계를 "실제 테두리" 로 선언하므로 대신 그릴 테두리가 없다 (코드 대조, `CoreSurfaceA11yContract.defaultSurface`). 기본 스타일에서 테두리 두께가 0인 떠 있는 표면 — **Toast · Tooltip · Menubar 드롭다운** — 은 강제 색 모드에서 채움도 그림자도 강제로 바뀌어 경계가 남지 않는다. 이 문장은 코드 계약의 설명에서 유도한 것이고, 실제 브라우저에서는 재지 않았다(§7).

같은 모드에 대한 선례가 레포에 있다. Tailwind v3 의 `outline-none` 은 `outline: 2px solid transparent` 로 컴파일되는데, 이유가 "색 강제 모드가 칠할 것을 남겨두려는 의도적 설계" 다 (`.claude/rules/web/pseudo-state-emit.md`). 투명한 선은 평소에 안 보이고, 강제 색 모드에서는 시스템 색으로 칠해진다.

### 2-2. 다크 모드 — 테두리가 거의 유일한 경계다

Dark 에서 `surface` 는 neutral/black 이고 그림자 색은 순백이다. 그림자 불투명도는 `md` 기준 0.06 · 0.04 다. 페이지가 `surface` 로 칠해져 있다면 패널과 페이지는 같은 색이 되고, 경계는 테두리와 옅은 흰 그림자만 남는다. 페이지 기본 배경이 무엇인지는 앱이 정한다(Web `CoUIWeb.background` 는 기본값이 없다) (코드 대조).

### 2-3. 프리셋 — 값은 스케일 위에 있어야 한다

표면 스타일 프리셋은 `--shadow-*` 변수를 다시 가리켜 그림자를 바꾼다. 스케일 밖 값은 리터럴로 나가 프리셋이 닿지 않는다. 가드 `check_shadow_indirection.sh` 가 이것을 막는다 (코드 대조). 그래서 아래 선택지는 전부 `CoreShadow` 스케일 안의 단만 고른다.

### 2-4. 테마 축 규칙

`.claude/rules/core/theme-axis-composition.md` 의 "강제되지 않는 property 에만 실린 경계는 그 모드에서 존재하지 않는다" 가 2-1 의 근거다. 같은 규칙의 따름정리 3 — "의도적으로 경계가 없는 표면은 경계를 받지 않는다. 의무는 경계 메커니즘 종류별로 매긴다" — 가 반전 채움 표면(Toast · Tooltip)을 따로 다루는 근거다.

## 3. 역할 묶기

반경 사다리의 역할에 맞췄다. 증거가 따로 다룰 것을 요구하는 곳만 나눴다.

| 역할 | 표면 | 반경 (확정) | 따로 둔 근거 |
|---|---|---|---|
| **① 떠 있는 패널** | Popup, Menu, DropdownMenu, ContextMenu, Menubar 드롭다운, Popover, Select 패널, DatePicker · TimePicker · ColorPicker 팝오버, Autocomplete · PhoneInput 드롭다운, NavigationMenu 패널, Fab 팝업, HoverCard, Toast | 12 | — |
| **② 모달** | Dialog, Drawer 패널, Command dialog | 16 | 뒤를 덮는 막(scrim)이 있다. 지금도 패널보다 한두 단 높은 그림자를 쓴다 |
| **③ 툴팁** | Tooltip | 8 (컨트롤 단) | 반경 사다리가 이미 컨트롤 단에 두었다. 그림자 · 테두리 필드가 아예 없다 |

**반전 채움은 역할이 아니라 형태로 다룬다.** Toast 는 그림자와 반경이 패널과 같다. 다른 것은 채움이 반전색이라 테두리를 그릴 수 없다는 것뿐이다. 그래서 Toast 를 별도 역할로 만들지 않고, 테두리 규칙에 "채움이 반전색인 표면은 보이는 테두리를 그리지 않는다" 는 **형태 기준**을 하나 둔다(§4-5). 이름 목록이 아니라 형태로 적는 이유는 `.claude/rules/process/design-code-handoff.md` "예외를 나열하지 말고 형태로 적는다" 와 같다. Tooltip 도 같은 기준을 받는다.

## 4. 선택지

### 4-1. ① 패널 — 그림자

| | 값 | 장점 | 단점 |
|---|---|---|---|
| **가** | `md` | 패널 16곳 중 15곳이 이미 이 값이다. 바뀌는 것은 NavigationMenu 하나(코드 기본값 1개, 세트 1개). 모달(`xl`)과 두 단 차이가 남는다 | 코드 주석은 `lg` 를 "Popover, Tooltip" 용으로 적었다 — 주석을 고쳐야 한다. NavigationMenu 의 큰 패널(최소 폭 256)이 지금보다 덜 떠 보인다 |
| 나 | `lg` | 패널이 더 분명히 뜬다. 코드 주석의 용도와 맞는다 | Popup 기본값 하나가 Popup 자신과 Popup 을 쓰는 12곳 전부의 앱 렌더를 바꾼다. Toast · HoverCard 도 바꿔야 한다. 캔버스는 15세트가 다시 그려진다. 모달이 `lg` 를 고르면 둘이 같아진다 |
| 다 | `sm` | 가장 가볍다 | 바뀌는 곳이 나와 같은 규모다. `sm` 은 코드에서 카드의 쉬는 상태 용도라, 떠 있는 패널과 놓인 카드가 같은 깊이로 읽힌다 |

다크 모드는 세 선택지 모두 같은 `shadow` 토큰(순백)을 쓰므로, 단이 높을수록 Dark 에서 흰 번짐이 넓어진다. 단별 Dark 렌더는 재지 않았다(§7).

### 4-2. ② 모달 — 그림자

| | 값 | 장점 | 단점 |
|---|---|---|---|
| **가** | `xl` | Dialog 가 이미 쓰고, 코드 주석이 "Modal, Dialog" 용으로 적은 단이다. 패널이 `md` 면 두 단 차이 | Drawer · Command dialog 두 곳이 바뀐다(코드 기본값 2개, 세트 2개). Drawer 는 화면 가장자리에 붙어 그림자 일부가 화면 밖으로 나간다(얼마나 나가는지는 재지 않았다) |
| 나 | `lg` | Drawer · Command dialog 가 이미 쓴다. 바뀌는 곳은 Dialog 하나(기본값 1개, 세트 1개) | NavigationMenu 패널이 지금 `lg` 다. 4-1 에서 가를 고르지 않으면 패널과 모달이 같아질 수 있다. Dialog 의 `xl` 은 코드 주석이 근거로 든 "Shadow Token Specification" 매핑을 따른 값이라, 그 근거를 뒤집는다 |

모달은 막(scrim)이 뒤를 어둡게 하므로 그림자 단의 차이가 패널보다 덜 보인다. 막 위에서 두 단이 얼마나 구분되는지는 재지 않았다(§7).

### 4-3. ① 패널 — 테두리

두께는 세 선택지 모두 1(`stroke1`)로 한다. 지금 두께 0인 패널은 Menubar 드롭다운 하나이고, §2-1 때문에 0을 패널 기본으로 둘 이유가 약하다. 0을 원하면 다 를 고른다.

| | 값 | 장점 | 단점 | 앱 렌더가 바뀌는 곳 | 캔버스가 바뀌는 세트 |
|---|---|---|---|---|---|
| **가** | `outline` 1 | Popup 기본값이고 캔버스 전체가 이미 이 값이다. 대비 가드가 3:1 을 검사하는 경계 토큰이다(Light 5.68). 모달 테두리와 같은 토큰이 된다 | 선이 진하다. 컨트롤(버튼 · 필드) 테두리와 같은 무게라 패널이 컨트롤처럼 읽힐 수 있다 | Menu · DropdownMenu · ContextMenu · Fab 팝업 · Menubar 드롭다운(색 + 두께) · NavigationMenu · TimePicker — 7곳. 코드 기본값 4개(Menu 색, Menubar 두께, NavigationMenu 색, TimePicker 색) | NavigationMenu · TimePicker — 2세트 |
| 나 | `outline-variant` 1 | 가볍다. 그림자가 깊이를 맡고 선은 보조한다. 메뉴 계열이 앱에서 이미 이 값이다. 고대비에서 진해진다(HCLight 3.92 · HCDark 8.02) | Light 대비 1.70 — 대비 가드가 "장식 구분선" 으로 보고 검사하지 않는 토큰이다. Dark 에서 3.02. 모달(`outline`)과 토큰이 갈린다. HoverCard 는 합성한 Card 의 테두리를 덮어야 하는데, HoverCard 는 "Card 기본값을 복제하지 않으려고" 테두리 기본값을 일부러 두지 않았다 — 이 원칙과 부딪힌다 | Popup · Popover · Select · DatePicker · ColorPicker · Autocomplete · PhoneInput · HoverCard · Menubar 드롭다운(두께) — 9곳. 코드 기본값 3개(Popup 색, Menubar 두께, HoverCard 새 기본값) | Popup · Menu · DropdownMenu · ContextMenu · Menubar · Popover · Fab · Select · DatePicker · ColorPicker · Autocomplete · PhoneInput · HoverCard — 13세트 |
| 다 | 테두리 없음 (0) + 그림자만 | 가장 깔끔하다 | §2-1 — 강제 색 모드에서 패널 경계가 전부 사라진다. 기본 스타일에 대신 그릴 테두리 규칙을 새로 넣어야 한다. §2-2 — Dark 에서 경계가 흰 6% 그림자뿐이다 | 지금 두께 1인 패널 전부 — 14곳(패널 16곳에서 Menubar 드롭다운 · Toast 를 뺀 수) | 15세트(Popup 과 Popup 인스턴스 · 패널 프레임을 그리는 세트) |

메뉴 계열 · NavigationMenu · TimePicker 가 왜 `outline-variant` 를 쓰는지 결정 문서에서 찾지 못했다. git 이력에서는 2026-06-18 패널 합성 정리(플로팅 패널 6종을 Popup 하나로 합성한 커밋) 때 세 컴포넌트 모두 옛 평면 필드의 `outlineVariant` 값이 그대로 옮겨졌다 (코드 대조). 그 전 코드에 남은 이유는 TimePicker 주석 한 줄뿐이다 — "uses outlineVariant — softer than the trigger border". 디자인 결정 기록은 아니다(§7).

### 4-4. ② 모달 — 테두리

세 곳이 이미 `outline` 1 이다. 질문은 패널과 맞출지다.

| | 값 | 장점 | 단점 |
|---|---|---|---|
| **가** | `outline` 1 그대로 | 바뀌는 곳 0. 4-3 가 와 함께면 떠 있는 표면 전체가 테두리 토큰 하나를 쓴다 | 4-3 나 를 고르면 패널과 모달이 갈린다(역할별이므로 규칙 위반은 아니다) |
| 나 | `outline-variant` 1 | 4-3 나 와 짝이 맞는다 | 3곳 · 기본값 3개 · 세트 3개가 바뀐다. Dialog 는 Dark 에서 막 위의 흰 선으로 경계가 보이는데, 그 선이 옅어진다 |

### 4-5. 반전 채움 표면 (Toast · Tooltip) — 테두리

평소에는 보이는 테두리를 그리지 않는다(코드 주석의 이유, §1-3). 질문은 강제 색 모드다.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| 가 | 지금대로 아무것도 안 한다 | 바뀌는 곳 0 | §2-1 — 강제 색 모드에서 Toast · Tooltip 경계가 사라진다 |
| 나 | 채움과 같은 색의 1px 테두리를 둔다. 평소엔 안 보이고 강제 색 모드에서 시스템 색으로 칠해진다 | §2-1 의 `outline-none` 과 같은 원리. 두 플랫폼이 같은 값을 갖는다. Toast 는 테두리 색이 이미 `inverse-surface` 라 두께 0 → 1 하나만 바꾼다 | Tooltip 에는 테두리 필드가 없다 — Core · Flutter · Web 에 필드를 새로 넣어야 한다(추가라 breaking 은 아니다). 1px 이 레이아웃을 바꾸는지 재지 않았다(§7) |
| **다** | Web 의 강제 색 모드 규칙에서만 그린다 — 프리셋이 이미 쓰는 `@media (forced-colors:active)` 경로를 기본 스타일에도 연다 | 평소 렌더는 두 플랫폼 모두 바이트 단위로 그대로다. 장치가 이미 있다(`theme_config.dart`). Flutter 에는 이 모드가 없어 비대칭은 의도된 것이다(§1-6) | 그 경로(`theme_config.dart` `surfaceStyleForcedColorsBlock`)의 선택자는 `[data-coui-style="…"] .coui-surface` 다 — "떠 있는 표면"(`functional`)만이 아니라 놓인 표면(`content`)까지, 표면 표시 `coui-surface` 가 붙은 **모든** 요소에 걸린다(코드 대조). `functional` 만 해도 Toast · Tooltip 외에 Dock · Scaffold · NavigationBar · DraggablePanel · Window · WindowPanel · RefreshTrigger 가 있고, `content` 쪽은 Card · TextField · Chip · Command 등 30곳이 넘는다. 대상을 테두리 0 인 반전 채움 표면으로 좁히는 선택자를 새로 설계해야 한다 |

Menubar 드롭다운은 4-3 에서 두께 1 을 고르면 이 문제에서 빠진다.

### 4-6. ③ 툴팁 — 그림자

| | 값 | 장점 | 단점 |
|---|---|---|---|
| **가** | 없음 (지금대로) | 바뀌는 곳 0. 반전 채움이 이미 배경과 크게 대비된다. 툴팁은 짧게 떴다 사라지는 표면이다 | 코드 주석(`lg` = "Popover, Tooltip")과 다르다 — 주석을 고친다 |
| 나 | `sm` 또는 `md` | 패널과 같은 "떠 있음" 신호 | Tooltip 에 그림자 필드가 없다 — Core · Flutter · Web 에 새로 넣는다. 캔버스 4변형이 바뀐다. Dark 에서 흰 채움 위 흰 그림자라 보이는지 재지 않았다 |

### 4-7. 역할 값을 코드에 어떻게 적나

"역할별로 하나로" 를 다음 컴포넌트가 어기지 않게 하려면 값이 한 곳에 있어야 한다. 지금은 컴포넌트마다 스케일 단을 직접 고른다.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| 가 | 지금처럼 각 컴포넌트 기본값이 스케일 단을 직접 고른다. 역할 표는 이 문서로 | 구조 변경 없음 | 역할이 코드에서 안 보인다. NavigationMenu `lg` 같은 이탈이 다시 생긴다 |
| **나** | Core 에 역할 별칭을 둔다 — 예: `CoreShadow.panel = md`, `CoreShadow.modal = xl`. 컴포넌트 기본값은 별칭을 참조한다. Web 변수는 늘리지 않는다(별칭이 가리키는 단의 `--shadow-*` 가 그대로 나간다) | 선례가 있다 — 모션 토큰이 "컴포넌트 default 는 alias 를 참조" 한다(`.claude/rules/core/design-tokens.md`). 프리셋은 그대로 닿는다 | 룰 문서와 가드를 손봐야 한다. 테두리 색은 이미 시맨틱 토큰(`outline`)이라 별칭이 필요 없다 — 그림자만 해당된다 |
| 다 | 나 + Figma 에도 역할 효과 스타일을 둔다 | 디자이너가 인스턴스에서 역할을 본다 | 캔버스 노드는 지금 효과 스타일을 쓰지 않는다(§1-4). 플러그인의 그림자 바인딩 방식을 바꿔야 한다. 반경 결정 #4 도 같은 종류의 비용("플러그인의 반경 바인딩 방식")을 착수 전 개발팀이 확인할 항목으로 적었다 — 확인이 끝난 비용은 아니다 |

## 5. 바뀌는 곳과 비용

### 5-1. 확정 조합 기준 (에이전트 권고 조합과 같다)

4-1 가 · 4-2 가 · 4-3 가 · 4-4 가 · 4-5 다 · 4-6 가 · 4-7 나 를 함께 고르면:

| 무엇 | 코드 기본값 | 앱 렌더 | 캔버스 세트 |
|---|---|---|---|
| NavigationMenu 그림자 `lg` → `md` | 1 | 바뀜 | 1 |
| Drawer · Command dialog 그림자 `lg` → `xl` | 2 | 바뀜 | 2 |
| 메뉴 계열 테두리 `outline-variant` → `outline` (Menu 기본값 하나가 DropdownMenu · ContextMenu · Fab · Menubar 를 끈다) | 1 | 바뀜 (5곳) | 0 — 캔버스는 이미 `outline` |
| Menubar 드롭다운 두께 0 → 1 | 1 | 바뀜 | 0 — 캔버스는 이미 1 |
| NavigationMenu · TimePicker 테두리 → `outline` | 2 | 바뀜 | 2 (NavigationMenu 는 위와 겹침) |
| HoverCard 그림자를 resolver 에서 Core 기본값으로 옮김 | 1 새 기본값 · resolver 2곳 | 그대로 | 0 |

| `CoreShadow` 주석(용도) 정정 | — | 그대로 | 0 |

캔버스는 4세트(NavigationMenu · TimePicker · Drawer · Command)가 다시 그려진다. 앱은 메뉴 계열 5곳 · NavigationMenu · TimePicker · Drawer · Command dialog 의 렌더가 바뀐다.

### 5-2. breaking 여부

공개 API(필드 이름 · 타입)는 바뀌지 않는다. 바뀌는 것은 **기본 렌더**다. 이전 선례에서 기본 렌더 변경을 breaking 으로 냈다 — Menu 반경 16 → 8 이 coui_core 0.140.0 에 "8(이전 16)" breaking 으로 나갔다(`컨테이너-반경-사다리-제안.md` §2-4). 같은 방식이면 이번 변경도 breaking 릴리스 노트가 필요하다. 필드를 새로 넣는 선택지(4-5 나, 4-6 나)는 추가라 그 부분만은 breaking 이 아니다. 지우는 필드는 없으므로 폐기 예고 창(`process/deprecation.md`)은 해당되지 않는다.

### 5-3. 반경 변경과 묶을지

반경 결정 #8 이 "Popup 계열 전체를 한 릴리스에" 로 정해졌다. 그림자 · 테두리 변경 대상이 거의 같은 계열이다. 한 릴리스에 묶으면 앱 사용처가 한 번만 흔들리고, 캔버스 전체 재생성(약 33분, `상태-표현-통일-제안.md` §6-3 실측)도 한 번이다. 나누면 각각의 시각 변화를 따로 확인하기 쉽다. §8 의 9번으로 올렸다.

### 5-4. 이 결정이 푸는 작업 순서

`컴포넌트-인벤토리.md` 진행 순서 기준.

| 순서 | 계열 | 이 결정이 정하는 것 |
|---|---|---|
| 1 | Primitive — Popup | 모든 떠 있는 패널의 바탕 값 |
| 2 | Autocomplete · Picker · SpecialInput | Autocomplete · DatePicker · TimePicker · ColorPicker · PhoneInput 패널 |
| 3 | Menu · Navigation | Menu · DropdownMenu · ContextMenu · Menubar 드롭다운 · NavigationMenu 패널 |
| 4 | Overlay · Feedback | Dialog · Drawer · Popover · HoverCard · Tooltip · Toast |

이미 완료된 Select · Fab · Command 도 값이 바뀌면 다시 확인해야 한다(Select 패널은 Popup 을 따르고, Fab 팝업은 Menu 를 따르고, Command dialog 는 자기 값을 갖는다).

## 6. 함께 드러난 `[일반]` 결함 후보

디자인 결정과 무관하게 고칠 수 있는 것들이다. 이 문서의 결정을 기다리지 않는다.

| # | 무엇 | 근거 (코드 대조) |
|---|---|---|
| 1 | Web Toast 그림자가 `emitShadow` 를 거치지 않고 리터럴로 굽혀, 기준색이 `on-surface` 이고 프리셋이 닿지 않는다. Flutter 는 `shadow` 토큰이다 | `coui_web/.../toast/toast_style.dart` `shadowLayers.toValue(base: 'rgb(var(--coui-on-surface))')` |
| 2 | 1번을 가드가 못 잡는다. 가드는 `.toValue(base:` 를 한 줄에서만 찾는데, Toast 호출은 두 줄로 나뉘어 있다 | `scripts/guards/tokens/check_shadow_indirection.sh` |
| 3 | HoverCard 그림자(`elevation: .medium`)가 Core 기본값이 아니라 두 resolver 에 직접 적혀 있다 — 단일 출처 규칙 위반 후보 | `coui_flutter` · `coui_web` 의 `hover_card_style.dart` |
| 4 | 주석이 실제 값과 다르다 — NavigationMenu 주석은 그림자 기준색을 "onSurface default" 로, Web Popup 주석은 `--coui-on-surface` 로 적지만 Popup 기본값은 `shadow` 토큰이다. PhoneInput 의 `defaultBorderColor` 주석은 "Also reused by the popup border" 라고 적지만 패널은 Popup 기본값(`outline`)을 쓴다 | `navigation_menu_style.dart`, `coui_web/.../popup/popup_style.dart`, `phone_input_style.dart` |

## 7. 확인 못 한 것

- 강제 색 모드에서 Toast · Tooltip · Menubar 드롭다운의 실제 렌더. 코드 계약의 설명에서 유도했고 브라우저에서 재지 않았다.
- 그림자 단별 Dark 모드 렌더, 모달 막(scrim) 위에서 `lg` 와 `xl` 이 구분되는 정도. 캔버스는 Dark 그림자를 그리지 못한다(§1-5).
- Drawer 그림자가 화면 밖으로 나가는 정도.
- 4-5 나 의 1px 테두리가 Toast(최소 높이 56) · Tooltip 레이아웃을 바꾸는지.
- 메뉴 계열 · NavigationMenu · TimePicker 가 `outline-variant` 를 고른 디자인 근거. 결정 문서에서 찾지 못했고, 코드에 남은 것은 옛 TimePicker 주석 한 줄뿐이다(§4-3).
- 캔버스 변수 `color/outline-subtle` 이 어디서 와서 어디에 쓰이는지. 값만 읽었다(§1-2).
- 효과 스타일이 이 문서의 20개 세트 밖 노드에 붙어 있는지. 20개 세트 안에서는 0개다.
- 유니북 등 소비 파일의 인스턴스가 이 값들을 덮어쓰고 있는지.
- 브랜드별 대비. 위 대비 수치는 CoUI 브랜드 기준이다.

사실 확인 때 새로 잰 것: `outline` 의 Dark · HCLight · HCDark 대비(§1-2), 효과 스타일 색이 변수에 연결되지 않은 리터럴이라는 것(§1-4), 20개 세트의 모든 변형(§1-4).
