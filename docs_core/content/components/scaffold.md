# Scaffold

`Scaffold`는 화면의 기본 구조를 잡는 통합 레이아웃 컴포넌트입니다. 위로 쌓이는 헤더 섹션, 중앙 본문, 아래로 쌓이는 푸터 섹션을 제공하며, 선택적으로 사이드바, 플로팅 액션 버튼, 로딩 진행 인디케이터를 함께 표시할 수 있습니다. 헤더 영역은 `AppBar`로 leading / 중앙 / trailing 클러스터를 손쉽게 구성합니다.

## 사용 시기 (When to Use)

**이 컴포넌트를 사용하세요:**
- 헤더 / 본문 / 푸터로 구성된 일관된 화면 골격이 필요할 때
- 본문 옆에 사이드바를 두는 데스크톱 레이아웃
- 본문 위에 떠 있는 플로팅 액션 버튼이나 상단 로딩 인디케이터가 필요할 때

**대신 다른 컴포넌트를 사용하세요:**
- `Card`: 화면 일부의 콘텐츠 박스가 필요할 때
- `NavigationBar`: 헤더가 아닌 주요 섹션 이동 네비게이션이 필요할 때

## 동작 스펙 (Behavior)

### 레이아웃

- **고정 모드**: 헤더 / 푸터가 레이아웃 공간을 차지하며 본문을 밀어냄
- **플로팅 모드**: `floatingHeader` / `floatingFooter`가 `true`면 본문 위에 겹쳐 표시
- **떠 있는 내비게이션 바**: `floatingFooter` 인 푸터가 `NavigationBar` 하나뿐이면 푸터 칸은 자기 배경을 칠하지 않고 바만 그립니다. 바가 자기 면을 그리므로, 리퀴드 글래스의 캡슐 바는 띠 위가 아니라 본문 위에 뜹니다. `footerBackgroundColor` 는 이 경우 쓰이지 않습니다
- **사이드바**: `sidebar`를 지정하면 본문과 가로로 나란히 배치

### 로딩 인디케이터

- `loadingProgress`를 지정하면 화면 최상단에 진행 막대 표시
- `loadingProgressIndeterminate`가 `true`면 무한 로딩 막대 표시

### 키보드(IME) 인셋 회피 — `resizeToAvoidBottomInset` (Flutter 전용)

- `true`면 헤더 / 본문 / 푸터 스택(플로팅 오버레이·FAB 포함)을 `MediaQuery.viewInsets.bottom` 만큼 하단 패딩 — 채팅 입력바·폼 같은 하단 고정 콘텐츠가 소프트 키보드와 IME 액세서리 스트립(물리 키보드의 자동완성 툴바 등) 위로 올라옵니다. Material `Scaffold.resizeToAvoidBottomInset`과 동일한 의미입니다.
- 소비한 인셋은 자식 `MediaQuery`에서 제거되어 중첩 Scaffold가 이중 적용하지 않습니다.
- 기본값은 `true` — Material `Scaffold` 의 기본값과 같고, Web 쌍둥이와도 같습니다. 브라우저는 IME 에 맞춰 visual viewport 를 리사이즈하며 이를 끌 방법이 없으므로, Flutter 만 `false` 이면 같은 코드가 Web 에서는 키보드 위로 올라오고 Flutter 에서는 가려집니다.
- 콘텐츠가 키보드 뒤로 이어져야 하는 화면(전면 미디어·지도)에서는 `false` 로 끕니다.
- 본문 높이가 줄어들므로 **스크롤 불가한 고정 높이 본문은 `BOTTOM OVERFLOWED` 를 냅니다** — 종전에 "가려짐"이던 것이 경고로 드러난 것이고, 본문을 스크롤 가능하게 만드는 것이 해법입니다.
- **Web에는 이 파라미터가 없습니다.** 브라우저가 IME를 문서 레벨에서 native 처리하기 때문입니다 — 모바일 웹에서 키보드 회피가 필요하면 앱 진입 HTML의 viewport meta에 `interactive-widget=resizes-content`를 지정하거나 CSS `100dvh` 단위를 사용하세요. 이는 Scaffold 인스턴스가 아니라 문서(document) 단위 설정입니다.

## 사용 가이드라인 (Usage Guidelines)

헤더·본문·푸터·사이드바·FAB를 함께 배치하는 화면 셸에는 Scaffold를 사용합니다. 본문 안의 방향·간격 배치는 [Frame](/components/frame), 콘텐츠 묶음의 표면은 [Card](/components/card), 여러 떠 있는 창의 상태 관리는 [Window](/components/window)를 선택합니다. Scaffold의 loadingProgress는 전체 작업 표시이고 콘텐츠 자리의 로딩은 호출자가 [Skeleton](/components/skeleton)으로 구성합니다.

### ✅ Do

<Callout type="tip">

**키보드 뒤로 이어져야 하는 화면에서만 `resizeToAvoidBottomInset` 끄기**

```dart
Scaffold(
  resizeToAvoidBottomInset: false,
  child: fullBleedMapView,
)
```

기본값이 `true`라 채팅 입력바·폼처럼 하단에 고정된 콘텐츠는 별도 설정 없이 소프트 키보드 위로 올라옵니다 — Material `Scaffold` 및 Web 쌍둥이와 같은 동작입니다. 끄는 것은 전면 미디어·지도처럼 콘텐츠가 키보드 뒤까지 이어져야 하는 화면뿐입니다. Web에는 이 파라미터가 없으므로 모바일 웹 키보드 회피는 viewport meta `interactive-widget=resizes-content` 또는 `100dvh`로 문서 단위에서 처리합니다.

</Callout>

<Callout type="tip">

**헤더에 `AppBar` 를 넣을 때는 `AppBar` 디바이더를 끄기**

```dart
Scaffold(
  headers: [
    AppBar(
      title: const Text('대시보드'),
      showDivider: false,
    ),
  ],
  child: body,
)
```

Scaffold 헤더 보더(`CoreScaffoldStyle.headerBorderColor` · `headerBorderWidth`)와 `AppBar` 하단 디바이더는 **같은 자리**(헤더 하단)에 그려집니다. 둘 다 켜 두면 선이 두 겹이 되고, 한쪽 색만 바꾸면 어긋난 두 줄로 드러납니다. 호출자가 `AppBar` 쪽을 `showDivider: false` 로 끄고, 헤더 경계선은 Scaffold 헤더 보더 한 곳에서 정합니다. Web · Flutter 동일합니다.

</Callout>

---

### ❌ Don't

<Callout type="warning">

**`floatingHeader`를 켠 채 본문에 상단 여백을 주지 않기**

```dart
// ❌ floatingHeader가 레이아웃 공간을 차지하지 않아 헤더가 본문 상단과 겹침
Scaffold(
  floatingHeader: true,
  headers: [appBar],
  child: contentWithNoTopPadding,
)
```

`floatingHeader: true`면 헤더가 본문 위에 겹쳐 표시될 뿐 레이아웃 공간을 차지하지 않습니다. 본문 콘텐츠가 헤더 아래로 가려지지 않으려면 본문 쪽에 헤더 높이만큼의 여백을 직접 줘야 합니다.

</Callout>

## 접근성 (Accessibility)

### 역할

`Scaffold` 는 루트와 본문 두 곳에만 역할을 붙이고, 나머지 슬롯은 그 안에 들어가는 위젯의 몫으로 둡니다.

- **Flutter**: 루트는 `Semantics(container: true, label: scaffoldLabel)` 로 이름 있는 컨테이너 노드가 되고(`scaffold.dart:289-296`), 본문은 `CoUISemantics(role: .main, label: mainLabel, container: true)` 로 감쌉니다(`scaffold.dart:178-183`). `.main` 의 전제 조건이 `label` 인데 라벨을 함께 주므로 역할이 실제로 붙습니다.
- **Web**: 루트는 `<div role="group" aria-label="{scaffoldLabel}">`(`scaffold.dart:242-246`), 본문은 `role="main"` + `aria-label="{mainLabel}"`(`scaffold.dart:186-189`).

`main` 랜드마크가 루트가 아니라 **본문에** 있는 것은 의도된 배치입니다 — 리더 사용자가 헤더와 내비게이션을 건너뛰려고 점프하는 지점이므로, 루트에 있으면 이미 있던 자리로 점프하게 됩니다. `sidebar` 가 있으면 사이드바를 포함하는 행이 아니라 안쪽 본문 셀에 붙습니다(`scaffold.dart:190-209`).

`headers` / `footers` 섹션과 `AppBar` 자신에는 두 플랫폼 모두 역할이 없습니다 — Flutter 의 `_ScaffoldSection` 은 `RepaintBoundary` + `DecoratedBox` + `Column` 이고(`scaffold.dart:408,472`), Web 은 평범한 `div` 입니다(`scaffold.dart:161-175`). `loadingProgress` 를 주면 그 자리의 `Progress` 가 Web 에서 `role="progressbar"` + `aria-valuemin`/`max`/`now` 를(`progress.dart:141-144`), Flutter 에서 백분율 문자열을 담은 `Semantics(value:)` 를 냅니다(`progress.dart:113-116`).

### 키보드

처리하는 키가 없습니다. Flutter `scaffold.dart` 에 `Shortcuts` / `Actions` / `LogicalKeyboardKey` 가 0건이고 Web `scaffold.dart` 에 `keydown` 핸들러가 0건입니다. `Tab` 은 헤더 · 본문 · 푸터 · FAB 안의 각 슬롯 위젯이 만든 정지점 사이를 이동할 뿐 `Scaffold` 자신은 정지점이 아닙니다.

### 스크린 리더

- **루트 이름**은 로컬라이즈된 `scaffoldLabel` 입니다(영어 `Scaffold` / 한국어 `스캐폴드`). 양 플랫폼이 같은 키를 읽습니다.
- **본문 이름**은 로컬라이즈된 `mainLabel` 입니다(영어 `Main content` / 한국어 `본문`).
- **헤더 · 푸터 · 사이드바 · FAB 의 이름**은 각 슬롯 위젯이 책임집니다 — `Scaffold` 는 아무 이름도 얹지 않습니다.
- **상태 통보는 없습니다.** `loadingProgress` 가 바뀌어도 통보되지 않습니다 — Flutter `Progress` 에 `liveRegion` 이 없고 Web `Progress` 에 `aria-live` 도 `role="status"` 도 없어, 진행률은 사용자가 그 지점으로 이동해야만 읽힙니다.

### 포커스 관리

- **진입** — 오버레이가 아니라 포커스 이동이 없습니다.
- **이탈** — 해당 없음.
- **트랩** — 없습니다. Flutter 에 `FocusScope` 가 0건이고 Web 에도 focus trap 이 없습니다.

헤더를 건너뛰는 수단은 skip link 가 아니라 본문의 `main` 랜드마크입니다 — 랜드마크 점프를 쓰는 리더 사용자는 헤더를 건너뛸 수 있지만, 키보드만 쓰는 사용자에게는 헤더 안의 정지점을 차례로 지나가는 것 말고 다른 경로가 없습니다.

### 알려진 제약

- **루트의 `role="group"` 과 이름을 호출부가 바꿀 수 없습니다.** Web 은 `role` / `aria-label` 을 `componentAttributes` **뒤에** 병합해 컴포넌트가 호출자가 넘긴 `attributes` 를 이깁니다(`scaffold.dart:242-246`) — 이 저장소의 일반적인 "호출자가 이긴다" 순서와 반대입니다. Flutter 에는 라벨 슬롯 자체가 없습니다(`scaffold.dart:289-291`). 한 문서에 `Scaffold` 가 여럿이면 전부 같은 이름으로 안내됩니다. 대안 없음.
- **헤더 · 푸터가 랜드마크가 아닙니다.** `banner` / `contentInfo` 역할이 어느 플랫폼에도 없어 리더의 랜드마크 목록에 페이지 머리말 · 꼬리말이 나타나지 않습니다. Web 은 `AppBar(attributes: {'role': 'banner'})` 로 호출부가 실을 수 있지만(`scaffold.dart:381`), Flutter `AppBar` 생성자에는 `attributes` 도 `Semantics` 슬롯도 없어(`scaffold.dart:490` 이하 — 파라미터는 슬롯과 `scaffoldStyle` 뿐) 호출부가 `AppBar` 를 직접 `Semantics` 로 감싸야 합니다.
- **`sidebar` 슬롯에 navigation 랜드마크가 붙지 않습니다.** 두 구현의 주석은 "사이드바는 내비게이션" 이라고 말하지만 실제로 역할을 내는 코드는 어느 쪽에도 없습니다(`scaffold.dart:184-193` / `scaffold.dart:190-203`). 사이드바가 내비게이션이라면 그 위젯 쪽에서 역할을 붙이세요 — 예: `Frame(a11y: CoreFrameA11y(role: .navigation, label: ...), child: sidebarContent)`.
- **`loadingProgress` 의 변화가 통보되지 않습니다.** 위 "스크린 리더" 에 적은 대로 양 플랫폼 모두 live region 이 없어, 로딩이 시작되거나 끝나도 리더는 말하지 않습니다. 진행 상태를 알려야 하는 화면이라면 `Scaffold` 의 인디케이터에 의존하지 말고 통보되는 표면(`Toast` · `Status` 등)을 함께 쓰세요.
- **`floatingHeader` / `floatingFooter` 를 켜면 두 플랫폼의 트리 순서가 갈립니다.** Flutter 는 그 섹션을 세로 스택에서 빼내 본문 **뒤** 오버레이(`Stacks`)로 옮기고(`scaffold.dart:197-230`), Web 은 DOM 위치를 본문 **앞**에 그대로 둔 채 `position: sticky` 클래스만 바꿉니다(`scaffold.dart:223` / `scaffold_style.dart:234`). 읽기 · 포커스 순서를 두 플랫폼에서 같게 유지해야 한다면 고정 모드(기본값)를 쓰세요.

## Adaptive AppBar actions

Set `adaptiveAppBarActions: true` with a direct `AppBar` in `headers` to place its movable controls
in the system’s reserved side strip. The scaffold owns the body inset and rail placement; do not
inset the same strip again in the app. See [AppBar](/components/app-bar) for glass, text-only actions,
preview overrides (`appBarControlInsets`) and physical edge spacing (`appBarRailPadding`).
