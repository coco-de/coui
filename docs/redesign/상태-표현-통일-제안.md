## 1. 실측 (2026-09-30)

60개 세트의 상태 관련 축과 불린 속성을 전수 조회했다.

### 1-1. 비활성·호버·포커스를 표현하는 9가지 방식

| 표현 | 세트 수 | 예 |
|---|---|---|
| `State` 열거형 | 16 | Button, Toggle, Checkbox, TextField, MenuItem |
| `Enabled` 불린 축 (true가 정상) | 24 | Slider, DatePicker, Autocomplete, Fieldset |
| `Disabled` 불린 축 (false가 정상) | 14 | Link, Accordion, Table, Stepper, Filter |
| `Focus` 불린 축 | 13 | Link, Tree, Breadcrumb, TimePicker, PhoneInput |
| `Hover` 불린 축 | 10 | Table, Badge, Pagination, MultiAnswerCard |
| `Focused` 불린 축 | 3 | Badge, Card, Window |
| `Hovered` 불린 축 | 1 | Card |
| `Show focus ring` 불린 속성 | 8 | Button, Toggle, RadioGroup, TextField, TextArea, Chip, Slider, MenuItem |
| `Focus` 불린 속성 (variant 아님) | 2 | StarRating, Range |

같은 뜻이 `Enabled`/`Disabled`/`State=disabled` 세 이름으로, 극성도 반대로 공존한다. 포커스는 다섯 가지 이름으로 존재한다.

### 1-2. `State` 열거형 16개도 서로 다르다

| 세트 | 값 (파일 순서 그대로) | 차이 |
|---|---|---|
| Checkbox · Select · MenuItem | enabled, hover, focus, pressed, disabled | 기준 |
| Fab | enabled, hover, **pressed, focus**, disabled | 순서 |
| Toggle · RadioGroup · TabItem | enabled, **disabled**, hover, focus, pressed | 순서 |
| TextArea | enabled, focus, disabled, hover | 순서 |
| TextField · InputOtp | enabled, hover, focus, disabled | pressed 없음 (입력 필드라 정상) |
| Button | enabled, hover, focus, pressed, **selected**, disabled | 값 상태가 섞임 |
| Chip · ThemeSwatch | enabled, hover, pressed, disabled | **focus 없음** |
| CommandItem | enabled, hover, pressed, disabled + `Active` 축 | focus 대신 가상 포커스(`Active`) |
| NavigationBarItem | **Default**, hover, disabled | 이름·대소문자 |
| Label | **default**, disabled | 이름 |

`Show focus ring` 보유 여부도 갈린다 — `State=focus`가 있는데 불린이 없는 세트가 5개(Checkbox, Select, Fab, TabItem, InputOtp), MenuItem은 같은 이름의 불린이 **두 개** 있다.

**순서가 어긋난 이유 (코드 대조).** 플러그인에 적힌 값 순서는 이미 R1 순서다. 멤버가 64개 이하인 세트는 Generate 때 다시 정렬되지 않아서, 나중에 추가된 값이 끝에 붙은 채 남았다. Fab·Toggle·RadioGroup·TabItem·TextArea가 모두 64개 이하이고, 64개를 넘는 TextField·Checkbox·Button은 정상 순서다.

### 1-3. 상태가 엉뚱한 층에 붙은 경우

| 세트 | 현재 | 문제 |
|---|---|---|
| NavigationBar | Hover × Disabled × Focus (24) | 항목 컴포넌트 NavigationBarItem이 이미 `State`를 갖는다. 바 전체의 호버는 의미가 없다 |
| Breadcrumb · Pagination | Hover × Disabled × Focus (각 8) | 여러 항목 중 **어느 것이** 호버인지 표현할 수 없다 |
| Badge | Hover × Focused (192) | 불린 곱으로 4배가 됐다. **(코드 대조)** 다만 Badge는 `onPressed`가 있으면 누를 수 있다 — 양 플랫폼 모두 hover 채움과 포커스 링을 그린다. 비상호작용 요소가 아니다 → §8-4 |
| Table | Disabled × Hover × Selected | 호버·선택은 행 단위다. **(코드 대조)** 코드에서도 행(`rowHoverColor`·`rowSelectedColor`)과 셀(`enabled`) 단위다 |
| Dock | Disabled × Focus | 도크 항목 단위다 |

### 1-4. 이름은 상태지만 상호작용 상태가 아닌 것

| 세트 | 축 | 실제 의미 |
|---|---|---|
| Window | `Focused` | 창 활성(앞에 있는 창). 키보드 포커스가 아니다. **(코드 대조)** 코드 이름도 양 플랫폼 모두 `focused`·`isFocused`다 |
| CommandItem | `Active` | 목록의 가상 포커스(`aria-activedescendant`). 실제 포커스는 입력창에 있다 |
| FileInput | `DragOver` | 파일을 끌어다 올린 상태 |
| Skeleton | `Enabled` | **(코드 대조)** 렌더 여부다. false면 아무것도 그리지 않는다(Flutter는 빈 상자, Web은 숨김). 애니메이션 여부가 아니다. 지금 캔버스는 false도 true와 똑같이 그린다 |

### 1-5. 캔버스 조회에서 빠진 4개 (코드 대조)

| 세트 | 현재 | 문제 |
|---|---|---|
| Clickable | `State[default, focused, pressed]` + `Enabled` 불린 축 | 이름이 R1과 다르고(`default`·`focused`), 비활성이 `State` 밖 불린에 있다 |
| Swap | `State[off, on]` | 값 상태가 `State`에 들어 있다(R2) |
| Subfocus · Swiper | `Enabled` 불린 축 | R4 대상 |

이 넷을 더하면 `State` 열거형 18개, 불린 축만 있는 세트 46개다.

## 2. 무엇이 문제인가

1. **같은 뜻, 다른 이름.** 디자이너가 인스턴스를 비활성으로 바꿀 때마다 "이 컴포넌트는 Enabled를 끄는가, Disabled를 켜는가, State를 고르는가"를 확인해야 한다. 극성이 반대라 실수가 잦다.
2. **의미 없는 조합이 생긴다.** 불린 두 개는 곱이 된다. `Enabled=false × Hover=true`, `Hover=true × Focus=true`처럼 코드에서 그려질 일이 없거나 우선순위가 정의되지 않은 칸이 세트의 절반을 차지한다. Button이 2026-08에 `Enabled + Hover` 불린을 `State`로 바꾼 이유가 정확히 이것이었다.
3. **포커스를 그리는 방법이 다섯 가지.** WCAG 2.4.7 대응을 점검하려면 컴포넌트마다 다른 속성을 찾아야 한다. Checkbox가 포커스 표현 없이 남아 있던 것도 이 불일치 속에서 놓친 것이다.
4. **상태가 컨테이너에 붙어 있다.** 항목이 여러 개인 컴포넌트에서 컨테이너 단위 상태는 시안에 쓸 수 없다.

## 4. 판단

### 4-1. 다른 디자인 시스템

- **Material 3 Figma 킷**은 상호작용 상태를 `State` 한 variant 속성(Enabled · Hovered · Focused · Pressed · Disabled 등)으로 두고, 선택 여부는 `Selected` 같은 별도 속성으로 둔다. 불린 축을 곱해 상태를 만드는 공개 킷은 찾기 어렵다.
- **HTML/CSS**가 같은 구분을 한다. 상호작용 상태는 의사 클래스(`:hover`, `:focus-visible`, `:active`, `:disabled`) 한 층, 값은 속성(`checked`, `aria-selected`, `aria-expanded`) 다른 층이다.
- **Flutter `WidgetState`**는 hovered · focused · pressed · selected · disabled · error를 **집합**으로 다룬다(동시에 여러 개가 참). Figma variant는 한 번에 하나만 고를 수 있으므로, 집합을 "배타적 `State` 하나 + 가장 자주 겹치는 포커스는 불린"으로 투영하는 것이 손실이 가장 적다. CoUI의 `Show focus ring`이 바로 그 장치다.

### 4-2. 실무

- 인스턴스 패널에서 드롭다운 하나로 상태를 고른다. 불린 세 개를 조합하는 것보다 빠르고 틀릴 수 없다.
- Figma 인터랙티브 컴포넌트(While hovering → `State=hover`)가 한 속성만 바꾸면 되므로 프로토타입 연결이 단순하다.
- 변형 수가 줄어드는 곳이 많다. NavigationBar 24 → 3, Breadcrumb·Pagination 8 → 1, Badge는 §8-4 결정에 따라 줄어든다. 반대로 Slider처럼 `Enabled` 하나뿐이던 입력 컨트롤은 hover·focus가 생기며 늘어난다 — 지금까지 **그릴 수 없었던 상태**가 생기는 것이라 비용이 아니라 누락 해소다.
- **(코드 대조)** 전체 멤버 수는 순감한다 — 지금 2,476개에서 적용 후 약 2,150~2,350개. 감소의 대부분은 Button `selected` 제거(−162)와 Badge에서 나온다.

### 4-3. CoUI 내부 일관성

- 16개 컴포넌트(완료 계열 대부분)가 이미 `State[enabled, hover, focus, pressed, disabled]` + `Show focus ring`을 쓴다. 나머지를 여기에 맞추는 것이 새 규약을 만드는 것보다 작다.
- 코드 인계 문서가 이미 규정해 둔 매핑이 그대로 쓰인다 — `State`와 `Show focus ring`은 prop이 아니라 의사 클래스와 `:focus-visible`로 대응한다(`button-코드-인계.md` §7).
- 비활성 색 규칙(`disabled-census.md`)이 `State=disabled` 한 자리에만 적용되면 되므로 감사가 쉬워진다.

## 5. 규칙 (확정 후 제너레이터 계약으로 승격)

**R1. 상호작용 상태는 `State` 한 축이다.**
값은 소문자, 순서 고정 — `enabled · hover · focus · pressed · disabled`. 컴포넌트에 없는 값은 빼되 순서는 지킨다(예: 입력 필드는 `enabled · hover · focus · disabled`). `default`는 쓰지 않는다.

**R2. 값 상태는 `State`에 넣지 않는다.**
선택·체크·켜짐·열림·펼침·오류·가상 포커스는 각자 축으로 둔다 — `Selected`, `Checked`, `On`, `Open`, `Expanded`, `Error`, `Active`. Checkbox(`State` × `Checked`), Toggle(`State` × `On`), RadioGroup(`State` × `Selected`)이 이미 이 모양이다.

**R3. `State`에 `focus`가 있으면 `Show focus ring` 불린을 반드시 둔다.**
`State=focus`에서는 링이 항상 보이고, 그 외 값에서는 불린이 링과 밴드를 켠다. 9/8·9/9 문서들은 Button·Toggle·RadioGroup이 이렇게 동작한다고 기록했지만, 오늘 조회에서는 불린의 존재만 확인했고 바인딩은 보지 않았다. 규칙 확정 전에 다시 실측한다. **(코드 대조)** 플러그인은 불린이 있는 8개 세트를 이미 이렇게 생성한다 — focus 멤버는 링을 켠 채 고정하고, 나머지 멤버는 불린에 묶는다. 남은 것은 캔버스 확인이다. pressed + 포커스, disabled + 포커스(메뉴 항목) 같은 겹침을 그리기 위한 Figma 전용 장치이며 코드 prop이 아니다.

**R4. 비활성만 있는 컴포넌트도 `State`로 쓴다.**
`Enabled`/`Disabled` 불린 축은 쓰지 않는다. 최소형은 `State[enabled, disabled]`. 극성 문제는 이것으로 사라진다. **(코드 대조)** 단, 코드에 비활성 상태가 없는 세트가 있다(§6-5) — 그 세트의 `disabled`를 어떻게 할지는 §8-5.

**R5. 상호작용이 없는 컴포넌트에는 상태 축을 두지 않는다.**
누를 수 없는 표시 요소는 축을 제거한다. **(코드 대조)** 처음 예로 든 Badge는 코드에서 누를 수 있는 형태가 있어 이 규칙의 대상인지 §8-4에서 정한다.

**R6. 상태는 상호작용 단위에 둔다.**
항목을 여러 개 담는 컨테이너(NavigationBar, Breadcrumb, Pagination, Table, Dock)는 상태 축을 갖지 않고, 항목 컴포넌트가 `State`를 갖는다. 카드처럼 **전체가 한 번에 눌리는** 컨테이너는 예외로 `State`를 가질 수 있다.

**R7. 코드에는 아무것도 추가하지 않는다.**
코드의 공개 API는 `enabled`(또는 `disabled`) prop과 런타임 상태다. `State`는 Figma에서 그 조합을 미리 보여주는 축이다. 이 매핑은 제너레이터가 한다.
**(코드 대조)** 이 규칙은 축 이름과 구조를 통일하는 일에 대한 것이다. 계열 리디자인에서 **새 상태 그림**(지금 코드에 없는 hover 색 · disabled 색 등)을 정하면, 그 값은 코드 계약에 들어가야 캔버스에 남는다 — 캔버스는 코드에서 다시 그려지기 때문이다. 어느 세트가 여기에 해당하는지는 §6-5.

## 6. 적용 — 무엇이 어떻게 바뀌나

### 6-1. 이미 `State`가 있는 세트 — 정리만

| 세트 | 조치 | 규칙 |
|---|---|---|
| Fab · Toggle · RadioGroup · TabItem · TextArea | 값 순서 정렬. **(코드 대조)** 플러그인이 작은 세트도 다시 정렬하게 고치면 한 번에 된다(§1-2) | R1 |
| NavigationBarItem | `Default` → `enabled`, 순서 정렬. **(코드 대조)** 코드에는 focus·pressed 그림 값도 있어 채울 수 있다. NavigationBar가 이 항목을 `State=Default` 이름으로 불러 쓰므로 두 세트를 함께 바꾼다 | R1 |
| Label | `default` → `enabled` | R1 |
| Clickable **(코드 대조)** | `default` → `enabled`, `focused` → `focus`, `Enabled` 불린 → `State`의 `disabled` | R1 · R4 |
| Swap **(코드 대조)** | `State[off, on]`은 값 상태 → 값 상태 축으로 옮긴다(`On` 등) | R2 |

R3를 권고하는 근거는 문서가 아니라 실무다 — pressed + 포커스, disabled + 포커스(메뉴 항목)는 `State` 하나로 그릴 수 없다.

### 6-3. 순서

1. 이 문서의 R1~R7 확정
2. **Claude Code: 공용 규칙과 검사를 먼저 넣는다** — 값 순서, `Show focus ring`, `State` 축을 만드는 공용 헬퍼와, 규칙 위반을 잡는 CI 검사. **(코드 대조)** 이것만으로 기존 세트가 규칙을 따르게 되지는 않는다. 상태 축은 세트마다 플러그인에 따로 적혀 있어서, 각 세트는 자기 차례에 그 세트의 전환과 변형 개명표를 함께 넣어야 바뀐다. 개명표 없이 축이 바뀌면 Generate가 그 세트를 거부한다
3. 6-1의 정리는 영향이 작으므로 한 번에 처리 가능
4. 6-2는 인벤토리의 작업 순서(wave)대로, 각 계열을 리디자인할 때 함께 바꾼다. **축 변경만 먼저 따로 돌리지 않는다** — 같은 세트를 두 번 흔들면 ⇄ 비교와 인스턴스 오버라이드가 두 번 깨진다

**비용 (코드 대조).** 플러그인 코드가 한 줄만 바뀌어도 모든 세트가 다시 그려진다(약 33분, 2026-09-28 실측). 그래서 2단계·3단계·각 wave가 각각 전체 재생성 한 번이다. 이 재생성에서는 손 편집 보존이 동작하지 않으므로, 적용 기간의 디자인 작업은 ⌘D 사본에서만 한다.

### 6-4. 안전장치

- 축 이름이 바뀌면 ⇄ 플러그인이 변형을 짝지을 수 없다. PR 본문에 **구 변형 → 신 변형 매핑표**(예: `Enabled=false` → `State=disabled`)를 붙이는 것을 규칙으로 한다. **(코드 대조)** 같은 매핑이 플러그인의 변형 개명표에도 행으로 들어가야 Generate가 통과한다. 그리고 개명은 원본 세트에만 적용되고 `(리디자인)` 사본에는 적용되지 않는다 — 사본에는 **새 축 이름**을 쓰고, ⇄가 개명표를 읽도록 플러그인을 고친다
- 파일 안에서 해당 세트를 쓰는 인스턴스의 오버라이드가 초기화될 수 있다. 재생성 전 소비처 목록을 뽑아 PR에 적는다
- **(코드 대조)** 이름만 바뀌는 변형은 유니북 인스턴스의 연결이 유지된다(설계상 — 실측 기록은 없어 첫 계열 전에 시험 파일로 확인한다). 합쳐지거나 없어지는 변형은 연결이 끊긴다 — 예: `Hover=true × Focus=true` 모서리, Button `selected` 162멤버. 이런 변형이 있는 계열은 **라이브러리 게시 전에** 유니북 인스턴스를 살아남을 변형으로 옮긴다
- **(코드 대조)** 라이브러리 게시는 지금 협업 절차의 "반영 조건"에 없다. 이 규칙을 적용하기 전에 협업 문서에 게시 단계를 넣는다

## 7. Claude Code 확인 결과 (2026-09-30 코드 대조)

1. **공개 API 영향.** `State` 축은 코드에서 파생되지 않는다 — 세트마다 플러그인에 값 목록이 적혀 있고, Button의 6값도 그렇다. 축 이름만 바꾸는 일이라면 Dart 공개 API 변경은 필요 없다. 다만 "제너레이터 규칙 하나로 44개"가 아니라, 공용 헬퍼를 만들고 각 세트를 자기 차례에 옮기는 일이다(§6-3). 인계 문서의 "breaking"은 둘이 다르다 — Checkbox는 코드 API 변경(`state` → `checked`)이었고, RadioGroup은 코드 표면은 그대로 두고 Figma 축만 바꾼 것이다
2. **값 순서 고정.** 강제할 수 있다. 플러그인에 적힌 순서는 이미 R1 순서이고, 캔버스 순서가 어긋난 것은 작은 세트를 다시 정렬하지 않기 때문이다(§1-2). 순서 검사와 작은 세트 재정렬을 함께 넣으면 된다
3. **R3 자동화.** 링과 밴드를 그리는 부품은 이미 공유돼 있다. 그러나 "`focus`가 있으면 불린을 둔다"는 규칙은 없고, 불린을 정의하는 코드가 8곳에 복사돼 있다 — 공용 규칙으로 모을 수 있다. MenuItem의 중복 불린은 플러그인이 만들 수 없는 형태다(§6-1)
4. **R6 컨테이너 축 제거.** Figma 축만 빼면 된다. 대상 컨테이너 모두 코드 계약에 `enabled`가 없어서 코드 prop을 없앨 일이 없다. 다만 NavigationBar는 NavigationBarItem을 `State=Default` 이름으로 불러 쓰므로 두 세트를 함께 바꿔야 한다
