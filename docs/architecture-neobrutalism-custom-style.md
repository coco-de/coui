# Architecture — Neo-brutalism 커스텀 스타일

상위: `tech-spec-neobrutalism-custom-style.md`
이 문서는 **미결 O3 · O4 를 닫고**, 축이 어디에 앉는지를 그림으로 고정한다.

---

## 1. 축의 자리 — seat 은 늘지 않는다

```
앱                    CoUI core                         플랫폼
─────────────────────────────────────────────────────────────────────
PrimitiveColors ──┐
                  ├─→ resolveThemeScheme ─→ CoreColorScheme ─→ 컴포넌트
CoreSurfaceStyleId┤        ↑                                    (축을 모름)
                  │        │
CoreSurfaceTuning ┴─→ applyTo(recipe) ─→ CoreSurfaceRecipe
                           │                    │
                           │                    └─→ resolveThemeGeometry
                           │                             │
                           │              Flutter: ThemeData.geometry
                           │              Web:     [data-coui-style]{--coui-*}
                           ↓
                    (단일 출처 — Flutter/Web 이 같은 함수를 부른다)
```

`CoreSurfaceTuning` 은 **7번째 자리가 아니다**. 축이 이미 앉아 있는 seat 이 읽는 *값*을 바꿀 뿐이고, merge chain 에 레벨을 끼우지도 `CoreXxxTheme` 에 슬롯을 더하지도 않는다(게이트 G6). 컴포넌트는 여전히 튜닝의 존재를 모른다.

**핵심 불변식**: 튜닝을 레시피로 접는 함수는 `applyTo` 하나다. 두 플랫폼이 각자 접으면 같은 입력에 다른 화면이 나오고, 그 divergence 는 나란히 놓고 보기 전까지 안 보인다.

## 2. O3 — docs_site 는 이 기능을 어떻게 보여주는가

**문제**: D1 이 튜닝을 빌드타임 1회로 못 박았으므로 앱 API 로는 라이브 커스터마이저를 만들 수 없다. 그런데 레퍼런스 사이트의 설득력은 정확히 그 라이브 데모에서 나온다.

**결론: docs 는 라이브 데모를 가질 수 있고, 그건 앱 API 를 여는 것과 다른 일이다.**

Web transport 가 이미 CSS 커스텀 프로퍼티다. `[data-coui-style="neo-brutalism"]{--coui-radius-4:…; --coui-control-shadow-offset-x:…}` 는 `:root` 에 앉지만, 커스텀 프로퍼티는 **상속**되므로 프리뷰 컨테이너 하나에 인라인으로 같은 변수를 덮으면 그 서브트리만 다른 튜닝으로 렌더된다:

```html
<div class="preview" style="--coui-radius-4:0px; --coui-control-shadow-offset-x:6px; …">
```

- 새 Dart transport 0. 라이브러리 API 표면 변화 0.
- 슬라이더 핸들러는 사이드바 스크롤·테마 토글이 이미 쓰는 **인라인 스크립트** 자리에 붙는다(이 사이트는 정적 렌더라 컴포넌트의 `events:` 는 브라우저에 도달하지 않는다).

**이건 docs 의 능력이지 앱의 API 가 아니다.** 문서가 그 차이를 명시해야 한다 — 데모를 보고 "앱에서도 런타임에 바뀌겠구나" 로 읽히면 D1 이 무의미해진다. 가이드는 코드 예제로 **빌드타임 API** 를 가르치고, 라이브 위젯에는 "이 페이지의 데모는 CSS 변수를 직접 덮는다" 를 적는다.

**Flutter 쪽 대칭**: Flutter 는 리빌드가 자연스러우므로 프리뷰가 `surfaceTuning` 을 state 로 들고 재빌드하면 된다 — Web 의 인라인 변수와 다른 메커니즘이지만 같은 capability 다(플랫폼 idiom 비대칭 허용 범위).

## 3. O4 — 수용 게이트 G4 의 세 번째 경로

현재 G4 는 프리셋을 둘 중 하나로 분류한다: 시맨틱 토큰을 그대로 쓰거나(`_kPresetsReusingBasePalette`), 자기 스킴을 등록하거나(`_presetSchemes()`).

**자유 파라미터를 가진 프리셋은 둘 다 못 한다.** 등록할 스킴이 앱마다 달라지기 때문이다. 게이트에 세 번째 분류를 추가한다:

> **자유 파라미터로 색을 굽히면** → 그 파라미터의 **전 범위를 훑는 sweep** 을 등록한다. 파라미터가 묶인 크기 안에서, 자유 축(hue 등)의 **최악값**이 임계를 넘는 것을 CI 가 증명한다. 스킴 하나를 등록하는 것으로는 이 프리셋을 덮을 수 없다 — 등록된 조합만 안전하고 앱이 고른 조합은 감사되지 않기 때문이다.

**왜 이게 완화가 아니라 강화인가**: 등록은 "우리가 고른 조합 하나가 안전하다" 를 말하고 sweep 은 "이 범위 안 어떤 조합도 안전하다" 를 말한다. 후자가 더 강한 진술이다. 대신 **크기를 묶을 수 없는 축은 이 경로를 쓸 수 없다** — 무한 범위는 훑을 수 없으므로, 그런 축은 애초에 앱에 열지 않는다.

`_checkPresetCoverage` 는 이 분류를 강제하도록 확장된다: 자유 파라미터를 선언한 프리셋이 sweep 없이 통과하면 실패.

## 4. 컴포넌트 파리티에 미치는 영향

**없어야 한다.** 튜닝은 컴포넌트 코드를 건드리지 않고, 튜닝하지 않은 앱은 identity 경로를 지난다(`applyTo` 가 레시피 자신을 반환).

패리티 캡처 매트릭스는 **튜닝하지 않은 프리셋**으로 계속 돈다. 튜닝된 조합을 매트릭스에 넣지 않는 이유는, 그 조합이 CoUI 가 출하하는 화면이 아니라 앱이 고른 화면이기 때문이다 — 매트릭스가 검증하는 것은 "CoUI 가 그리는 것이 두 플랫폼에서 같은가" 이고, 튜닝의 파리티는 §8 매핑의 되읽기 테스트가 본다.

베이스라인이 움직이면 그건 새 기능이 아니라 **identity 경로 누수**다.

## 5. 무엇이 이 설계를 틀리게 만들 수 있나

| 가정 | 깨지면 |
|---|---|
| 커스텀 프로퍼티가 프리뷰 서브트리에 상속된다 | O3 의 라이브 데모가 불가 → 정적 증거로 후퇴 (기능 자체는 무관) |
| `C_max` > 0 | W2 미착수 (D8 이 이미 격리) |
| 앱이 프리셋당 튜닝 하나만 필요로 한다 | 스타일별 튜닝 맵이 필요 — `ThemeConfig(surfaceTunings: {id: tuning})` 이 이미 맵이라 열려 있다 |
| 컴포넌트가 축을 모른다 | 어떤 컴포넌트가 튜닝을 읽어 분기하는 순간 그 컴포넌트만 지원되고 나머지는 조용히 빠진다 (게이트 G6 이 막는다) |
