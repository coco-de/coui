# Socratic Discovery: style-chain-showcase

- 일자: 2026-08-07
- 방식: 내부 DX 기능이므로 사용자 5단계 인터뷰 대신 **코드 실측 + 룰 정본 + 사용자 기결정(A1)** 으로 답을 채우는 압축 인터뷰. 사용자에게 되물은 것은 범위 해석 1건(A1)뿐이며, 나머지 판단은 근거와 함께 `docs/decision-log-style-chain-showcase.md` 에 기록 — 게이트에서 일괄 검토 가능.

## Q-트리 1: "예시가 부족하다"의 정확한 의미는?

- **Q1. 무엇이 부족한가 — API 인가 문서인가?** → 문서다. API 는 이미 완비: Flutter 131개 파일 `withStyle`, 컴포넌트당 getter ~30개(radius 19 + 색 11), Web 완전 대칭(`coui_web .../button.dart:442-671` ↔ `coui_flutter .../button.dart:595-788`).
  - **Q1a. 문서의 어디가 부족한가?** → md 산문(120개 문서 동일 보일러플레이트 1문단 + getter 1개 예시) **그리고** 프리뷰(chain 예제 119개 존재하나 내용 최소 + `kDocsChainPreviewMode = hidden` 으로 비노출).
    - **Q1b. 그럼 "반영"의 최소 단위는?** → ① chain 예제 내용 확충 ② 노출 모드 전환 ③ md 산문 교체. 셋 중 하나만 하면 반쪽(내용 없이 노출 = 빈약한 갤러리, 노출 없이 내용 = 아무도 못 봄).
      - **Q1c. "모든 스타일 옵션"은 문자 그대로인가?** → 사용자 확인 완료(A1): **계열 대표 + full-control**. getter 전수(30개)·필드 전수(39개) 나열은 비채택. 나머지 조합 탐색은 랜덤 토글(B)의 몫 — 두 파트가 상호보완이 되도록 역할 분담.

## Q-트리 2: "랜덤 토글"은 무엇을 랜덤하게 하는가?

- **Q2. 랜덤의 대상은 값인가 토큰인가?** → 사용자 원문이 "옵션별 **토큰** 변경" — 토큰이다. 임의 값(슬라이더류)이 아님. 이 구분이 spike-3592 봉쇄(임의 값 transport 부재로 착수 보류)와 본 건을 가르는 경계.
  - **Q2a. 어떤 토큰 축인가?** → 컴포넌트 공통 uniform 표면인 primitive getter 축(radius 19 × 색 11)이 유일하게 "전 컴포넌트 × 양 플랫폼"에서 저작 0으로 성립하는 축. full-control 필드 축은 컴포넌트마다 다르고(39필드) 순열 폭발 + per-component 저작 필요 → v1 제외 (D3).
    - **Q2b. 랜덤이면 재현이 안 되는데 "비주얼 테스트"가 되는가?** → 결정적 seed 셔플이면 둘 다 만족: 사용자 체감은 랜덤, 시퀀스는 재현 가능 (D4).
      - **Q2c. "코드와 비주얼 동시"는 어느 코드인가?** → 코드 패널(Web/Flutter 탭 모두)이 현재 순열의 체인 코드를 표시해야 함. getter 체인은 규칙적(`.radiusN.colorX`)이라 순열→코드 문자열이 결정적으로 파생됨 — 손 저작 스니펫 불필요.
        - **Q2d. 두 프리뷰가 다른 순열을 보이면?** → 이 도구의 존재 이유(파리티 시각 증명) 부정 — 동시성·동일성이 하드 요구(REQ-B7). spike-3592 §6 "반쪽 구현은 핵심 가치를 부정"과 동일 논리.

## Q-트리 3: 순열은 어떻게 두 플랫폼에 도달하는가? (기술 전제)

- **Q3. Flutter 프리뷰는 런타임에 순열을 받을 수 있는가?** → 현재는 불가: `FlutterPreview`(`docs_site/lib/components/flutter_preview.dart:30-55`)는 hydration 시점에 `PreviewApp(component, variant)` 를 고정 생성. 런타임 전달 경로는 신규 배선 필요 — **이 스펙의 기술 리스크 1순위(R1)**.
  - **Q3a. 신규 배선은 spike-3592 가 막은 그 작업 아닌가?** → 아니다. 스파이크가 막은 것은 "임의 `CoreColorScheme`(62슬롯 구조체) 값을 나르는 채널". 본 건이 나를 것은 **순열 식별자(문자열/인덱스)** — 기존 채널이 이미 나르는 bool/enum/variant 문자열과 같은 급. 후보 경로: 순열 식별자를 기존 variant 문자열 채널에 인코딩(전 배선 시그니처 무변경) — Design 단계 확정 (D6).
    - **Q3b. 순열 적용은 누가 하는가?** → getter 는 컴포넌트 타입에 붙어 있으므로(무공통 supertype) **chain 예제 내부**가 순열 식별자를 해석해 자기 컴포넌트에 체인을 적용해야 함. 예제가 순열-인지(parameterized) 형태가 되어야 한다는 뜻 — REQ-A1 확충과 REQ-B 가 같은 파일을 만지므로 같은 Epic 에 있어야 함.

## Q-트리 4: 범위 경계

- **Q4. docs_app(네이티브)도 v1 인가?** → 순열 로직은 순수 Dart 공유 위치에 두되(REQ-B4), 랜덤 버튼 UI 는 v1 docs_site 만 (D5 — 스코프 봉쇄, Level 2).
- **Q5. Style 슬롯 없는 컴포넌트(withStyle 미언급 19개 md)는?** → 대상 제외가 정당 — withStyle 체인은 `CoreXxxStyle` 슬롯 + `merge` 보유 컴포넌트 한정(룰 `cross-platform/api.md`). 단 "Style 슬롯 있는데 chain 예제 없는" 역방향 갭은 조사·보충 (REQ-A5).
- **Q6. 노출 모드는 appended 인가 only 인가?** → appended (D2) — only 는 md 선언 variant 갤러리를 치환해 기존 문서 가치를 파괴.
