# Figma 플러그인 — 코드 변경을 캔버스까지 보내기

[가이드 목차](README.md) · 이전: [검증](verification.md) · 다음: [업그레이드](upgrading.md)

**export → build → Import → Generate는 서로 다른 단계입니다.**
`melos run figma:sync`가 성공해도 Figma의 열린 문서를 자동 수정하지는 않습니다.

## 디자인 변경을 받을 때

디자인 변경은 리디자인 이슈로 받습니다. 역할과 단계, 이슈 · PR 템플릿,
캔버스 확인 요청 형식은 [디자이너 · 개발자 협업](design-collaboration.md)에 있습니다.
어느 결정을 어떤 컴포넌트에 반영하는지 먼저 연결합니다.
canvas의 그림과 대조 리포트는 의도를 확인하는 자료이고, 그 자체가 코드에
반영됐다는 증거는 아닙니다. 코드 머지 → 그 코드로 재생성 → Web/Flutter
대조 → 디자인 측 확인의 완료 조건은
[협업 가이드의 검수 항목](design-collaboration.md#7-검수--누가-무엇을)에서 확인합니다.
아래의 소비자용 토큰 내보내기는 이 CoUI 계약 반영 절차와 별도입니다.

## 먼저 준비할 것

- [Dart workspace 설치](getting-started.md)와 Node.js 24, npm이 필요합니다.
  빌드 명령과 의존성은 [플러그인 안내](../../tools/figma-token-sync/README.md)와
  [package-lock.json](../../tools/figma-token-sync/package-lock.json)을 따릅니다.
- Figma Desktop과 대상 파일 편집 권한. 개발용 plugin을 import할 수 있어야 합니다.
- **Pretendard의 정적 9 weight(Thin–Black)**를 OS에 설치합니다. 저장소의
  [OTF 폰트](../../docs_site/fonts/)를 사용할 수 있습니다. variable font 하나로
  대체하지 않습니다. 폰트가 빠지면 Generate가 오류를 냅니다.
- **Geist Mono Regular**도 OS에 설치합니다. 플러그인이 읽는 Geist Mono
  굵기는 코드 역할이 진술하는 굵기(지금은 모두 400)와 문서 코드 블록의
  Regular뿐이라, 다른 굵기는 없어도 됩니다. 저장소의
  [GeistMono OTF](../../docs_site/fonts/)(`GeistMono-Regular.otf`)가 코드가
  번들한 것과 같은 판입니다. 이 폰트는 빠져도
  실행이 멈추지 않아 놓치기 쉽습니다. Import는 `Code/*` 텍스트 스타일을
  만들거나 갱신하지 못하고 로그에 `! text style "Code/…"` 줄과 실패 수를
  남깁니다. Generate는 코드 라벨을 Pretendard로 그리고 실행 로그에 한 줄
  남깁니다. 캔버스의 코드가 본문 서체로 보이면 먼저 이 설치를 확인합니다.
- 여러 페이지와 variable mode를 지원하는 Figma 플랜. Starter의 페이지
  제한으로 전체 라이브러리를 만들 수 없습니다. 소비 프로젝트의 Extended
  Variable Collection 은 Figma 가 **Enterprise** 기능으로 안내하지만 Organization
  플랜 파일에서도 만들어졌습니다. 플러그인은 플랜을 미리 판정하지 않고, Figma 가
  거부하면 그 이유를 알립니다.
- 처음에는 실습용 파일에서 확인합니다. 리디자인 반영(대조 · 컴포넌트 반영)은
  정본 파일에서만 돌리고 Figma 브랜치는 쓰지 않습니다
  ([디자이너 · 개발자 협업](design-collaboration.md) 3장). 정본
  라이브러리 위치는 [figma_library.json](../../docs_core/content/_data/figma_library.json)에서 확인합니다.

## 1. export와 bundle build

**저장소 루트**, workspace 의존성 설치 후 실행합니다.

```bash
melos run figma:install
melos run figma:sync
```

예상 결과와 각 단계는 다음과 같습니다.

| 명령 | 읽는 것 | 만드는 것 |
|---|---|---|
| `figma:install` | 플러그인 lockfile | `node_modules` (`npm ci`) |
| `export:figma-tokens` | Core 토큰·팔레트·라이브러리 메타데이터·코드 브랜드 | 루트 `build/tokens.figma.json` + 추적하는 `tools/figma-token-sync/src/data/brands.json`(브랜드 값 표) |
| `export:figma-components` | Core Style/Contract 등 exporter 입력 | `tools/figma-token-sync/src/data/components.json` |
| `figma:build` | `code.ts`, `src/`, 생성 데이터 | `tools/figma-token-sync/code.js` |
| `figma:sync` | 위 두 exporter와 build 순차 실행 | 토큰 JSON + 컴포넌트 JSON + bundle |

`components.json`과 `brands.json`은 추적하는 생성 파일입니다. 원본 수정 뒤 재생성하고 diff를
검토해 커밋합니다. `brands.json`은 코드 브랜드가 라이브러리의 색과 다른 값만 담은 표로, 소비 파일의
브랜드 확장 컬렉션을 채우는 데 쓰입니다(플러그인 README의 "브랜드 확장 컬렉션"). JSON이나 `code.js`를 직접 고쳐도 다음 생성이 덮어씁니다.

TypeScript만 바꾸는 반복 작업에는 `figma:watch`를 사용할 수 있습니다.
다만 Core 변경은 별도 export가 필요하고, watch 시작 시 계산되는 해시/빌드
신원도 있으므로 최종 검증 전에는 watch를 종료하고 `figma:sync`로 완성본을 만듭니다.

## 2. 내 checkout의 플러그인 연결

Figma Desktop에서 **Plugins → Development → Import plugin from manifest…**를
선택하고, 이번 checkout의 `tools/figma-token-sync/manifest.json`을 엽니다.
메뉴 표기는 Figma 버전에 따라 조금 다를 수 있습니다.

플러그인이 이미 열려 있었다면 닫았다가 다시 실행해 새 bundle을 읽게 합니다.
빌드 identity의 브랜치/커밋이 이번 작업과 맞는지 확인하세요. 다른 checkout의
manifest를 연결해 두면 이 폴더를 빌드해도 그 플러그인은 바뀌지 않습니다.

## 3. Import to Variables

플러그인의 토큰 입력에서 **루트 `build/tokens.figma.json`**을 파일로 선택하거나
내용을 붙여넣고 **Import to Variables**를 실행합니다. `components.json`과 `brands.json`은
여기에 넣는 파일이 아닙니다. 그 데이터는 bundle 안에 들어 있습니다.

예상 결과: 토큰 컬렉션·변수 및 역할별 텍스트 스타일이 생성/갱신됩니다.
이름과 의미는 exporter가 내보낸 현재 데이터가 기준입니다. Import 오류가
있으면 Generate 전에 해결합니다.

## 4. Generate Components

같은 대상 문서에서 **Generate Components**를 실행합니다. 초기 파일은
전체 생성으로 준비하고, 이후에는 UI의 섹션 범위 선택으로 확인 범위를 줄일
수 있습니다. 합성 자식과 의존 관계도 함께 확인합니다.

예상 결과: `❖ Badge` 같은 컴포넌트 페이지와 변형 세트가 나타납니다.
로그의 built/skipped/failed를 읽습니다. 코드 변경이 없어서 skipped인 것과
실패해서 생성되지 않은 것을 구별하세요. **낡은 세트 보기**는 아직 옛 build로
남은 세트를 찾을 때 사용합니다.

플러그인은 **지금 열려 있는 문서**를 대상으로 합니다. 정본 식별자는 안내를
돕지만 다른 파일 실행을 무조건 막아주는 장치가 아닙니다.

## 5. 실제 Figma에서 검증

- 변경한 Variant/Size/State/Enabled와 컴포넌트 고유 축을 전환합니다.
- 색·치수의 variable binding, 텍스트 역할/스타일, Light/Dark를 확인합니다.
- **인스턴스**를 만들고 가로·세로를 늘려 자식, 보더, 미디어, 간격이 따라오는지
  확인합니다. 아이콘/버튼처럼 고정 크기여야 하는 자식을 무조건 늘리지는 않습니다.
- 재실행 후 기존 인스턴스 연결과 component id/key가 유지되는지 확인합니다.
- 다른 페이지의 인스턴스에서 안쪽 레이어(아이콘 색, 글자 색)를 덮어쓴 뒤 그 세트를
  다시 반영해 덮어쓰기가 남는지 봅니다. 반영은 멤버의 안쪽 노드를 지우지 않고
  유지하므로 남아야 하고, 유지하지 못한 레이어는 로그의 `kept N / replaced M` ·
  `↺` 줄에 교체로 세어집니다(`tools/figma-token-sync/README.md` 의 "다시 그려도
  안쪽 노드를 유지한다").
- 필요하면 **Verify identity idempotence** / **Verify reset completeness**를
  사용합니다. 동작과 비용은 [플러그인 레퍼런스](../../tools/figma-token-sync/README.md)에 있습니다.

`figma:check`의 test double에는 실제 Figma layout engine이 없습니다.
`audit:layout` 출력이나 selftest 통과만으로 리사이즈 검증을 대신하지 마세요.
[레이아웃 감사](../../tools/figma-token-sync/LAYOUT_AUDIT.md)가 실제 측정 예시입니다.

## 어떤 소스를 고치나요?

| 문제 | 위치 |
|---|---|
| 공유 기본값 자체가 틀림 | Core Style/토큰 |
| Core 필드가 JSON에 안 나옴 | `packages/coui_core/bin/figma_reader/` |
| JSON 값은 맞지만 Figma 배치가 틀림 | `src/components/*.ts`의 builder |
| 여러 builder의 공통 배치/바인딩 문제 | `src/helpers.ts` 등 공통 helper |
| 컴포넌트 누락·합성 순서 | `src/registry.ts`와 section registry 배열의 `needs` |
| 이름 변경 후 기존 연결 유지 | `src/renames.ts`와 identity 검증 |

Figma 인스턴스를 detach해 오류를 숨기기보다 원본 builder를 고쳐 재생성합니다.
디자이너의 손 편집은 별도 리디자인 자료로 보존하고, 그 의도를 코드에 반영합니다.

## 빈 슬롯의 대역

계약에서 `W` / `W?`로 선언된 슬롯(`child`, `leading`, `media`처럼 아무 위젯이나
받는 슬롯)은 Figma에서 **교체 속성(INSTANCE_SWAP)**으로만 나타낼 수 있습니다.
텍스트 속성이나 불린으로는 "어떤 컴포넌트든 들어온다"를 말할 수 없습니다.
그런데 교체 속성은 **기본값이 컴포넌트여야** 선언됩니다. 기본값 없는 교체
속성은 Figma가 받지 않습니다. 그래서 builder는 슬롯 자리에 컴포넌트 하나의
인스턴스를 그려 두고, 교체 속성의 기본값을 그 인스턴스가 그리는 멤버로
둡니다. 그 컴포넌트가 빌더 전용 대역 `.Slot`입니다.

- **빈 자리를 표시할 뿐입니다.** `.Slot`은 채움 없는 점선 외곽선입니다. "호출자가
  넘기는 위젯이 이 자리에 온다"만 말하고, 무엇이 올지는 주장하지 않습니다.
  디자이너가 인스턴스에서 실제 컴포넌트로 교체하는 출발점입니다. 채운 상자는
  내용이나 로딩 상태로 읽히므로 슬롯 표시에 사용하지 않습니다.
- **라이브러리에 게시되지 않습니다.** 이름 앞의 `.`은 Figma에서 "게시하지 않음"
  입니다. 소비 파일의 에셋 패널에는 나타나지 않고, 이 파일의 슬롯 기본값으로만
  쓰입니다.
- **생김새.** `Shape` 축이 두 칸입니다 — `rectangle`(모서리 0)과 `circle`(모서리
  full). 외곽선은 `outline` 색, `stroke-width/1` 두께, 안쪽 정렬이고, 점선 간격은
  디자인 시스템의 점선 리듬(`CoreDashedBorder`, 3 on / 2 off)을 따릅니다. 멤버
  상자(160×40 · 40×40)는 미리보기 크기이고, 대부분의 슬롯은 builder가 크기를
  정합니다(채우기 · 고정 상자 · 배율).
- **계약이 없는 세트입니다.** `.Slot`은 coui_core에 대응하는 컴포넌트가 없어
  components.json 레코드도, 문서 프레임도, 충실도 대조도 없습니다. REGISTRY
  항목의 `fixture` 표시가 그 사실을 말하고, 그리는 값은 `fixture.checkedBy`가
  가리키는 셀프테스트(`slot fixture drill`)가 단언합니다.
  `check_figma_registry_parity.sh`는 `.`으로 시작하는 이름과 `fixture` 표시가
  짝을 이루는지 봅니다.
- **대부분 기본 숨김입니다.** `W?` 슬롯은 호출자가 넘기지 않으면 `null`인 것이
  위젯 기본값입니다. 그래서 인스턴스를 감싼 홀더 프레임에 `Show <슬롯>` 불린을
  걸고 대부분 꺼 둡니다. 보이는 자리는 불린 없이 늘 그려지는 필수 슬롯(`W`)이거나,
  그 슬롯이 있어야 미리보기가 그 컴포넌트로 읽히는 곳(Clickable 같은 래퍼의
  `child`, Scaffold의 `sidebar`)입니다.
- **인스턴스 이름은 슬롯 이름입니다.** 대역 인스턴스는 대역 컴포넌트의 이름
  (`.Slot`)으로 남지 않습니다. 레이어 패널에서 그 이름은 슬롯이 아니라 컴포넌트의
  내용처럼 읽히기 때문입니다.
  - 인스턴스가 곧 슬롯 자리이면 슬롯 이름을 씁니다. 예: `child`, `children[0]`.
  - 홀더 프레임이 감싸면 홀더가 슬롯 이름이고, 인스턴스는 `<슬롯> content`
    입니다. 홀더에 `Show <슬롯>` 불린이 걸렸는지와는 무관합니다 — Overlay 의
    필수 슬롯처럼 불린 없이 홀더만 있는 곳도 같습니다. 예: `leading` 안의 `leading content`. Popover ·
    HoverCard의 `trigger`, ContextMenu의 `child`처럼 기본값이 대역이 아닌
    슬롯도 같은 이름을 씁니다.
  - 슬롯이 아닌 대역은 대역하는 대상의 이름을 씁니다. 예: Drawer 뒤의 앱 화면은
    `app content`입니다.

대역 지정은 `tools/figma-token-sync/src/slot-stand-in.ts` 한 곳에 있습니다.
builder는 `slotStandIn` · `slotStandInDefault`로 인스턴스와 교체 기본값을 받고,
슬롯 종류(`rectangular` · `text` · `circular`)만 고릅니다. `rectangular` ·
`circular`는 `Shape=rectangle` · `Shape=circle`이고, `text`는 `rectangle`
인스턴스를 문단 상자(200×64 — 16px 세 줄, 줄 사이 8)로 맞춥니다. 크기를 정하지
않는 슬롯도 자리 크기가 문단 하나만큼 남습니다. 대역 컴포넌트 이름은
`kSlotStandInComponent` 상수 하나이고, 대역을 쓰는 REGISTRY 항목은 그 상수를
`needs`에 둡니다.

**이미 문서에 있는 교체 기본값.** builder는 INSTANCE_SWAP 속성을 다시 선언할 때
기본값을 다시 쓰지 않습니다(`component-props.ts`의 `defineProp`). 기본값은 노드
id라 문서마다 다르고, 디자이너가 일부러 다른 컴포넌트를 골라 두었을 수 있기
때문입니다. 예외는 builder가 스스로 기본값을 바꾼 경우 하나입니다.
`slotStandInDefault`는 새 기본값(`.Slot` 멤버)과 함께 **그 슬롯 종류에 builder가
넣던 바로 그 `Skeleton` 멤버 id**를 넘깁니다. 기존 기본값이 정확히 그 id이면
builder 말고는 아무도 고르지 않은 것이므로 `.Slot`으로 옮깁니다. 다른 값이면
builder가 넣은 값이 아니므로 그대로 두고, Generate 로그에
`ℹ <세트>: 교체 기본값 유지(빌더가 넣던 값이 아님) — <속성> → <컴포넌트>`로
남깁니다. 기본값이 문서에 없는 노드를 가리키면 `<id>(문서에 없는 노드)`로 적습니다. 기본값이
옮겨지면 그 세트를 쓰는 인스턴스 중 교체를 덮어쓰지 않은 것은 새 기본값을 따라가고,
디자이너가 교체해 둔 인스턴스는 그대로입니다(시험 파일 실측). 부분 실행도 `Skeleton`
페이지를 함께 로드해서, 이전 기본값을 찾지 못해 조용히 건너뛰는 일이 없습니다.

이 이전은 **속성마다 한 번**입니다. 속성을 처음 본 실행이 이전 여부를 정하고 세트에
표시(플러그인 데이터 `coui-swap-adopted:<속성>`)를 남기며, 그 뒤로는 `replaces`를
읽지 않습니다. `Skeleton`은 이제 실제 컴포넌트라 디자이너가 슬롯을 일부러 그
멤버로 두었을 수 있고, 그 선택을 다음 Generate가 되돌리면 안 되기 때문입니다.
builder가 처음부터 속성을 만든 세트와 옛 기본값이 없던 문서도 첫 실행에서 표시가
남아 같습니다.

`.Slot`은 자기 레코드가 없지만 `Frame`의 점선 리듬을 읽어 그립니다. 그래서 REGISTRY
항목이 `fixture.dataFrom: ['frame']`로 읽는 레코드를 밝히고, 세트 내용 해시가 그
레코드를 함께 해시합니다 — 점선 리듬이 바뀌면 `.Slot`도 낡은 세트로 잡혀 다시
그려집니다. `figma_registry_names.py --fixture-faults`는 `dataFrom` 이름이
components.json의 레코드인지 확인합니다(오타는 `null`로 해시되어 조용히 지나갑니다).

`npm run selftest:registry-runtime`의 slot stand-in name drill이 모든 builder를
돌려 대역 인스턴스가 대역 컴포넌트 이름으로 남은 곳이 없는지 확인하고, slot
fixture drill이 `.Slot`의 외곽선 · 점선 · 모양 · 상자, 문단 상자, 기본값 이전
규칙(한 번만 옮기고, 디자이너가 되돌려 둔 값은 건드리지 않음), 점선 레코드가 바뀌면
해시가 따라 움직이는지를 확인합니다.

## 손 편집과 역방향 경로

일반 Generate는 기존 영속 세트를 제자리에서 갱신합니다. 손 편집 보존 기능도
있지만 **모든 과거 편집을 무조건 복구하는 보장**은 아닙니다. 지문/빌드 신원
조건과 보존본/백업의 차이는 [플러그인 README](../../tools/figma-token-sync/README.md)의
“손 편집 보존 + 리디자인 대조”를 먼저 읽습니다. 삭제·retired 정리는 별도
opt-in/dry-run 경로로 다룹니다.

| 경로 | 결과 | 자동 코드 수정인가? |
|---|---|---|
| 구조/충실도/리디자인 대조 JSON | canvas와 코드의 차이를 리뷰할 리포트 | 아니요. [reverse 도구](../../tools/figma-token-sync/reverse/README.md)로 검토 |
| 소비자용 토큰 내보내기 | 같은 스냅샷의 `figma_tokens.g.dart` + `tokens.figma.json` | 소비 프로젝트가 쌍으로 받아 검증하는 별도 경로 |
| 코드의 token/component export | CoUI 라이브러리를 Figma에 투영할 데이터 | code→Figma 생성 경로 |

색상은 코드의 팔레트 입력에서 유도되므로 Figma에서 색 변수만 바꿨다고 Core에
역반영되지 않습니다. 소비자용 dimension 내보내기를 Core 원본을 임의로
덮어쓰는 수단으로 사용하지 않습니다. 두 파일을 다른 시점에 따로 받으면
짝 검증이 깨집니다.

Figma 브랜치에서는 Import/Generate를 할 수 있지만, 구조 스냅샷의 정본
fileKey 검증은 다릅니다. 구조 리포트는 브랜치를 merge한 뒤 정본에서 받는
절차를 [reverse 레퍼런스](../../tools/figma-token-sync/reverse/README.md)에서 확인합니다.

## 다른 세션의 bundle과 충돌한다면

**루트**에서 아래 읽기 전용 명령으로 소유자를 확인합니다.

```bash
cd tools/figma-token-sync
npm run bundle:owner
```

예상 결과: bundle의 워크트리·브랜치·커밋 정보가 출력됩니다. 다른 작업의
bundle이라면 manifest 경로와 담당 세션을 확인하고 빌드 위치를 정합니다.
강제 덮어쓰기를 기본 해결책으로 쓰지 않습니다.

## 팀에 배포하기

**개발 plugin을 빌드한 것**, **팀 plugin을 게시한 것**, **라이브러리 변경을
Publish한 것**, **소비 파일이 업데이트를 받은 것**은 각각 별개입니다.

현재 GitHub Actions의 **Figma plugin package**가 ZIP을 준비합니다.
기존 팀 plugin의 **Publish new version**은 게시자가 Figma Desktop에서
수행합니다. 이후 라이브러리 파일에서 Import/Generate와 검증을 완료하고
라이브러리 변경을 게시해야 소비 파일에서 업데이트할 수 있습니다.
[배포 절차](../../tools/figma-token-sync/README.md)와 [업그레이드 체크리스트](upgrading.md)를 따르세요.

## 소비 파일 점검 — 넘기기 전에 글자 확인

**제품 화면 파일**(CoUI 라이브러리를 쓰는 소비 파일)에서 돌리는 읽기 전용 점검입니다.
화면을 앱 개발자에게 넘기기 **전에** 그 파일의 디자이너가 돌립니다. 라이브러리
업데이트를 받은 뒤에도 한 번 더 돌립니다.

왜 필요한가: 텍스트 스타일이 붙은 글자는 코드에서 역할 이름 하나(`labelSmall` 등)로
옮겨지고, CoUI 가 바뀌면 같이 따라갑니다. 숫자로만 지정한 글자는 옮기는 순간 굳습니다.
드리프트 점검 · 낡은 세트 보기 · CI 가드는 모두 라이브러리 파일과 이 저장소만 보므로,
소비 파일의 글자는 이 점검 말고는 아무도 보지 않습니다.

돌리는 법:

1. 소비 파일에서 플러그인을 열고 **관리** 탭 → **소비 파일 점검**을 누릅니다.
   범위는 **현재 페이지**(기본) 또는 **모든 페이지**입니다.
2. 화면 흐름 주석처럼 점검할 필요가 없는 레이어가 있으면 그 이름을 쉼표로 적어
   건너뜁니다. 이름은 레이어 이름과 글자 하나까지 같아야 합니다. 그 이름의 레이어
   아래는 읽지 않고, 건너뛴 글자 수와 **범위에서 찾지 못한 이름**을 로그에 따로
   적습니다 — 조용해진 목록이 깨끗한 목록으로, 철자가 틀린 이름이 건너뛴 것으로
   읽히지 않게 하려는 것입니다. 적은 이름은 이 컴퓨터에 기억해 두고 다음에 플러그인을
   열 때 다시 채웁니다(파일에는 쓰지 않습니다).
3. 결과는 같은 분류 · 같은 값을 한 줄로 묶어 개수와 함께 보여 줍니다. 줄을 누르면
   그 글자들을 선택하고 화면을 옮깁니다. 여러 페이지에 걸친 줄은 페이지마다 버튼이
   붙습니다. 다른 명령이 도는 동안에는 목록이 눌리지 않습니다 — 선택은 현재 페이지를
   옮기는데, 도는 명령은 새 노드를 현재 페이지에 만들기 때문입니다.
   **아무것도 바꾸지 않습니다** — 고치는 것은 디자이너의 판단입니다.

| 분류 | 뜻 | 할 일 |
|---|---|---|
| 경고 · 가져온 사본 중복 | 이 파일이 같은 라이브러리 변수를 두 번 가져와 사본이 둘이다. 옛 사본에 묶인 레이어는 라이브러리가 바뀌어도 옛 값으로 남고, 사본이 둘인 변수는 확장 컬렉션에서 덮어쓸 수 없다(`Mismatched variable type`). 줄마다 옛 사본을 참조하는 노드 · 스타일 · 별칭의 수와 현재 사본과의 모드별 값 차이를 적습니다 | **옛 사본 다시 연결**을 누르고 파일을 닫았다가 다시 엽니다(아래). 「라이브러리 컴포넌트 안」으로 남은 자리는 라이브러리 업데이트를 받습니다 |
| 경고 · 옛 브랜드 컬렉션 | 화면이 브랜드마다 따로 게시되던 라이브러리 컬렉션(`Semantic/ Color · <브랜드>`)에 묶여 있다. 브랜드 확장 컬렉션은 `Semantic/ Color · CoUI` 변수만 덮으므로 그 자리는 브랜드 값이 바뀌어도 따라오지 않는다. 줄마다 참조하는 노드 · 스타일 · 별칭의 수와 같은 이름의 `Semantic/ Color · CoUI` 변수(짝)를 적습니다 | **옛 브랜드 컬렉션 다시 연결**을 누르고 파일을 닫았다가 다시 엽니다(아래). 「짝 없음」인 줄은 어느 슬롯이어야 하는지 정해 손으로 다시 연결합니다 |
| 경고 · 브랜드 원시값에 직접 | 화면이 코드 브랜드의 원시값(`Primitives` 의 `color/<브랜드>/…`)에 직접 묶여 있다 — 이것도 브랜드 값을 따라오지 않는다 | 어느 시맨틱 슬롯이어야 하는지 정해 손으로 다시 연결합니다. 명령은 옮기지 않습니다 |
| 경고 · 덮어쓰기 | CoUI 컴포넌트 안 글자의 글꼴 · 굵기 · 크기 · 행간 · 자간 · 텍스트 스타일을 인스턴스에서 바꿨다 | 덮어쓴 값을 되돌립니다(Reset). 그 모양이 필요하면 그 컴포넌트의 리디자인 이슈로 올립니다 |
| 경고 · 역할에 없는 조합 | 크기 · 행간 · 자간 · 글꼴 중 하나라도 역할과 다르다. 줄에 가장 가까운 역할과 다른 값을 함께 적습니다 | 그 역할에 맞춥니다. 꼭 필요한 값이면 역할 추가를 리디자인 이슈로 묻습니다 |
| 경고 · 스타일 없음 | 값은 역할과 같은데(굵기만 다른 것 포함) 역할에 연결돼 있지 않다 | 줄에 적힌 스타일을 붙입니다. 굵기만 다르면 붙일 때 굵기가 역할의 굵기로 바뀝니다 — 그 굵기가 꼭 필요하면 그 굵기의 역할을 리디자인 이슈로 묻습니다 |
| 경고 · 로컬 스타일 | CoUI 라이브러리가 아닌 텍스트 스타일 — 이 파일의 로컬 스타일, CoUI 와 이름만 같은 로컬 사본, 다른 라이브러리의 스타일 | CoUI 라이브러리 스타일로 바꿔 붙입니다 |
| 통과 · CoUI 스타일 | CoUI 라이브러리의 텍스트 스타일이 붙었다 | — |
| 통과 · 역할 변수 + 굵기만 다름 | 스타일은 없지만 크기 · 자간이 역할 변수(`font-size/<역할>` · `letter-spacing/<역할>`)에 묶였고 굵기만 다르다. 이 점검을 정한 요구사항이 통과로 정한 모양입니다 — Figma 는 스타일 위에 굵기를 덮으면 스타일을 떼어 냅니다 | 새로 만들지는 않습니다. 캔버스 규칙([팀의 디자인 토큰 규칙](https://github.com/coco-de/skills/blob/main/internal/coui/rules/core/design-tokens.md) 의 "Figma 캔버스에서 타이포는 텍스트 스타일로 적용한다")은 역할의 시맨틱 변수에 묶인 채 굵기를 덮은 노드를 피할 모양으로 적고, Generate 는 같은 경우 역할을 버리고 크기 단계 변수(`font/size/<n>`)에 묶습니다 |
| 통과 · 고정폭 글 안 한글 | 코드 글 안의 한글 구간을 **고정폭 한글 칠하기**가 본문 서체로 칠했다 — 스타일은 떨어졌지만 크기 · 줄 상자 · 자간은 그 글의 코드 역할과 같다 | — (글을 고쳐 쓴 뒤에는 칠하기를 다시 돌립니다) |
| 대상 아님 · CoUI 컴포넌트 안 | 덮어쓰지 않은 CoUI 컴포넌트의 글자 — 라이브러리의 몫입니다 | — |
| 대상 아님 · 다른 라이브러리 컴포넌트 안 | CoUI 가 아닌 라이브러리(기기 상태 표시줄 같은 것)의 글자. 덮어써도 경고하지 않습니다 | — |

이 점검에서 문서를 바꾸는 명령은 같은 칸의 두 버튼 — **옛 사본 다시 연결**과 **옛 브랜드
컬렉션 다시 연결** — 뿐입니다.

**옛 사본 다시 연결**은
모든 페이지에서 옛 사본을 참조하는 이 파일의 노드(채움 · 선 · 효과 · 그 밖의 필드) · 로컬
스타일 · 로컬 별칭을 현재 사본으로 옮기고, 다시 읽어 남은 참조를 셉니다. 플러그인은 옛 사본을
지울 수 없습니다 — 참조가 0 이 된 뒤 **파일을 닫았다가 다시 열면** Figma 가 정리합니다. 다시
열면 이 파일이 쓰지 않는 라이브러리 변수도 그 덮어쓰기와 함께 정리되므로, 연 뒤에는 **토큰**
탭의 **같은 이름의 로컬 토큰으로 다시 맞추기**를 돌립니다. 이 명령은 확장 컬렉션마다 덮어쓰기가
없는 변수에 이름과 타입이 같은 로컬 변수의 별칭을 모든 모드에 넣고, 짝이 없는 변수를 로그에
적습니다. CoUI 컴포넌트를 새로 넣은 뒤에도 돌립니다 — 새로 들어온 변수는 덮어쓰기 없이 CoUI
기본값으로 칠해지기 때문입니다.

**옛 브랜드 컬렉션 다시 연결**은 모든 페이지에서 옛 브랜드 컬렉션의 변수를 참조하는 이 파일의
노드 · 로컬 스타일 · 로컬 별칭을 라이브러리 `Semantic/ Color · CoUI` 의 **같은 이름** 변수로
옮깁니다. 범위는 옛 사본 다시 연결과 같습니다 — 인스턴스 안은 이 파일이 덮어쓴 필드만 옮기고,
라이브러리 컴포넌트 안에서 덮어쓰지 않은 자리는 라이브러리 업데이트를 받습니다. 짝이 없는 이름과
브랜드 원시값에 직접 묶인 곳은 옮기지 않고 로그에 적습니다. 다시 읽어 남은 참조를 센 뒤, 파일을
닫았다가 다시 열고 **토큰** 탭의 **이름으로 다시 맞추기**를 돌립니다 — 새로 묶인 CoUI 변수에
브랜드 확장의 값이 채워집니다. 브랜드 컬렉션 목록은 코드 브랜드(`brands.json`)에서 읽습니다.

역할 판정은 Generate 가 라벨에 스타일을 붙일지 정할 때 쓰는 비교 함수(`roleDeparture`)와
역할 표를 그대로 씁니다 — 필드가 같은지의 답은 두 자리에서 같습니다. 다만 묻는 것이
달라 결론이 다를 수 있습니다: 이 점검은 "스타일을 붙이면 그림이 바뀌는가" 를 묻기 때문에
행간을 다른 단위로 적어도 같은 그림이면 같은 역할로 보고, 글자가 그려지는 타이포 모드의
값과 견줍니다. 굵기만 다른 글자는 Generate 가 역할을 버리는 경우인데, 이 점검은 역할
변수에 묶였으면 통과로, 아니면 스타일 없음으로 셉니다(위 표). 한 글 안에 모양이 섞여
있으면 구간마다 따로 판정하고, 로그는 그때 글 수와 구간 수를 함께 적습니다.

### 도달 범위 — 여기까지만 봅니다

- **글자 모양만** 봅니다. 색 · 간격 · 컴포넌트 선택은 보지 않습니다. 예외는 「가져온 사본
  중복」입니다 — 글자가 아니라 변수를 보고, 범위와 상관없이 파일 전체(숨은 레이어 포함)를
  봅니다. 인스턴스 안은 이 파일이 덮어쓴 자리만 이 파일의 참조로 세고, 라이브러리 컴포넌트가
  들고 있는 자리는 「라이브러리 컴포넌트 안」으로 따로 셉니다. 그라데이션 색 지점의 바인딩은
  보지 않습니다.
- **크기와 자간은 그 글자가 그려지는 타이포 모드의 값과 견줍니다.** 텍스트 스타일은 크기와
  자간을 역할 변수에 묶으므로, 붙였을 때 그려지는 크기는 그 글자가 푸는
  `Semantic/ Typography` 모드(Mobile · Tablet · Desktop)의 값입니다. 소비 파일은 대개 첫
  모드인 Mobile 로 그리고, 거기서는 display · headline 이 코드 스케일보다 작습니다(Mobile 의
  Headline/Large 는 24). 그래서 Mobile 프레임에서 숫자로 적은 24 는 Headline/Large 로
  나옵니다. 두 역할이 그 모드에서 같은 그림을 그리면(Mobile 의 Headline/Medium 과
  Title/Large 의 20) 모드마다 크기가 같은 역할을 제안합니다 — 숫자로 적은 글자는 모든
  모드에서 그 크기입니다. 모드마다 크기가 다른 역할을 제안할 때는 줄에 그 모드를 함께
  적습니다.
- 글자의 모드를 읽지 못하면 코드 스케일(Desktop)과 견주고, 모드마다 크기가 다른 역할이면
  "붙여도 그림이 그대로" 라고 말하지 않습니다 — Mobile · Tablet 으로 그려지는 글자라면 붙일
  때 크기가 바뀝니다. 크기가 역할 변수에 묶인 글자는 그려진 크기가 모드를 알려 주므로 이
  일이 없습니다.
- 행간을 역할과 다른 단위로 적은 글자는 같은 크기에서의 역할의 단위로 바꿔 견줍니다 — 배수
  역할은 퍼센트로, 고정 줄 상자 역할(코드 역할의 21px)은 픽셀로. 그림이 같으면 같은
  역할입니다.
- **앱 코드는 보지 않습니다.** 앱이 이 글자를 어떻게 옮겼는지는 앱 저장소의 몫입니다.
- **라이브러리 업데이트를 받았는지는 보지 않습니다.** 디자이너가 일부러 미루는 경우가
  있어서입니다. 옛 판의 CoUI 컴포넌트 안 글자도 대상 아님으로 셉니다.
- 보이는 글자만 읽습니다. 자기나 조상이 숨겨진 글자, 빈 글자는 세지 않습니다.
- CoUI 컴포넌트의 슬롯에 바꿔 넣은 **이 파일의 컴포넌트** 안 글자(대화상자의 내용 ·
  앱 바의 앞쪽 같은 자리)는 화면 글자처럼 읽습니다 — 라이브러리 안에 있어도 이 파일의
  글자입니다.
- 로컬 컴포넌트 **정의** 안에서 CoUI 컴포넌트 글자를 덮어쓴 것은 그 정의가 있는
  페이지를 점검할 때 보입니다. 그 로컬 컴포넌트의 인스턴스는 덮어쓰기를 정의에서
  물려받고, Figma 는 물려받은 덮어쓰기를 인스턴스에 적지 않습니다.
- CoUI 컴포넌트는 플러그인 빌드가 아는 컴포넌트 이름으로 알아보고, 모르는 이름이면
  글자가 CoUI 타이포 변수에 묶였거나 CoUI 텍스트 스타일이 붙었는지로 한 번 더 묻습니다.
  둘 다 아니면 다른 라이브러리로 셉니다 — 오래된 빌드의 플러그인은 그렇게 새 컴포넌트를
  놓칠 수 있습니다(라벨을 모두 덮어써 스타일도 변수도 남지 않은 경우).
- 본문 서체 이름은 범위 안의 CoUI 스타일과 `font/family` 변수에서, 없으면 범위 안 CoUI
  컴포넌트의 글자가 그려진 서체에서, 그래도 없으면 켜진 라이브러리 `Primitives` 의
  `font/family/<이름>` 변수 이름에서 읽습니다(읽기만 합니다). 모두 없으면 글꼴은 비교하지
  않고 로그에 그렇게 적으며, 그때는 스타일을 붙여도 그림이 그대로라고 말하지 않습니다.
- 한 줄이 한 페이지에서 선택하는 노드는 200개까지입니다. 개수는 늘 전체 수입니다.
- 줄은 분류와 값으로만 묶고, 어느 레이어 아래인지는 묶는 기준이 아닙니다. 그래서 주석
  글자와 화면 글자가 같은 모양이면 한 줄에 섞입니다 — 주석 레이어는 이름을 적어
  건너뜁니다(2번).
